# Second Root — Development Claude 自律進行ルール

> 目的: 「CI/レビューの通知待ちで何時間も止まる」を防ぎ、許可済みの開発を人間承認の境界まで確実に進める。
> 本書は `docs/AI_WORKFLOW.md`、`.ai/tasks.json`、`.ai/blockers.md` に**追加する運用ルール**。既存のセキュリティ・権限・レビュー・CI・品質基準を緩めない。

## 1. 原則

- **承認済みの現在の Task / スコープ内**では、調査 → 最小実装 → テスト → 修正 → Fresh Review → 最新HEADのCI確認 → 条件付き feature→develop マージ → develop反映確認 → `.ai/` の状態更新まで、原則として都度質問せず進める。
- 必要のない「次は何をしますか？」を挟まない。レビューで見つかった問題を直し、必要な再確認を済ませたら次へ進む。無関係な機能追加や無制限のリファクタリングはしない。
- GitHubの **feature→develop** 自律マージは `docs/AI_WORKFLOW.md` §4 の全条件を満たす場合のみ。**develop→main は必ず人間承認**。
- このルールは、個別の承認ゲート（例: HUMAN-017・HUMAN-018）の承認を**意味しない**。

## 2. CI / 外部確認の待ち方（再発防止）

1. push 後、対象PR番号・**最新head SHA**・開始時刻・必要なcheck・Fresh Reviewの対象SHAを記録。
2. 通知イベントだけに依存しない。セッションが実行可能であれば、約5分後にGitHub Actions/check-runを**直接照会**し、未完了なら約10分ごとに再照会する。可能な範囲で待機時間に独立して進められる安全な作業を進める。
3. 途中でpushが増えたら、**最新head SHAの必須CIとFresh Reviewを再評価**。旧SHAの成功を新SHAの成功とみなさない。
4. 最新SHAの必須CIがすべて成功し、Fresh Reviewer PASS（最新head SHA対象、`.ai/reviews/<task-id>.md` に保存済み。feature→developでは常に必須）、Critical/Highが0、競合なし、Protected Scope変更なし、必要なintegration条件達成を確認できたら、追加の問題がない限り自律マージしてdevelopを確認する。
5. checkが失敗したらログを調べて修正する。timeout/infra障害とコード不具合は区別する。テストのskip・閾値引き下げ・チェック解除による「green化」は禁止。
6. **セッション自体が停止したら自力で再開できるとは限らない**。有効な待機実行環境や承認済みのscheduled checkがない場合、「自動的に後で確認する」と約束しない。進捗と次の確認条件をGitHubに残し、利用者に**現時点では自動再開できない**と報告する。
7. 目安として、同じ外部待ちが30分以上続いて解決不能、または確認可能な時間枠を使い切った場合は、沈黙して待ち続けず、未完了の理由と最新状態を明示する。実際に存在しないタイマーやリマインダーを作成済みと主張しない。

## 3. 人間承認まで進める／必ず止める境界

**自律でよい:** 既存Task範囲内のソース・docs変更、テスト、Fresh Review依頼・修正、PR作成、CI確認、条件を満たすfeature→developマージ、進捗の記録、リポジトリ・GitHub/CI・ローカルtest環境の**読み取り専用**の診断（Production/Stagingのデータ・secretへのアクセスを除く）、実行コマンド・rollbackの準備。

**実行前に個別の明示承認が必要:**

- `HUMAN-018`: Second RootのWSL上で実Codexにデザイン画像を生成させる操作（ChatGPT利用枠を消費）。`HUMAN-017`: 3店舗比較のWSL実Codex実行。
- Production / Staging / Supabase・DBの書き込み・reset、設計worker / queue / bridge / flag / timerの実行・切り替え、実営業のDM・メール送信。
- develop→mainのマージ・Production公開、secret/credentialの設定や移動、課金や契約、権限・セキュリティ境界の変更。
- `docs/AI_WORKFLOW.md` §7 のProtected Scope、実機設定変更（`.wslconfig`等）、破壊的なファイル掃除・データ削除、不要ブランチ削除、許可範囲外の外部副作用。
- CIやFresh Reviewが不足するマージ、品質ゲートの変更・弱体化。

承認待ちは**勝手に実行しない**。既存の承認済み範囲だけを使い、非破壊な準備を完了してから、**承認対象・コスト/時間上限・副作用・実行コマンド・停止条件・rollback**を提示する。「この運用ルールに同意した」ことを個別承認に読み替えない。

## 4. 作業の現在地と復旧

- 初回と再開時は `docs/AI_WORKFLOW.md` §2 の全手順に従い、加えて開いているPRと最新head SHAのCIを確認する。
- 作業の意味ある区切りでcommit+pushし、**Task / branch / PR / 最新SHA / CI / review / 次のアクション**を記録する。feature branchでは `.ai/progress.md` を編集しない（`.ai/progress.md` 冒頭の注意）。作業中の現在地はPRの説明・コメントに残し、merge後に `docs/AI_WORKFLOW.md` §3 に従ってdevelopへの `.ai/` のみの記録commitで `progress.md` を更新する。
- 人間の操作待ちは `.ai/blockers.md` のID・解除条件を明示する。権限がない・ツールが使えない・ローカルWSLにアクセスできない場合は、処理したふりをせず具体的な次操作を提示する。
- 既存Task以外に進む場合は `docs/AI_WORKFLOW.md` §3 の新規Task追加ルールを守る。新機能・MVP拡大・有料サービスを自分で決めない。

## 5. 報告フォーマット

- **現在地:** Task、PR、branch、最新SHA、CI（どのSHA）、Fresh Review、マージ状態。
- **完了事項:** 実際に確認した事実のみ。
- **ブロッカー:** `なし / HUMAN-xxx / CI / 実機アクセス / その他` と具体的理由。
- **次の一手:** 自律で続行する操作、または**人が承認する正確な範囲**。
- **影響範囲:** Production / Staging / DB / worker / timer / 送信に触れたか（なければ未変更）。

「作業中」「待っています」だけで終えない。実行できない作業と実行済みの作業を混同しない。

## 6. 例（HUMAN-xxx 待ちの PoC PR）

- PoC PRのコードreviewとCIが最新SHAで成功したら、merge条件を確認してfeature→developマージまで進める。
- 実機での実行（例: HUMAN-018）は別途承認が出るまで実行しない。成果物が実際にできるまでは「生成済み」と言わない。
- 成果物の手動受け渡しが必要なら、該当runbook（例: `docs/operations/design-image-poc.md`）の手順を案内する。後続工程を先回りして自動で本番公開しない。
- すでにPRがマージ済みなら、同じレビュー/mergeを繰り返さず次の承認待ちタスクの準備へ進む。


## 7. 目標達成型・低トークン運用（2026-10-30 オーナー方針）

> **成果物・品質・事業への寄与を最大化し、同じ調査・報告・レビューのループを減らす。** この節は上記の承認境界と `docs/AI_WORKFLOW.md` のCI・レビュー条件を緩めない。

1. **開始時に1つの到達点を固定する。** `.ai/tasks.json`・`.ai/progress.md`・進行中PRから、未完了の最優先成果物と終了条件を1つ選ぶ（2026-10-30時点の例：架空菓庵 B v1.1 のPC1440・SP390全ページ比較。完了後は再開しない）。目標と無関係な抽象化、研究件数拡大、予定外PRを始めない。必要な作業は既存TaskとPRの中で完結させる。
2. **承認済みのスコープは自己完結させる。** 必要箇所の調査 → 最小修正 → 対象テスト → 独立Fresh Review → 最新HEADの必須CI → 条件付きfeature→developマージ → 完了記録。実行可能な作業を「次は何をしますか」で止めない。特別な承認を一般の自律マージ許可に読み替えない。
3. **原因単位でループ予算を設ける。** 同一問題の修正は原則2案まで。直らなければログ・試した修正・最小再現と停止理由を残し `blocked` にする（既存のTask試行上限3回を超えない）。新しい証拠がない調査の反復は禁止。CI失敗はまず失敗テストとログに絞り、症状に沿う修正をする。ランダムなpushやジョブ再実行でgreenを狙わない。
4. **レビューは原則1回＋必要な差分レビュー1回。** Medium以上や安全性に関わる問題を修正したら最新HEADの変更範囲を独立Fresh Reviewerが再確認する。なお `docs/AI_WORKFLOW.md` の「マージ対象の最新HEADに対するFresh Reviewer PASS」は常に必要。Lowは実害があるものだけまとめて直し、見送った理由を残す。未解決なら止める。
5. **CIの失敗は分類して対処する。** 実際のassertion失敗と、timeout・OOM・ネットワーク・キャンセルを区別する。一時的障害と証拠がある場合だけ失敗jobを最大1回再実行。旧SHAの失敗は新SHAの失敗と混同しない。テストskip・基準緩和・失敗の隠蔽はしない。
6. **トークンを節約する。** 読むのは必要な差分と該当行だけ。既に得たSHA・ログ・結論を再収集しない。ログは失敗箇所だけ抽出し、対象テストを先に回す。複数agentによる同一調査、定型の進捗連投、通知ごとの反応、説明の重複、進捗報告だけのPRを避ける。意味ある区切りでのみ簡潔に記録する。
7. **報告はゲート単位。** 原則「完了」「解決できないブロッカー」「個別承認が必要」の3場面だけにまとめ、日本語で `結果 / HEAD SHA / CI・レビュー / 次の1アクション / 影響範囲` を短く書く。終了したsessionが自動再開するとは主張しない。
8. **オーナー承認を越えない。** 実Codexは承認IDごとに個別の明示許可が必要（研究テキスト承認や「自律化の承認」は実行許可ではない）。実画像生成・再試行も別承認。main・公開・DB・秘密情報・営業送信・worker・jail・CI基準の変更は既存のProtected Scopeに従う。生成の技術合格・デザインの暫定評価・オーナー最終判断を混同しない。

---
本ルールは「継続して勝手に動ける能力」を新たに与えるものではない。**動作可能なセッション内の自律進行**と、停止後にも再開できる永続的な作業記録を定めるものである。
