# Second Root — デザイン先行の制作方針（2026-10-25 決定）

**決定者:** オーナー（2026-10-25、「その方針で固めよう」）。**状態:** 制作方針として決定。実画像生成・アセット利用・CSS制限変更・本番操作の個別承認ではない。追跡: [DEV-108 / Issue #131](https://github.com/ioda47871-byte/second-root/issues/131)。

## 到達目標

小規模な実店舗に対し、その店の実際の特徴を反映した、プロ品質で**店舗ごとに構図が違う**オリジナルWebサイトを作る。固定テンプレートの選択・技法の数・テスト通過数を成功の代理指標にしない。

**主経路: 事実と素材 → 店舗固有の Design DNA → 方向性2案 → ChatGPTによるWebデザイン画像（別途承認） → Claudeによる忠実な実装 → 1440/390の実画面比較 → オーナーの最終判断。**

### 役割と責任

| 担当 | 責任 | 禁止・注意 |
|---|---|---|
| Claude / 店舗分析 | 公式情報やオーナー提供情報を根拠とともに整理し、逐語引用・欠けた情報・利用可能な素材を記録する | 店舗の実績、商品、顧客層、価格、予約経路、写真を補完しない |
| 参考研究 / Design DNA | 根拠が追える技法を選び、異なる構図の2案を作る | 80の参照候補を80の審査済み根拠と見なさない。参考サイトの写真・ロゴ・独自レイアウトを転用しない |
| ChatGPT / アートディレクション | 店舗らしさを表現するオリジナルWebページの画像・余白・文字・商品への視線誘導を設計する | 見栄えだけのポスター、無断の本物らしい店舗画像・実績・値段、実装不能な表現を押し通さない |
| Claude / Web実装 | デザイン画像・構図の仕様をもとに、事実JSONを唯一の文言根拠としてHTML/CSSを作る | 画像の文字から事実を創作しない。作りやすさを理由にデザインを黙ってテンプレート化しない |
| 自動検査 + AI比較 | 技法・引用・素材・CSS制約を検査。PC/スマホの実画面を撮り、視覚上の差分と悪化点を報告する | テストの合格を「美しい」の証拠にしない。見ていない解像度・動作は unknown |
| オーナー | デザインの美しさ・採用・画像利用・公開の最終判断 | AI案を自動でhuman_reviewedへ昇格させない |

### ルールの位置づけ

1. **技法利用の適格判定は事実にのみ依存**する（DEV-107を維持）。業種を入れ替えただけで技法が使えるようになることはない。
2. **クリエイティブな方向性の探索では業種・サイトの目的・オーナーの希望を参考にしてよい。** ただし、業種から実在商品・強み・予約の事実を推定することは禁止。根拠が欠ければ「情報不足」と明示する。
3. Design DNAの8項目と技法T1〜T8は**安全な判断材料**であり、構図・配色の8種類の固定テンプレートではない。2案は配色違いではなく、Heroの見せ方・節のリズム・視線誘導に実質的な差を持たせる。
4. 見た目の設計は先に行うが、CSSの現行許可表・画像権利・店舗の事実は早期に照合する。「デザイン先行」は「制限解除」ではない。

## 設計から公開までのゲート

| Gate | 前進に必要な証拠 | 失敗時 |
|---|---|---|
| G0 入力品質 | 実在する引用・使える商品名・店の強み・CTAの真偽・承認済み素材一覧、欠けた項目 | 不足項目を一覧化。嘘を埋めない |
| G1 コンセプト | 同一店舗で**構図の異なる2案**、根拠を持つDesign DNA、使わない技法の理由、1440/390の想定 | 別の構図を提案。業種テンプレートへの退避はしない |
| G2 デザイン画像 | **別途個別承認された生成操作**でWebサイトらしい画像を得て、人が元画像を確認。既存の `docs/operations/design-image-eval-template.md`：hard failなし・合計22/25以上・各項目4以上・人の確認 | 本実装に進まず方向性を見直す。画像が出たことだけでは合格にしない |
| G3 レスポンシブ設計 | 1440の完成構図に加え、**390pxの別設計**（順序、CTA、文字、余白、商品、nav）が具体的。390pxのデザイン画像がないなら「モバイル画像との一致」は未検証と明記 | 390pxプランを補強。PC画像の縦長トリミングで代用しない |
| G4 HTML/CSS実装 | Claudeが事実の正本・現在許されたCSS・使用承認済み素材だけを利用し、1440/390を実ブラウザ描画 | 実装不能な部分と代替案を記録。CSS制限を勝手に変更しない |
| G5 最終比較 | 元画像/構図仕様と実装結果の差（視線・商品視認性・配色・文字・余白・CTA）、スマホの可読性、弱点・悪化点を報告し人が審査 | 再設計か修正。自動スコアやCIを美的評価の代わりにしない |
| G6 公開 | 個別承認・必要なレビュー・公開環境の条件 | 未承認ならローカルPoCで停止 |

**品質基準は維持。** 既存の参考資料・Design DNA・画像評価・comp-to-siteの基準は弱体化しない。独立Fresh Reviewと最新HEADの必須CIに合格するまではfeature→developを統合しない。develop→main、本番デプロイ、Staging/DB/Supabase、worker/timer/bridge/実営業はオーナーの別承認。

## 最初の縦断PoC — 小さく試す

### 本命: 和菓子A「朝の一つ包み」

- **入力:** `design-library/poc/design-dna/proposals/wagashi.json` のA案と、その元fixtureの逐語引用。確認できる「毎朝炊く粒あん」「一つずつお包み」等のみ使う。
- **G1:** 和菓子B「今日の店頭」を**写真なしの構図比較**に使う。両案をサイト完成まで作り込まず、まず本命1案をビジュアルで検証。
- **G2:** どら焼きの美味しさとブランドらしさを両立する、単なるポスターではないWebページ画像（header、Hero、商品、店舗情報、footerを含む）を評価する。画像生成する場合は都度、対象・回数・使用環境を特定して明示承認を受ける。**現時点では画像生成しない。**
- **素材:** デザイン画面から切り抜いた商品写真はページ素材として使用禁止（内部の比較目的の参照だけ）。単独の画像は、そのファイルのSHAと**ローカルでの利用範囲**に結びつく明示的な承認がある場合にだけ使用。無ければ単色プレースホルダーで構造を確認し、写真込み品質は `unknown`。新しい素材生成も別承認。
- **G3/G4:** PC=1440pxとスマホ=390px。PC画像のみでスマホ完成と主張しない。写真有無、fact accuracy、実装制限、アクセシビリティ、レイアウトのずれを比較。
- **合格宣言:** 画像品質の人の評価と実装忠実度の審査は**別々**。どちらも成立して初めて「この一連の方法が一例で動いた」と言える。量産可能性は別店舗で再検証する。

### 補助テスト

- **和菓子B:** 画像を使わない比較基準。ビジュアルの勝者と自動判定しない。
- **パン屋A「店名の二つの半分」:** 情報が乏しいfixtureで誤魔化さずに止められるかの確認。最小必須の実商品名、特徴、写真権利、予約/来店の目的など、不足項目を出力する。無理に完成品評価をしない。
- **パン屋B:** 今回は保留。
- **次の独立店舗:** 和菓子Aの縦断PoCが人の評価を通って初めて、実在の事実・素材が十分な別業種でも検証。これも自動営業への投入許可ではない。

## DEV-108 初回の事実・素材監査（読み取り専用、2026-10-25）

正本は `scripts/sales-design-worker/compare/shops/wagashi.json`（DEV-073の**架空の店舗**）と `design-library/poc/design-dna/proposals/wagashi.json`。以下は人が確認した実在店舗の事実ではなく、**ローカル比較用fixtureの確認**。

| 項目 | 実際にfixtureで確認できる範囲 | PoCの扱い |
|---|---|---|
| 店名 | `架空菓庵` | 比較用の架空名として使用可能。実在商号とは主張しない |
| 商品 | 説明文に `季節の上生菓子`、`粒あんのどら焼き` | **説明文にある逐語引用だけ**利用。menu_itemsの `テスト` 品名は製品名として使用しない |
| こだわり | `毎朝炊く粒あん`、`一つずつお包みしています` | 和菓子Aの番号付き説明T4に採用可。「手作りの歴史」「限定販売」「受賞」等は追加しない |
| 営業情報 | `9:00〜18:00（売り切れ次第終了）`、`水曜・第2火曜` | 架空店舗のダミー情報として表示可能。現実の店への来店誘導には使わない |
| 所在・アクセス | `名古屋市東区テスト町一丁目2-3`、`テスト線テスト駅 1番出口から徒歩4分` | ダミー地名・路線を実在アクセスとして扱わない。部分引用の `1番出口から徒歩4分` だけで実用導線が完成したとも主張しない |
| 電話・予約 | `052-000-0731`。予約経路の事実なし | 架空の番号から実在の電話導線や予約可能性を創作しない。実際の発信リンクを設置しない |
| 画像 | 和菓子の単独画像・その使用許可・ファイルSHAと承認範囲をこのリポジトリから照合できていない | **G2商品画像・G4ページ素材には未承認**として扱う。SHAに結びつく承認記録が存在し、人が照合するまでは画像として使用しない（現時点でリポジトリに該当記録はない） |
| 必要なサイト行動 | 購入・通販・予約の確かな経路なし | Heroのリンクは事実に対応するページ内情報等に限定する。注文可能性を示唆しない |

**既存提案との矛盾（修正ポイント）:** `proposals/wagashi.json` の和菓子A `product_visual.choice` は「the crop the owner approved for private local PoC use」と記す。この切り抜きは、オーナーが Issue #117 で局所 PoC の非公開用途に限って承認したものだが、オーナーの 2026-10-25 の決定（Issue #131、同日のチャットでの画像利用条件）が**既存のWebデザイン画像から切り抜いただけの画像は実装素材に使わない**と定めたため、ページ素材から外れる。`docs/operations/design-image-assets.md` も comp の切り抜きを内部参照だけに限っている。**compから切り出した画像は実装素材に使わない**。実際に独立の素材画像とSHAに紐づく個別承認があれば、その用途を別途照合する（現時点では未確認）。DEV-107の提案ファイル自体をこのTaskで書き換えたり、画像利用を既成事実化しない。

**G1を満たす材料:** A案は「どら焼きの断面写真を主役＋朝の2工程を番号付き＋店舗情報」、B案は「文字による季節の上生菓子＋来店前の情報札」。構図上の差は説明できる。両案の個別の美的評価はまだ行われていない。

**G2の実行経路:** リポジトリに現在あり、承認の手順が決まっている画像生成の経路は、WSL 上の Codex CLI（`sr-designgen` の ChatGPT サインイン、承認1回につき1回の呼び出し、`docs/operations/design-image-poc.md`、HUMAN-018 型の個別承認）だけである。comp-to-site の取り込み（`docs/operations/comp-to-site.md`）もこの PoC の `report.json`（`png_sha256` 等）と fixture の事実を前提にする。オーナーが ChatGPT の対話画面など**別の経路**で作った画像を使う場合は、その取り込みの設計（出所・SHA・事実との照合・評価記録）と承認を先に別途決める必要がある。

**G2の最初の必要な確認:** 画像生成の実行経路（上記）、使用する方向性と入力SHA、画像生成回数と利用枠、コンプの表示範囲、失敗時の停止条件を明示したうえで**個別承認**を受ける。生成された画像は直接見て、製品魅力・ヘッダー／商品／情報／footerのWeb構造を含むか採点する。**まだ画像の出力も正式スコアも存在しない。**

**G3で必要な別設計:** デスクトップ1440では左に商品画像・右に店名の非対称構図。モバイル390では DEV-107 の A 案の `mobile.choice` どおり、**完全な店名と「毎朝炊く粒あん」→商品画像（全幅）→番号付きの 1「毎朝炊く粒あん」・2「一つずつお包みしています」→説明文の品名（季節の上生菓子・粒あんのどら焼き）→ダミーであることを明示した店舗情報**。スマホに元画像の単純縮小を使わない。実装した実画面で確かめるまで、レイアウトの成否は未知。

**判断:** アートディレクションの**オフライン準備は可能**。しかし、単独素材の権利・承認は未確認で、実画像生成も未承認。G2の先へ進んだという報告はしない。

## 次の実務順（安全な準備を先行）

1. この方針をリポジトリの正本として残し、独立Fresh ReviewとCIを通す（DEV-108）。
2. 既存和菓子Aの根拠、画像のSHA・承認範囲、写真の不足、構図・スマホ仕様、現在のCSSで再現できない箇所を**読み取り専用・オフライン**でチェックする。実際に使える画像があるという前提を置かない。
3. G1で「何を視覚化するか」「画像なしでも検証できる範囲」「G2画像生成の必要性」を記録する。
4. **最初の実画像生成はHUMAN-xxxとして個別に承認してから1回ずつ**。勝手にCLI/Codex/WSLへアクセスせず、計測可能なハードフェイル・品質審査を通す。
5. 人がG2を承認した後だけClaudeのHTML/CSS実装へ進む。その後のworker・営業・公開は別タスク/別承認。

## 改訂時の注意

- 研究候補80件、10件のレスポンシブ調査は**観察と候補**。元の `human_review` は `pending` を維持し、技法採用判断を参考元の正式な人間レビューに転用しない。
- CSSの固定表示・clip-pathや波形・切り欠き・店名以外の縦書きは現状未承認。魅力的な案に含まれても実装可能として誤記せず、独立のcapability審査と承認を求める。
- 同じ文章を使わないことは美しさ・独創性の証明にならない。実画面とオーナー判断を優先する。

## 2026-10-28｜追加の研究運用ルール：Identity Lock

CP-014/015の画像生成で、対象の店名・業種が別店舗（KOALA／cobaco）にすり替わったケースを受け、[店舗同一性監査の研究手順](identity-lock-research-policy.md)を追加した。G0時に店名・業種・出典を固定し、G2の画像を**対象店の画像として扱う前**に出力物の屋号・業種を画像ごとに検査する。不一致はREJECT、未検証はHOLD、店名業種のみ一致はPASS_IDENTITY_ONLYで、デザインの採用とは別判定。

`design-library/intelligence/v02/identity-audit.mjs` は目視結果の構造化記録を検証する研究用ツールであり、OCR/画像生成器の自動検証ゲートではない。本番システム、画像生成の権限や個別承認、既存G0–G6の審査を変更しない。
