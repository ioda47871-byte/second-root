# 店舗専用デモの正式な制作フロー（IMAGE_FIRST、オーナー決定 2026-11-25）

状態: **正式仕様**（オーナー決定 2026-11-25、PR #337 の修正指示を反映）。この文書は工程と原則を定め、既存の実装との違いと実装の順番を §6 に挙げる。違いを埋める実装は別の PR で行う。
実画像生成・root の再設定・営業の送信は、この文書では何も承認しない（実行には毎回オーナーの明示の承認が要る）。

## 1. 正式な制作順序

| 段 | すること | 担当 | 入力 | 出力 | 次へ進む条件 |
|---|---|---|---|---|---|
| 1 | 店舗情報と**成功例の原本**の分析 | Claude（ChatGPT の分析を受けてもよい） | 確認済みの事実、原本を開ける成功例（[全件一覧](../../design-library/success-cases/originals-catalog.md)の区分 A） | 分析の記録と、オーナーが閲覧する確認ページ（§3.1） | 原本で確認した成功例が 3 件以上、かつ**オーナーが原本の選定と採用するデザイン原理を確認** |
| 2 | Web サイト**全体**のオリジナルのデザイン画像を生成 | Codex（IMAGE_FIRST の依頼モード） | 段 1 の分析と原理、事実、承認済みの日本語、成功例の参照画像（§3.5 の上限内） | PC と SP の、それぞれページ全体のデザイン画像（§3.2） | 生成の成功（失敗なら止まる。§4） |
| 3 | 独立評価と**オーナー承認**でデザインを確定 | 独立レビュー（Claude の別の文脈）、オーナー | 段 2 の画像 | デザイン審査の記録（§3.3）と承認の記録（承認した画像の SHA-256） | 審査の記録がそろい、オーナーが承認（生成の成功だけでは進めない） |
| 4 | 承認したデザインに要る写真・背景・装飾の素材を生成 | Codex | 承認したデザイン画像（参照、上限内）、素材の一覧（デザインから決める） | 素材の画像（「イメージ」として管理） | 生成の成功と、素材の独立レビュー |
| 5 | デザイン画像に**忠実な** Web サイトの実装 | Claude | 承認したデザイン、段 4 の素材、事実 | HTML/CSS | — |
| 6 | Playwright で PC/SP を撮影し、元のデザインと比べる | Claude | 段 5 の頁、段 2 の画像 | PC1440・SP390 の全ページ画像、比較の記録 | 再現性の審査 |
| 7 | 品質審査の後、オーナーへ完成デモを提出 | Claude → オーナー | 段 6 の結果、文章の監査 | 確認ページ | オーナーの最終承認（公開と送信は別の承認） |

## 2. 原則

1. **成功例の原本を実際に確認してからデザインに着手する。** 文章の記録だけの成功例を「参照した」と書かない（§3.1）。
2. **既存のテンプレートに当てはめない。** 節の順番・数・形を、コードで固定した骨格から作らない。
3. **写真素材を先に大量に生成し、それに合わせてデザインを決める方式を標準にしない。** 素材は、承認したデザインが求めるものだけを、その後で作る（段 4）。
4. **デザイン画像の生成が失敗したら止まる。** Claude が HTML/CSS の直接の設計に切り替えて、それを IMAGE_FIRST の成功として扱わない（§4）。
5. **デザイン画像の承認の前に本実装を始めない。**
6. **PC と SP の構図、日本語の情報設計を評価する。** 日本の客に向けた店では日本語が情報の中心（英語はブランドと装飾）。
7. **Codex の実行の制約に合わせる**（§3.5。参照画像の上限など）。
8. 店の事実を作らない（Identity Lock）。未確認の商品・価格・営業時間・製法・歴史・理念は書かない。足りない情報は「追加調査が必要」と記録する。
9. 生成した写真は営業提案用のイメージ素材（MVP_SPEC §7.1 の限定の改定の 5 つの条件）。

## 3. 段ごとの決まり

### 3.1 段 1: 分析の記録とオーナーの確認

店ごとに、非公開の置き場（リポジトリの外）へ記録する。各成功例について:
- id、**証拠の種類**（画像で確認 / 頁を描画して確認 / 文章だけ）、見たファイルのパスと SHA-256
- 構図・情報設計・店らしさ・PC/SP の表現の観察
- その店へ持ち込む**原理**（構図そのものではない）と、写さないこと
- その店の事実から導いた、**その店固有のデザインの原理**（成功例の足し合わせではない）

**オーナーが閲覧できるようにする。** 分析の記録から、非公開の確認ページ（ローカルの HTML。外部へ公開しない）を作る。選んだ原本の画像（または頁の画面写し）を開ける形で並べ、それぞれの横に、採用するデザイン原理と写さないことを書く。オーナーは原本の選定と原理を確認し、足りない・違うと判断すれば選び直す。この確認が段 2 へ進む条件。

成功例の全件と原本の所在は [`design-library/success-cases/originals-catalog.md`](../../design-library/success-cases/originals-catalog.md) にまとめた（原本あり・文章のみ（未取り込み）・所在不明の 3 区分。原本ありはそこから開ける）。オーナーの採用記録では重複を除いて 37 件、GitHub の台帳には 31 件で、差の 6 件（SR-002、CP-033〜037）は原本が ChatGPT ライブラリにあり未取り込み。2026-11-25 に原本を開けるのは 4 件（CP-001・CP-002・CP-003・SR-001）で、**他店の参照に数えられるのは 3 件**（CP-001〜003）。SR-001 は架空の店の Second Root 自身の頁で、台帳の方針（`second-root-research-successes.json`「他店の参照ではない」）により閲覧はできるが参照には数えない。**一覧の作成だけでは「成功例をすべて見られるようにする」作業は未完了。** 全件を開ける閲覧ページの整備、原本の復元（ChatGPT ライブラリからの取り込みと SHA-256・目視の照合）、参照の義務化の検査は Issue #336 で続ける。

### 3.2 段 2: ページ全体のデザイン画像

- デザイン画像は、**ページ全体として一貫した構図**であること。決まった節（hero・紹介・言葉・品書き・情報など）を 1 枚ずつ描いた分割画像を並べたものは、正式なデザイン画像として扱わない。
- PC と SP は、**同じデザインの方針**（段 1 の原理・色・書体・素材の扱い）に基づき、**それぞれ独立して設計する**。SP は PC を縦に積み直したものではない。
- 節の数と順は、コードで決めずに、分析と方針から決める。
- 縦に長いページで道具の解像度が足りないときも、節ごとの分割で補わない。全体の画像を先に承認し、細部が要るときは、その承認した全体の画像を参照する追加の画像で補う（追加の生成は許可枠の中で、§5）。

### 3.3 段 3: デザイン審査の記録

独立レビューは、次の 5 つの観点ごとに、判定（合格 / 要修正 / 不合格）と根拠（画像のどこを見たか）を記録する:

| 観点 | 見ること |
|---|---|
| 独自性 | 既存のテンプレート・成功例の構図の写しになっていないか |
| 店舗固有性 | その店の確認済みの事実と固有の原理から来ているか。店名を入れ替えても成り立つ汎用の構図ではないか |
| 情報設計 | 読む順、必要な情報だけか、行動の導線（来店・連絡・SNS など）が分かるか |
| 日本語 | 日本語が情報の中心か。文字の量・行の長さ・読む順が日本語に合っているか。未確認の事実を書いていないか |
| PC/SP の完成度 | それぞれが独立した完成した構図か。SP の最初の画面で店が分かるか |

**技術的な生成の成功（画像が保存された）だけでは段 4 へ進めない。** 5 つの観点の記録がそろい、オーナーが承認したときだけ進む。判定はオーナーが下す（独立レビューは助言）。

### 3.4 段 3 と段 4 のつながり

段 4 の依頼は、段 3 で承認したデザインの run と、承認した画像の SHA-256 を参照する。素材の一覧（何を・どの比率で・どこに使うか）は、承認したデザインから決める（自由記述の写真の題材ではない）。

### 3.5 Codex の実行の制約

- 1 回の依頼 = Codex の実行 1 回・画像 6 枚まで・再試行なし・1 依頼 ID は 1 回だけ（root の事前許可の上限の中）。
- **参照画像は 1 回の画像の呼び出しにつき 5 枚以内**（安全策として採用。根拠は §4.1）。成功例・承認したデザイン・素材のどれを参照するときも、1 枚の画像の生成で参照するのは 5 枚以内にし、依頼の検査で 6 枚以上を拒否する。
- 既定のモデルは code mode で画像の道具を呼ぶ。画像の呼び出しの記録は Extension の項目だけで、始まる前に断られた呼び出しは記録が残らない。
- 失敗した依頼も、試行の記録と回数の上限を使う（失敗しても枠を使わない、とは扱わない）。
- 金額は不明。ChatGPT のプランの利用枠（各回 6 枚まで）を使う。

## 4. 失敗したとき

- デザイン画像の生成（段 2）が失敗したら、**その店の制作を止めて報告する**。HTML/CSS の直接の設計への切り替えは、オーナーが例外として指示したときだけ、**研究・暫定の成果**として扱い、IMAGE_FIRST の成功とは呼ばない。
- 同じ依頼 ID の再試行はしない。新しい依頼は、原因の修正とオーナーの新しい承認の後だけ。

### 4.1 `CODEX_NO_IMAGE`（`req-vatten-design-01`、Issue #335）の原因: 証拠と推定

| 区分 | 内容 |
|---|---|
| **証拠**（保存された記録・ソースで確かめた） | 依頼は写真 6 枚を `--image` で添付し、プロンプトは 6 枚の画像（PC 2 + SP 4）のプロンプトのそれぞれで「添付した 6 枚の写真だけを使う」と求めた。Codex は時間切れにならず終了し、利用上限・サインアウトの表示は無く、セッションの記録は読めた。記録に画像の項目・失敗した項目は無く、保存された画像も無い（`image_calls=0`、`image_failed=0`）。止まった区分は `TOOL_NOT_SEEN_CODE_MODE`。同じ CLI・同じ既定のモデル・同じ大きさのデザインの依頼で、写真を添付しなかった 11-21 の run は 6/6 枚を保存した。画像の道具は、引数の検査で `referenced_image_paths` が 6 件以上なら拒否する（文言「must contain at most 5 paths」は `docs/operations/design-image-poc.md:436` に記録、その拒否の検出は `lib/design-agent/design-image/capability.ts:220` の `INVALID_ARGS_SIGN`）。引数の検査で拒否された呼び出しは項目を残さない。 |
| **推定**（記録で直接は確かめられない） | モデルが 6 枚を参照して画像の道具を呼び、上限 5 枚で拒否され、プロンプトの「失敗したらすぐ止まる」に従って終えた（最有力）。ほかに、添付画像のパスを渡せなかった、指示の矛盾（実店舗の「商品を描かない」と添付の写真）で止めた、の可能性も残る。モデル名は失敗の run では記録されず、同じ機械で 15 分前の run から推定した。区別に要る記録（code mode のセル数・引数の拒否）は保存されず、セッションの記録も片付けで消えたため、どれかに確定できない。利用上限は除外できる（上限なら失敗した項目が残るか、終了コードが変わる）。 |
| **採用する対策** | 推定が確定しなくても、**参照画像を 1 回の呼び出しにつき 5 枚以内にする**ことを安全策として採用する（§3.5）。あわせて、引数の拒否と code mode の記録を run の事実に残す（Issue #335 の修正）。 |

## 5. 許可枠と承認

- 生成は root の事前許可（1 日・1 週の回数の上限、固定した worker の commit、期限）の中だけで行う。
- **デザインの修正（段 2 の作り直し、段 3 の要修正）や生成の失敗で許可枠が足りなくなったときは、新たなオーナーの承認が要る。** 枠の追加・期限の延長・固定 commit の更新は、オーナーが root で行う。Claude は枠を増やさず、枠の外で生成しない。
- 失敗した依頼も枠を使う（§3.5）。1 店に少なくとも 2 回（デザイン・素材）が要り、直しにはさらに回が要る。

### 6.1.1 再開の条件（2 段階を区別する）

| 再開するもの | 範囲 | 条件 |
|---|---|---|
| **(a) デザイン生成段階の再試験** | 段 1〜3（分析・オーナーの確認 → ページ全体のデザイン画像の生成 → 審査）だけ。素材の生成・本実装には進まない | §6.1 の 1〜3 がマージ済み、オーナーによる固定 commit の更新、**その店の実画像生成の新しい承認** |
| **(b) 正式な制作フローの運用開始** | 段 1〜7 の全部（デザインの承認 → 素材の生成 → Claude の実装 → 再現性の検証 → 提出） | (a) の条件に加えて、§6.1 の 4〜9 がマージ済み、Issue #336 の閲覧ページと参照の照合が使える状態、素材の生成の別の承認 |

**1〜3 は (a) の最小条件であって、正式な制作フロー全体の完成条件ではない。** (a) で承認されたデザインが出ても、(b) の条件がそろうまでは素材の生成と本実装に進まない。

### 6.2 運用上の制約（実装を変えずに守る）

- 許可枠: 事前許可は 1 日 2 回・1 週 2 回（オーナーが設定）。足りなければオーナーの新しい承認（§5）。
- 固定 commit: root の事前許可は worker の commit を固定する。develop に入った修正を使うには、オーナーが root で更新する。
- 1 回の依頼は画像 6 枚まで、再試行なし、1 依頼 ID は 1 回だけ。失敗も枠を使う。
- 既定のモデルは固定していない（`-m` なし。2026-11 は gpt-6.1-terra、code mode）。モデルが変わると道具の呼び方の記録が変わりうるので、run ごとにモデル名を記録して確かめる。
- 成功例の原本は区分 A だけを参照に使う。B・C は取り込みと照合の後だけ。

### 6.3 後続の軽微な修正

- 自動実行の要約が写真の run を `image=invalid`・`pc=0 sp=0` と表示する。
- npm の修正（PR #334）の Low 4 件（隠し方の抜け、npmrc の一時フォルダの片付け、試験の不足）。
