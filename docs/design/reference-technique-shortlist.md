# 参考10件から絞った技法の提案（DEV-106、Issue #128）

**状態: AI の提案。オーナーの採用判断待ち。** human review ではなく、どの技法も採用済みではない。
根拠は `design-library/research/v03/viewport-evidence-20261025.json` の10件の記録（1440 / 390 の実画面、
画像は commit していない）。ChatGPT の第二意見はオーナー経由の3件（DX-002・DX-013・DX-033）だけで、
それも元のスクリーンショットではなく PR の記録をもとにした意見である。

## 前提: Second Root の現在の制約

Claude が実装する CSS は `lib/design-agent/comp-impl/page-css.ts` の許可表に縛られる。主なもの:

- `position` は static だけ（固定表示・追従表示はできない）。`overflow` も不可（横スクロール列はできない）。
- `clip-path`・mask・疑似要素・背景画像は不可（波形・切り欠き・ブロブ形の枠はできない）。角丸 `border-radius` は可。
- 背景は単色だけ。画像は spec の image slot（最大8）として置き、承認済み画像に限る。
- 縦書きは `vertical_name`（DEV-102、未承認）で **店名だけ**。告知文やキャッチコピーの縦書きは範囲外。

このため「既存技術で実装可能か」は、**可**（今の制約の中で作れる）・**一部**（形を変えれば作れる）・
**制約の変更が要る**（人の承認が要る）の3段階で書く。

## 提案（8件）

### T1. 予約・電話への常時導線

- **根拠:** DX-013（スマホのヘッダーに電話と予約）、DX-008（スマホの固定ヘッダーに営業時間と予約、中ほどで固定を確認）、
  DX-011（スマホ下部に院ごとの予約バーを固定）、DX-023（PC で3つのボタンがどのスクロール位置でも右下に残る）。
- **優れている点:** 予約制の店で来訪者が最も探す2つの行動が、スクロールなしで常に届く。
- **適する店:** 理容・美容室、整体・鍼灸、クリニック、予約制の飲食。実在する電話番号か予約手段があること。
- **使うべきでない場合:** 予約を取らない店（パン屋・持ち帰り中心）、予約手段が未確定の店。ボタンが3つを超える場合。
- **PC とスマホ:** PC はヘッダー右に電話番号の文字と予約ボタン。スマホは上部ヘッダーに短く、または下部の1行バーに1〜2個。
- **Claude の実装の難しさ:** 低い（固定しない版）。固定表示は CSS の制約で今は書けない。
- **既存技術:** **一部**。ページ先頭のヘッダーに置くことは可。スクロール中も残す固定表示は **制約の変更が要る**
  （`position: fixed` は検査の前提を変えるため、別の検討と承認が必要）。

### T2. 来店前の不安に答える事実の列

- **根拠:** DX-008（土日祝も営業・駅徒歩3分・近隣パーキング・完全個室を第一画面に線画アイコンで並べる）。
- **優れている点:** 対象の客が「自分に合うか」を本文を読む前に判断できる。
- **適する店:** 制約の多い客層を持つサービス業（子連れ、駐車、営業日、個室など）。
- **使うべきでない場合:** 事実が2つ未満、または確認できない事実しかない場合。4つを超えると雑音になる。
- **PC とスマホ:** PC は第一画面の下に横一列。スマホは2×2の格子。
- **Claude の実装の難しさ:** 低い。ただし事実は店舗の入力からだけ取り、作らない。
- **既存技術:** **一部**。文字と枠（角丸）での列は可。線画アイコンは image slot を使うか、アイコンなしの文字だけにする。

### T3. 文字で読める店舗情報と営業日の表

- **根拠:** DX-005（2店舗それぞれの住所・電話・営業時間・定休日を文字で）、DX-011・DX-036（営業日・定休日の月間カレンダー）、
  DX-008（院名・住所・営業時間・定休日・支払い・駐車場の表）。逆に DX-013 は当初、看板写真にしか時間が無いと誤って記録していた（訂正済み）。
- **優れている点:** 時間と休みが画像ではなく文字なので、読める・写せる・検索に乗る。不定休が電話なしで分かる。
- **適する店:** すべての店。特に不定休・複数店舗・時間帯が分かれる店。
- **使うべきでない場合:** カレンダーは、店が更新し続けられない場合は載せない（古い表は誤解を生む）。
- **PC とスマホ:** PC は写真の横に2列の表。スマホは1列の項目と値。
- **Claude の実装の難しさ:** 低い（表）。カレンダーは中程度（日付の正しさをデータで保証する必要がある）。
- **既存技術:** **可**（表は grid で書ける）。カレンダーは表示は可だが、営業日データの入力項目が今は無い。

### T4. 番号付きの「こだわり」または「選ばれる理由」

- **根拠:** DX-005（大きな橙の数字と丸い写真の3項目）、DX-011（細い数字と線画の6項目）、DX-008（3つの理由）。
- **優れている点:** 店の理由を決まった順で読ませられ、数字で拾い読みしやすい。
- **適する店:** オーナーが具体的に言える理由が2〜4つある店。
- **使うべきでない場合:** 理由が抽象的、または AI が作ることになる場合（一般的な宣伝文になる）。5つ以上。
- **PC とスマホ:** PC は写真と文の左右交互か横並び。スマホは写真→数字→見出し→文の縦積み。
- **Claude の実装の難しさ:** 低い。
- **既存技術:** **可**。数字は文字、写真は image slot。

### T5. 比べられる商品の一覧と、属性の尺度図

- **根拠:** DX-036（豆ごとにロット・焙煎度・産地・精製・風味・価格／売り切れを同じ形の行で並べ、焙煎度を浅→深の尺度図で説明）。
- **優れている点:** 詳しい客は比べて選び、初めての客は尺度図で用語を読める。
- **適する店:** 属性で選ぶ商品の店（コーヒー、茶、日本酒、パンの粉、化粧品）。
- **使うべきでない場合:** 属性の事実を店が出せない場合。行の項目が多すぎてスマホで読めない場合。
- **PC とスマホ:** PC は1行に項目を並べる。スマホは名前と価格を1行目、属性を2行目に折る。
- **Claude の実装の難しさ:** 中程度（項目の折り返しを幅ごとに設計する）。
- **既存技術:** **可**（grid と単色の小さな札）。尺度図は文字と枠の並びで作れる。

### T6. 注文や来店の流れのステップ図

- **根拠:** DX-006（オーダーケーキの注文の流れを、例の写真より前に簡単な絵の段階で示す）。PC の設計画像だけで確認。
  ブランドサイトは HTTPS で開けず、スマホ版は未確認。
- **優れている点:** 手間のかかる注文の不安を、連絡前に下げる。
- **適する店:** 受注生産（ケーキ、花、仕立て、印刷）、初回の流れがある施術。
- **使うべきでない場合:** 流れが店の実際と一致しない場合。絵の中に文字を入れて正確さを保てない場合。
- **PC とスマホ:** PC は横一列の段階。スマホは縦の番号付きリスト。
- **Claude の実装の難しさ:** 低い（文字と番号のみ）。絵を付けると中程度。
- **既存技術:** **一部**。番号と文字の段階は可。線の矢印・絵は image slot か省略。

### T7. 地色の切り替えと、店から決めた一つの形を繰り返す

- **根拠:** DX-002（クリームとベージュの交互で線なしに節を分ける）、DX-005（波形の境界と同じ人物の繰り返し）、
  DX-023（写真の枠とボタンが同じ切り欠きの形）。ChatGPT の第二意見も DX-002 の地色の区分を小規模店向きとした。
- **優れている点:** 少ない要素で「設計された」一体感が出る。形を店の個性から決めれば独自性の芯になる。
- **適する店:** すべての店。形は店の商品・建物・名前の由来から1つだけ選ぶ。
- **使うべきでない場合:** 参考サイトの形（波・切り欠き・ブロブ）をそのまま使う場合は模倣になる。地色の差が小さすぎて区切りに見えない場合。
- **PC とスマホ:** 両方で同じ。スマホでは形を小さく、数を減らす。
- **Claude の実装の難しさ:** 低い（地色）。形は中程度。
- **既存技術:** **一部**。地色の交互は可。形は角丸・円・ピル形の範囲で可。波形・切り欠き・ブロブは **制約の変更が要る**（clip-path 等）。

### T8. 看板商品を一つだけ主役にする第一画面

- **根拠:** DX-027（二色の面に商品一つだけ。ギャラリーの縮小画像でだけ確認、本サイトは 503）、DX-033（大きな商品写真と文字の役割分担）。
  逆の例として DX-002 は第一画面の写真が切り替わり、看板商品が最初に見えるとは限らない。ChatGPT は、看板商品を大きく見せる構成を勧めた。
- **優れている点:** 店が何の店かを最初の画面で決める。
- **適する店:** 明確な看板商品があり、承認済みの良い写真がある店。
- **使うべきでない場合:** 看板商品が無い店、写真が弱い店、複数店舗ブランドの演出を単店に持ち込む場合（ChatGPT の指摘）。
- **PC とスマホ:** PC は商品写真と店名を左右に分ける。スマホは写真を上、店名と一文を下。
- **Claude の実装の難しさ:** 低い（構成）。品質は写真に依存する。
- **既存技術:** **可**（hero の image slot と単色の面）。写真は承認済みのものに限る。

## 提案しないもの（理由つき）

- **店名以外の縦書きの一文**（DX-002・DX-008・DX-011・DX-033 で見た）: 効果はあるが、`vertical_name` は店名だけ。
  告知文や標語へ広げるのは新しい capability と承認が要る。採用するなら別 Task。
- **開幕アニメーション・文字のフェードイン・横スクロールのカルーセル**: 表示の遅れや撮影・閲覧での欠けの原因になり、今の CSS でも書けない。
- **受賞メダルや順位の大きな掲示**（DX-011）: 内容を下へ押し、店の個性ではない。

## 撮影の失敗とデザインの欠点の区別

`OPENING_SCREEN_NOT_CLEARED`・`FULLPAGE_DARK_BELOW_FOLD`・`SCROLL_REVEAL_NOT_RENDERED`・`LAZY_IMAGES_MISSING`・
`POSSIBLE_SLIDE_IN_MID_STATE` などは撮影側の問題として記録し、弱点に数えない。見えなかった項目は `unknown`。
DX-013 の PC は許可された1回の再撮影（15秒待ち）で第一画面だけ確認でき、それより下は `unknown` のまま。
