# 成功例レベルに近づくための制作工程 (DEV-156、Issue #193)

2026-11-03。成功例20件の原理 (`docs/design/success-principles-v1.md`) と失敗パターンから組んだ、Second Root の制作工程の案。

- 実務で毎回使う手順として書いた。各段に、入力・出力・通過の条件・使う道具を置く。
- **この工程を通しても、「成功例レベル」とは言わない。** 判定はオーナーが PC/SP の実画像で行う。
- 参照する成功例の原理 (`principles-v1.json`) は今 `TEXT_ONLY_PROVISIONAL` である。画像のある案件の品質の実証は、Claude 自身が参照画像を見た記録 (`VISUAL_VERIFIED`、DEV-158) があるときだけ行う。
- 実 Codex・画像生成・有料 API・本番の変更は、この工程の中でも別の承認が要る。

## 全体

| 段 | 何をするか | 出力 | 通過の条件 (止める条件) |
|---|---|---|---|
| 1 | 店の情報を集める | 事実パック、情報不足の一覧、店の世界の語彙 | 事実が出典つきであること。業種の一般論で埋めていないこと |
| 2 | 店固有のモチーフを取り出す | モチーフの候補 3つ以上 (源の分類つき)、選んだ中心のモチーフ1つ | チェック C1 |

| 5 | 品質を審査する | 5項目の評価票 (オーナー)、失敗の符号つきの所見 | オーナーの採否。機械の検査は補助で、単独で合格にしない |

## 各段の詳細

### 段1 店の情報を集める

- **入力:** 公式・第三者の情報、実店舗の写真 (権利の確認済みのものだけ)、オーナーの指示。
- **作るもの:**
  - 事実パック (`shop_facts_pack_v1`)
  - 情報不足の一覧
  - 店の世界の語彙 (物・素材・製法・時間・空間・行為)。`second-root-design-director` の手順 2。
- **原理:** P8 (実店舗の事実と空気から始める)。CP-025 v2 は業種の雰囲気で埋めて不採用になった。CP-026 v4 (暗い異国風) は、ドラフト審査待ちの記録の分析 (`design_analysis`) では、実店舗の明るい空気と合わなかった。
- **止める:** 事実が少なく、店の世界の語彙が集まらないとき。業種の一般論で水増ししない。

### 段2 店固有のモチーフを取り出す

- 語彙から、中心のモチーフの候補を3つ以上出す。それぞれに次を書く。
  - 源の分類
  - 「何が構造になりうるか」 (支点 → 釣り合い、棚 → 区画、工程 → 読み順)
- 1つを選ぶ。
- **原理:** P1・P2。
- **チェック C1** (下)。

### 段3 構造が違う3方向を立てる

- 方向ごとに、次を書く。
  - 中心のモチーフが Hero と全区画でどう現れるか (区画ごとのモチーフの面と終点)。
  - 構造記述子の8観点 (`lib/design-agent/structure/descriptor.ts`)。
  - PC と SP の別の計画。
  - 守る核。
  - 参照した成功例の原理 (`principles-v1.json` の P と、使わない理由)。
- **3方向は Hero の型と流れの型の両方が違うこと** (`directionsDiffer`)。配色・写真の差し替え・Hero の左右の入れ替えは別案に数えない。
- **原理:** P2・P3・P4。
- **チェック C2・C3・C5。**

### 段4 PC/SP の完成カンプを作る

- 方向ごとに、PC 1440 と SP 390 の**全頁**を作る。
- オフラインでは、B 方式の試作 (`checkPrototype` と `renderPrototype`、JS 無効・通信なし) で作れる。
  - B 方式は重なり・`transform`・`clip-path`・インライン SVG を使える。実装レーンより表現の幅が広い。
  - 写真は仮の板 (役割と大きさだけを決める)。
- 実画像の生成は別の承認 (Issue #193 §3)。
- カンプの記録に残すもの:
  - 素材 (仮・生成・実写)
  - 書体の有無
  - 作り方
- **原理:** P3・P5・P6。
- **チェック C4。**

### 段5 品質を審査する

- 評価票 (`design-library/research/three-methods/review-sheet.md` の5項目) で、オーナーが PC/SP を見て決める。
  - 5項目: 店舗らしさ・独創性・視覚的完成度・PC・SP。
  - 複数案は盲検で並べる (#180 の X/Y/Z の手順)。
- 機械の所見 (構造記述子・SP の所見・Identity・横はみ出し) は補助で、**単独で合格にしない** (`READABLE_BUT_FLAT` の記録 CP-025 v1「技術的に壊れていないだけ」)。
- 不採用なら、失敗の符号 (`principles-v1.json`) で理由を記録する。

### 段6 実装する

- 既存の実装レーン: `impl-lane`、`comp-impl`、実装レーンの CSS 許可一覧。
- **許可一覧で作れない表現** (重なり・縦書き・切り抜き・等幅の書体) は、勝手に緩めない。
  - 差分表を作り、安全な表現手段を提案する。DEV-083 の段階 B〜F で、オーナーの承認が要る。
- 安全の検査: Identity・横はみ出し・許可一覧。

### 段7 カンプと比べる

- `impl-compare` で、区画ごとの差 (位置・色・縁) を記録する。記録だけ。
- 差の原因を分ける。
  - 許可一覧の制約による差
  - 実装の誤り
  - 素材の違い

### 段8 直す

- **直す前に、守る核を名指しする** (P7)。
- 1巡に1つの原因。上限は直す対象で違う。
  - カンプの自己批評と再設計 (段3〜4): `second-root-design-director` の規則どおり**最大2巡**。2巡で良くならなければ、直すのをやめて報告する。
  - 実装の修正 (段6〜8): `runLoop` の `LIMITS` (3回、原因ごとに2回)。
- 色や反射だけの変更を改良と呼ばない (`SURFACE_ONLY_CHANGE`)。
- 全体の作り直しで核を失わない (`CORE_LOST_IN_REFINEMENT`)。

### 段9 成功と失敗を記録する

- run の記録には、次を残す。
  - 方向・カンプ・実装の SHA
  - 評価
  - 失敗の符号
  - 費用 (呼び出しの回数・時間)
  - 修正の回数
- 成功例 DB への追加は、オーナーが採用したときだけ。原本は public なリポジトリに入れない (SHA と記録だけ)。

## 制作前のチェックリスト (段2〜4 で使う)

機械で読む版は `principles-v1.json` の `checklist`。
- 答えは「はい / いいえ / 未確認」と、根拠 (どこに書いたか、どの画像のどこか)。
- **1つでも「いいえ」なら、次の段へ進まない。**
- 「未確認」は、理由を書いて進んでよい。審査で必ず見る。

| ID | 問い | 判定のしかた | 関係する失敗の符号 |
|---|---|---|---|
| C1 | 店固有性: 中心のモチーフは、この店の事実 (物・素材・製法・時間・空間・行為) から来ているか | 事実パックの id を挙げられること。入れ替えテスト (同業の別の店にすると、どこが成立しなくなるか) に答えられること | `MOTIF_NOT_TRANSLATED`、`GENRE_CLICHE`、`ATMOSPHERE_MISMATCH`、`WRONG_SHOP` |
| C2 | 3方向が構造的に違うか | Hero の型と流れの型が、どの2方向でも両方違うこと (`directionsDiffer`)。兄弟の構造の近さ (`structuralSimilarity`、観点ごとの重みつき) が 0.6 未満であること (以上なら `SIBLINGS_SAME_SKELETON`)。配色・写真の違いだけでないこと | `SURFACE_ONLY_CHANGE`、`TOO_CLOSE_TO_REFERENCE` |
| C3 | Hero 以降まで一貫した世界観があるか | 区画ごとに「モチーフのどの面か」を1行で言えること。最後の区画の終点があること。区画の順を入れ替えると話が壊れること | `HERO_ONLY_WORLD`、`NO_PAGE_STORY`、`LOWER_SECTIONS_GENERIC` |
| C4 | PC/SP がそれぞれ成立しているか | SP の1画面目 (390×844) に何が入るか、PC から並び・大きさ・重なりの扱いをどう変えるかを書けること。SP が PC の縮小・単純な縦積みでないこと | `PC_SP_NOT_DIFFERENTIATED` |
| C5 | 成功例と比べて平凡化していないか | 汎用の LP の印 3つ (汎用の Hero = `split_copy_media`・`centered_headline`、汎用の流れ = `stacked_bands`、区画の半分以上が `split_copy_media`・`grid_cards`) のうち、2つ以上がそろわないこと (機械: `structureFindings` の `GENERIC_SKELETON`)。原理 P1〜P5 のうち、どれを満たすかを方向ごとに挙げられること | `MOTIF_NOT_TRANSLATED`、`LOWER_SECTIONS_GENERIC`、`SPLIT_HERO_DEFAULT`、`READABLE_BUT_FLAT`、`TOO_QUIET`、`MECHANISM_OVER_LOOK` |
| C6 | 写真・図形・文字が関係しているか | 文字・線・注釈がモチーフの言語になっている所を挙げられること。写真の役割が重ならないこと | `IMAGE_TYPE_RELATION_WEAK`、`PROP_OVER_PRODUCT` |
| C7 | 改良なら、守る核を先に名指ししたか | 改良の前に、守る部分と直す部分を分けて書くこと | `CORE_LOST_IN_REFINEMENT`、`OVERCROWDED_INFO` |
