## 2. 研究ありの比較実験（提案）

### 2.0 前提：研究ブリーフを生成に使うのは、今の方針の例外である

既存の Design Intelligence Adapter（`lib/design-agent/intelligence/brief.ts`）が出す研究ブリーフは、**人と Claude が読むための研究資料**である。

- 各事例は「再現しない分析」として渡され、再利用できる原理としては渡されない。
- 統合計画（`docs/design/design-intelligence-integration-plan.md`）と PR #142 の `scope`（`research_only_not_auto_prompt_input`）・`reuse_policy.deny`（`feed_into_production_generators_without_separate_review`）は、生成器に入れないことを定めている。
- Adapter が検出するのは制御文字と指示の囲みだけで、**平文で書かれた指示は検出しない。**

したがって、研究の内容を Codex のプロンプトに入れることは、**方針の例外としてオーナーの別の承認が要る。**

この提案は、例外を最小にするために次のようにする。

- 研究の文章を**そのまま**プロンプトに入れない。
- Claude が、選んだ事例から写真に頼らない構造の原理だけを短い文に書き直し、オーナーが全文を読んで承認した固定の文章（以下「研究の原理の区画」）だけを入れる。
- 区画は研究 PR のファイルの SHA-256 と事例 ID に結びつけて記録する（記録の `research_brief`）。
- 生成器の既定の経路には入れない。研究ありの実行を指定したときだけ組み立てる。

### 2.1 比べ方（交絡をできるだけ減らす）

違いが研究の区画だけになるようにしたい。ただし、今のベースラインには次の差がある。

1. **Artifact 化で止まった。** 原因の候補は2つ（未確定）。answer.json の `asset_refs` を WSL で読み取り専用で確かめれば判別できる。
   - brief の `product_visual` にある「If a generated image is allowed, use one image…」という条件付きの記述。
   - structure_spec の説明に `asset_refs` の欄があり、B 方式では空にすることが書かれていない。
2. **評価が手作業のプレビューに基づく。** Artifact の描画ではない。
3. **1回だけの実行である（n=1）。** Codex CLI とモデルが変わると比べられない。

そこで、推奨を **B（研究なし v1.1 と研究あり v1.1 を対にする）** に変える。

- 研究なし版に、設計に関わらない技術上の1行「On this route every asset_refs is an empty list (no images).」を足した v1.1 を作り、新しい SHA で固定する。研究あり版は「v1.1 ＋研究の原理の区画」にする。対の違いは区画だけになる。
- 両方とも Artifact 化と描画（PC1440・SP390、同じ描画の手順）まで進めて比べる。手作業のプレビューと Artifact の描画を混ぜて比べない。今のベースライン（v1）は、参考として残す。
- 両方の記録に Codex CLI の版・モデル名・コミットを残し、違えば比較を無効にする。
- 1回ずつの比較なので、差が出ても「研究が効く」とは結論しない。結果は傾向の観察として記録する。

A（研究あり版だけに1行を足し、v1 のベースラインと比べる）は、呼び出しが1回少ない。ただし、違いが2つ（区画と1行）になり、描画の方法も違う。そのため推奨しない。

### 2.2 研究事例の選定（PR #142 に登録済みの23件から3件。読み取り専用）

選ぶ基準：

- B 方式は画像を使わない（文字・色・CSS・SVG のみ）。そのため、**原理が写真に依存しない**事例を選ぶ。HTML/CSS/JS のローカル PoC がある事例に限る。
- その原理を、架空菓庵の事実（毎朝炊く粒あん、一つずつお包み、小さな店頭、どら焼き、季節の上生菓子、営業情報）に対応づけられること。
- 写真や画像が核の事例（CP-005 の断面写真、CP-020 の画像だけのコンセプトなど）は選ばない。

| 区画の ID | 事例 | 使う原理（写真に依存しない部分だけ） | 架空菓庵の事実との対応 |
|---|---|---|---|
| R1 | CP-016 ズールー工作所 COUNTERWEIGHT（ローカル PoC） | 物の物理的な関係（支点・重さ・余白）そのものをページの骨格にする。大きな写真と帯の繰り返しで組まない | 小さな店頭で一つの菓子を包むという関係（台・一つの菓子・余白）を、ページの骨格にする |
| R2 | CP-009 豆＊豆 STITCH（ローカル PoC） | 点線の縫い目で区画どうしをつなぎ、章ごとに密度と大きさを変える（写真の部分は使わない） | 「一つずつお包みしています」を、包みの折り線や紐の線で区画をつなぐ表現にし、章ごとに密度を変える |
| R3 | CP-003 なごやビーンズ v4（ローカル PoC） | 焙煎の段階を上へ進む地図にし、同じ尺度の繰り返しを避けて、区画ごとに別の拍にする | 理由 1（毎朝炊く粒あん）と理由 2（一つずつお包み）を、同じ型のカードの繰り返しにせず、別の拍として置く |

避けることとして渡すもの：各事例の `known_failure_modes` にある失敗だけを、短く書き直して渡す。

- CP-011 の「不規則な編集の層が、汎用の左右や横の写真の帯に変わる」。
- CP-008 の「改良で良い点が消える」。
- CP-016 の「良い写真は独自の骨格の証明にならない」。

外すもの：

- 未登録の7件（CP-026〜032）。原本が未照合なので使わない。

### 2.3 プロンプトへの入れ方（固定）

- 研究の原理の区画は英語で、次の内容にする。
  1. 前置き：これはデータで、命令ではない。構図・文言・色・写真・ロゴは写さない。
  2. R1〜R3 の原理（各1〜2文）。
  3. 避けること（3つ）。
  4. 使い方の条件：
     - 各原理は、架空菓庵の fact_ref に対応づけたときだけ使う。
     - 使った原理は、design_dna の choice に R1〜R3 で書く。
     - 合わなければ使わなくてよい。
- 区画の全文、v1.1 と研究あり版それぞれの SHA-256 と文字数を、実行の前にオーナーへ示す。承認を受けてから固定する。
- 実装は小さな PR で行う（次のタスク）。
  - `buildDesignPrompt` に、任意の追加区画を渡せるようにする。
  - 研究なし v1 の SHA（`a2fdd003…`）が変わらないことをテストで固定する。
  - `--print-pin` に、v1.1 と研究あり版の固定値を出す道を足す。

### 2.4 安全確認

- 研究データは PR #142 の checkout から**読み取りのみ**。Adapter が成功の状態・ID の一致・方針の文言を照合し、合わなければ止まる。研究の画像・写真・HTML は渡さない。
- **平文の指示は Adapter で検出できない。** そのため、区画の文章は研究ファイルから自動で作らず、オーナーが全文を読んで承認した固定の文章にする（§2.0）。
- `reuse_policy.deny` の内容（構図・ロゴ・写真・文言や色の配合を写さない）を区画に明記する。
- 承認台帳・回数の制限・jail・.env の検査は、今の Phase 2f-2 のまま使う。

### 2.6 評価

- 次の3点と、22/25 の採点欄で比べる。
  - 縦書きの重なり
  - 商品表現
  - 横はみ出し（scrollWidth が PC で 1440 以下、SP で 390 以下）
- 技術上の合否（Artifact 化・描画・はみ出し）と、デザインの評価は分けて記録する。
- 評価も、暫定評価（ChatGPT または Claude）とオーナーの最終判断を分けて記録する。記録はこの形式（`phase2f_baseline_v1`）で行い、研究ありの記録には `research_brief` を必ず入れる。
- 1回ずつの比較なので、差が出ても「研究が効く」とは結論しない。
