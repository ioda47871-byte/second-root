## 2. prompt: 現行 v2 / v1.1 と 新 v3

### 何が変わるか

- **v3 = v2 + `COPY_V3_RULES` (末尾に追加)**。ほかは v2 と1バイトも違わない (テストで固定: `v3 === v2 + "\n" + rules`)
- v2 を土台にした理由: v2 (開いた方向、brief なし) が B/C の一番新しい版で、事実と技術の規則 (`B_V11_RULES`・`V2_FACT_RULES`・画像の正直さ) を既に持つ。v1.1 は brief を使う古い比較実験の版で、v1.1 との差は v2 との差 + brief の有無になる
- 追加した規則 (英語、他の行と同じ):
  1. **事実とラベルだけ、すべての店で。**事実は逐語 (`fact_ref`)、ほかは短い中立な `ui_label`。言い換え・要約・途中で切る・つなぐ・飾ることを禁じる。決め台詞・タグライン・標語・詩を書かない。回答に創作の欄は無い。**例外は1つ:** v2 の住所の規則 (`名古屋市東区` だけを見せる) が、事実の一部だけを見せてよい唯一の値であると明記した
  2. **発明しない一覧:** 価格、予約の経路、在庫、営業年数・経験年数、店主や店員の言葉、お客様の声、順位、受賞、商品の特徴。無い情報は落とし、業種の一般論で埋めない
  3. **区画の役割:** 各区画に、訪問者がそこで知ることを1つ。`live_text` はその区画が見せる事実を挙げ、見出しは後に続くものを平易に言うラベル。見せる事実の無い内容の区画は飾りで埋めず落とす。中立な `ui_label` だけのナビゲーション (header・CTA・footer) は内容の区画に数えない
  4. **五つの軸を生成の手引きとして** (語の禁止一覧ではないと明記): 自然な日本語 / この店だけ / 役に立つ / 抑制と変化 (ページの声は1行まで、それも事実の value を目立たせたもの) / 正しさ (架空と実在の区別)
  5. **平易は欠点ではない:** メニュー・アクセス・営業時間は良いラベル。詩的にしない。Hero が拠る1つの強い事実は平らにしない

### なぜ

- v1〜v2 は「事実を逐語・中立なラベル」と1行で言うだけで、**区画の役割**と**ページ全体の抑制**を言わない。
  回答の形が許す範囲でも、見出しのラベルを全部同じ型にする・事実の無い区画を作る・Hero 以外にも声を持たせる、はできる
- 仕様案の五軸と「発明しない」一覧を、生成の側にも同じ言葉で置く (審査だけにあると、毎回 REVISE で戻る)

### 意図して変えなかったこと

- **回答の形 (`codex_design_v1`) は変えない。**創作の文 (`creative_expression`) を B/C 経路に入れるには schema の変更が要り、それは承認の範囲外。
  そのため v3 は、架空の店でも創作の文を書かせない (v2 と同じく厳しい側)。架空の研究の店の創作の文は、今までどおり comp-lane の文の記録だけにある
- 語の禁止一覧を prompt に入れない (仕様: ブラックリストでは解決しない)
- 事実パック・方向・参照の扱い、画像の規則、技術の制限
- **v3 は v2 の事実の規則 (`V2_FACT_RULES`) をそのまま継ぐ。**その規則は架空菓庵の fixture 専用 (`テスト` を含む値を見せない、住所は `名古屋市東区` だけ) なので、v3 は**まだ店に依らない版ではない**。別の店で使うには、この fixture 専用の行を店の事実パックから導く形に変える必要がある (有効化の作業に含める。§5)

### 危険

| 危険 | 見込み | 対策 |
|---|---|---|
| prompt が長くなり (6996 → 9594 字)、デザインへの注意が薄れる | 中 | 比較の実行で、デザインの質 (構造記述子・オーナーの評価) が v2 より下がらないかを見る |
| 「平易」を強く言いすぎて、全部が平板なラベルになる | 中 | 「Hero の1つの強い事実を平らにしない」「詩的にしない」の両方を置いた。審査 v2 も平板化を不合格にする |
| 区画を落とす指示で、必要な区画 (時間・道順) まで減る | 低 | 「役に立つ」の軸で時間・道順を名指し。審査の `COPY_INFORMATION_MISSING` が拾う (DEV-199a、PR #259、develop に未マージ。それまでは審査 v2 の手順で人が拾う) |
| 英語の指示が日本語の文体に効かない | 中 | 規則は「どの事実をどの順で見せるか」と「ラベル」に絞った。文体そのものは逐語の事実なので生成側が書かない |
| v3 が誤って実行される | 低 | CLI が拒否 (テストで固定)。実行には CLI の変更 + 承認 ID + SHA の照合が要る |

## 3. 審査: 現行 SKILL.md と 新 文章審査 v2

### 何が変わるか

| 観点 | 現行 SKILL.md (変えていない) | 文章審査 v2 (提案) |
|---|---|---|
| 規則の形 | §1: 見せてよい文字は事実そのままと中立なラベル。決め台詞・言い換えを禁止。§8 の批評表 (critique-checklist 4) で「事実そのままか」を1問 | 区画ごとの役割を先に書く → 五軸で読む → 決め台詞の累積と1つの強い行を区別 → 判定 (fail / hold / revise / approve_candidate) → 道ごとの規則 → 改稿の規則 → 報告の形 |
| 研究の道の創作の文 | `creative_expression` は架空の店だけ (comp-lane.md)。数・役割の点検なし | ページの声は原則1行。Hero 以外の3区画以上の決め台詞は `COPY_RHETORICAL_OVERUSE`、同じ型の見出しは `COPY_REPETITIVE_CADENCE`。ページ全体で1つの指摘 |
| 事実が足りないとき | 「情報不足」と書き、埋めない | 同じ + **HOLD** (再生成しない、創作で埋めない) |
| 改稿 | 守る部分を先に名指し、最大2巡 (デザインの批評) | 同じ + `claim_type` を変えない + 事実は逐語のまま + SHA が変われば審査をやり直す |
| 罰しないもの | (書かれていない) | 普通のラベル、出典つきの平易な文、事実としての「ひとつずつ」。「詩的でない」は不合格の理由にならない。AI の文かどうかを断定しない |
| 承認との関係 | 「最後に決めるのはオーナー」 | 同じ。`approve_candidate` は送信・完成ではない |

判定コードは仕様案と DEV-199a の `copy_quality_review_v1` (別 PR、未マージ) に合わせた。

### なぜ

現行の規則は1行ずつの禁止であり、輪の決め台詞はどれも単独では「架空の店の創作の文」として許された。
足りないのは、ページ全体の累積を見る手順と、事実不足で止まる (HOLD) 手順である。

### 危険

- 審査が厳しすぎて、研究の道の表現の幅が消える → 1つの強い行を明示的に残す。点数は補助で、最後はオーナー
- ディレクター (Claude) の判断がぶれる → 機械の `copy_quality_review_v1` の結果を下限にし、緩めない。報告の形を固定
- SKILL.md と提案の二重管理 → 有効化は SKILL.md から1行で読むか、内容を移すかのどちらか (審査 v2 §9)

## 4. 評価の方法

**ここに書く実行は、どれもオーナーの承認の後である。**この PR では何も実行していない。

1. **文の比較 (費用なし):** DEV-199c の4業種 (パン屋・美容室・飲食店・自転車修理) の commit 済み架空頁の fixture に、
   審査 v2 の手順を当てる。輪の元のコピーで累積を検出し、Hero「まがった車輪も、まっすぐに。」を単独では拒否しないこと、
   平易な出典つきの頁を罰しないことを確かめる
2. **prompt の比較 (Codex の実行、承認が要る):** 同じ事実パック・同じ方向で v2 と v3 を各 N 回。見るもの:
   - `copy_quality_review_v1` の判定と指摘の数 (`COPY_RHETORICAL_OVERUSE`・`COPY_REPETITIVE_CADENCE`・`COPY_INFORMATION_MISSING`)
   - 区画ごとの事実の有無、見出しの型の重なり
   - デザインの質が下がっていないか (構造記述子、`GENERIC_SKELETON`、PC/SP の全頁をオーナーが見る)
   - 回数・費用・店・prompt の SHA は、実行の前にオーナーへ報告する (DEV-199c の計画)
3. **合格の目安 (提案):** v3 が v2 より REVISE を減らし、HOLD を正しく出し、デザインの評価を下げないこと。数値は補助で、決めるのはオーナー

検証計画の正本は **DEV-199c** (`.ai/tasks.json` の DEV-199c。4業種の PC/SP 全頁での過検出・見逃しの検証と、Codex 実行計画の報告) である。
