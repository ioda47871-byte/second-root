1. **Low — a design-view failure hides the whole funnel** (`app/admin/sales/history/page.tsx:27-35`).
   - `loadFunnel` and `loadDesignOutcomes` share one `try`. With `SALES_AI_DESIGN_ENABLED=true`, an error from `sales_design_daily` alone returns `null`. The page then shows 「ファネルを読み込めませんでした」, even though `sales_funnel_daily` loaded fine.
   - Suggestion: catch the design load separately and fall back to `design: null`, or show a design-only error.
2. **Low — an unknown design code is shown twice** (`components/admin/FunnelSummary.tsx:124`).
   - For a code that is not in `DESIGN_ERROR_LABEL`, `designErrorLabel` returns the raw code, so the line reads `CODE（CODE）`.
   - This is cosmetic only. The DB check `^[A-Z][A-Z0-9_]{2,47}$` limits codes to uppercase identifiers, so no free text or PII can leak.
3. **Low — migration ordering against DEV-058.** `origin/feature/dev-058-review-summary` adds `20261020120000_sales_design_review.sql`, which sorts after this migration.
   - If DEV-058 reaches Staging first, `supabase db push` rejects 20261020110000 as out of order (it would need `--include-all`).
   - The two do not conflict in schema: DEV-058 only adds columns and replaces a function, and neither drops nor retypes anything these views depend on.
   - Suggestion: apply them to Staging in timestamp order. Note that both timestamps are dated tomorrow.
4. **Low — test gaps.**
   - No test covers the page-level fallback (view missing → funnel section error, rest of 履歴 intact). No test covers the flag-off path that skips `loadDesignOutcomes`; the unit test only renders `FunnelSummary` with `design={null}`.
   - Both behaviours are simple and read correctly in the code.
5. **Low — possible flake near JST midnight** (`tests/integration/funnel.test.ts`).
   - `since` and "today" are fixed when the module loads, and the persist cap is 5 shops per JST day.
   - A run that crosses 00:00 JST while seeding could either hit the cap or split the "today" rows across two days. It is unlikely in CI.

## Checked and fine (reviewer)

- **State machine vs. stage definitions.** I read `20260927000000` (checks plus the `sales_check_outreach_update` transitions) and `20260927000200/0300/0500`.
  - Only `drafted→sent|lost`, `sent→replied|lost`, `replied→meeting|lost` and `meeting→won|lost` are possible.
  - `lost` can follow a send. The view correctly counts those as sent, and only `lost ∧ sent_at is null` as 見送り.
  - `sales_mark_sent` sets `status` and `sent_at` together, so a drafted row never has `sent_at`. That makes 準備 = 見送り + 送信 + 未送信 exact.
  - `sales_record_reply` requires `sent`, so a reply implies `sent_at`. The meeting step requires a reply, and won requires a meeting, so the stages nest and rates are ≤ 100%.
  - `won_amount_jpy` is non-null exactly when `status='won'` (check constraint).
  - DNC does not close drafts. A DNC'd draft stays in 未送信 and is also counted in DNC, which matches the docs.
- **Consistency with `sales_metrics`.** The total row uses the same tests for sent, replied, meeting, won and amount. The integration test asserts equality, and `sales_metrics` itself is unchanged; `metrics.test.ts` still passes.
- **JST bucketing.**
  - `(created_at at time zone 'Asia/Tokyo')::date` does not depend on the session TimeZone.
  - `jstDate` adds a fixed +9h offset (Japan has no DST), so it does not depend on the server TZ.
  - `periodSince` = JST today − 29 days, inclusive, which is 30 days. The same `since` filters SQL (`gte`) and `sumFunnel`.
  - Boundaries are tested in unit tests (23:59:59 vs 00:00 JST) and in integration (00:00 JST included, 1s earlier excluded).
- **Security.**
  - Both views are `security_invoker=true` over tables with admin-only SELECT RLS.
  - Grants are SELECT only to `authenticated` and `service_role`. PUBLIC, anon and authenticated get `revoke all`, and the service_role default write privileges are revoked too. The integration test asserts the exact grant set.
  - A non-admin gets 0 rows, and anon gets `42501`.
  - The only text column is `design_error_code`, which is regex-constrained, so no emails or names are exposed. The view is read only with the flag on.
- **Joins.** The unique partial index on the initial outreach per prospect and `sales_demos.prospect_id unique` rule out double counting.
- **searchParams.** Next 16.3.6 and `PageProps<"/admin/sales/history">` (typegen) are used, and `searchParams` is awaited as a Promise. `parseFunnelPeriod` accepts only `"30d"` and `"all"`; arrays and unknown values fall back to 30d. Admin auth runs before anything else.
- **Migration.** It is additive: two new views and grants, with no table, function or `sales_metrics` change. It applies cleanly after 20261019120000 (`supabase db reset` ran clean locally). It is not idempotent (`create view`), which matches the repo convention for one-shot migrations.
- **Scope.** Changes stay within allowed_scope, with no forbidden-scope changes. Docs (MVP_SPEC §9.1, ARCHITECTURE) match the SQL.
