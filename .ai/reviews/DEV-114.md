## 判定: FAIL（Critical 0 / High 1 / Medium 4 / Low 5）

render_pair_complete や handoff を不正に作る経路（fail-open）は見つからなかった。構想画像・原本の欠落・生成情報の不明・停止・寸法違い・2倍描画・未宣言/差し替え/リンク/親リンク/ハードリンク/FIFO は、どれも止まるか incomplete になる。quarantine の試作が `handoff.files` に入る経路もない。

一方、オーナーの拘束要件2「画素数・PNG ファイルサイズの上限を**テストで検証**」が満たされていない。テストは定数の値を見るだけである。強制する分岐を消す変異でも、全テストが通る。これを High とした。

Medium は4件である。
- `readChecked` の差し替え対策がテストで守られていない。
- png.ts との一致テストの網羅が不足している。
- C の「素材ごとの承認」が緩い。
- オーナーアップロードの出所が整合していない。

### High

1. **画素数・PNG バイト数・パッケージ合計の上限が強制されていることを、どのテストも検証していない。**
   - **場所:**
     - 強制している箇所: `lib/design-agent/artifact/intake.ts:199`（`width * height > limits.maxPixels`）、`:178`（`bytes.length > limits.maxBytes`）、`:326`（原本の読み込み上限 `cap = limits.maxBytes`）、`:337`（`PACKAGE_LIMITS.totalBytes`）
     - テスト: `tests/unit/design-agent/artifact/intake.test.ts:241-253`
   - **原因:** テスト `keeps the limits tied to the existing ones` は `PNG_LIMITS.*.maxPixels` などの**定数の値**を比べるだけである。上限を超える入力を拒否するテストがない。
     - 例外: 高さ 16001 のテスト（`maxSide`）。
     - サイズ上限のテストは、試作 CSS と `artifact.json` だけにある（`:223-229`）。
   - **再現（変異実験。どれも 73/73 pass）:**
     - `checkArtifactPng` の `|| width * height > limits.maxPixels` を削除
     - `checkArtifactPng` の `bytes.length > limits.maxBytes ||` を削除
     - 原本の読み込み上限 `cap = limits.maxBytes` を `1e9` に変更
     - パッケージ合計の検査を `if (false)` に変更
   - **影響:**
     - 現在のコードは正しく止まる。ただし、要件2は「画素数・ファイルサイズ・メモリの上限をテストで検証」を拘束条件としている。
     - 構想画像では `maxSide` 8192 なので、8192×8192 = 6700 万画素が `maxPixels` だけで止まっている。この検査が消えると、後の展開で 268 MB の RGBA を許してしまう。それでも CI は気づかない。
   - **修正案:** 次の4件のテストを足す。
     1. 構想画像 7000×6000（4200 万画素・各辺は 8192 以下）→ `ARTIFACT_PNG_INVALID`
     2. 1440 の描画で、IHDR は正しく、`maxBytes`+1 バイトになるよう補助チャンクで水増しした PNG → `ARTIFACT_TOO_LARGE`（`readChecked` の上限）
     3. 同じ PNG を `checkArtifactPng` に直接渡す → `ARTIFACT_PNG_INVALID`
     4. 上限以内のファイルを積み、合計が `totalBytes` を超えるパッケージ → `ARTIFACT_TOO_LARGE`
     - 4 は、テスト用に上限を注入できないなら、上限以内の素材を必要な数だけ並べれば作れる。24 MiB×4 程度で済む。

### Medium

1. **`readChecked` の差し替え対策（fstat 照合・`/proc/self/fd`・親ディレクトリの再確認・読み込みバイト数の一致）は、どれもテストで守られていない。**
   - **場所:** `intake.ts:121`・`:123-124`・`:125-131`・`:139`
   - **再現（変異実験。どれも 73/73 pass）:**
     - `:121` の dev/ino/size/nlink の照合を `if (false)` に変更
     - `:124` の `real !== path` を無効化
     - `:130` の親の再確認を無効化
     - `:139` の `got !== e.size` を無効化
   - **原因:** 親リンクのテスト（`intake.test.ts:173-180`）は、走査の時点ですでにリンクであるため、`inventory`（`:96`）で止まる。`readChecked` の検査は一度も実行されない。
   - **評価:** コードの理屈は健全である。
     - 開いた fd の inode が走査で見たものと同じであること、開いた時点の実パスがルート内であること、親が走査時と同じ inode であることを順に確かめる。
     - 確かめた後に読み、同じバッファで SHA と PNG を検査する。
     - 親を一瞬リンクに替えて戻す攻撃や、ファイルを外へ rename して戻す攻撃も、`/proc` の実パスか inode の照合で止まると判断した。
     - ただし、受け入れ基準5「確認と読み込みの間の差し替えを拒否する」の根拠は、テストに一つもない。
   - **修正案:** テスト用に、`inventory` の直後に呼ばれる差し込み口（例: 内部 export の `intakeArtifactForTest({ afterInventory })`）を設ける。そこで次の操作をして、それぞれ `ARTIFACT_PATH_UNSAFE` になることを確かめる。
     - 親を rename してリンクに置き換える
     - ファイルを同名の別ファイルに置き換える
     - ファイルを伸ばす・縮める
     - ハードリンクを足す
     - 本番の経路に影響しない形にすること。

2. **png.ts との一致テストの網羅が不足している。**
   - **場所:** `intake.test.ts:255-287`、`intake.ts:191`・`:198`・`:200-201`・`:205`・`:211`
   - **png.ts を import しない判断について:** 判断自体は妥当である。`design-image-poc.test.ts` の既存ガード（design-image を import してよいのは PoC と comp-impl だけ）を緩めずに済む。比較用に、テストからだけ png.ts を import している。現状のコードは、png.ts と行単位で同じ判定である（読み比べた）。
   - **不足:** 一致テストの8ケースは、署名・IEND なし・末尾データ・CRC・bit depth・最小辺・最大辺だけを扱う。
   - **再現（変異実験。どれも 73/73 pass）:** 次の6分岐は、片側を消してもテストが落ちない。
     - 2つ目の IHDR
     - IDAT 0個
     - interlace 値
     - 空でない IEND
     - チャンク名の文字種
     - `maxPixels`
   - **影響:** 将来どちらかが変わると、「同じ構造検査」という文書（`docs/design/design-artifact-v1.md:51`）の主張が、黙って崩れる。
   - **修正案:** ケース表に次を足す。
     - IHDR の重複、IDAT なし、interlace=2、IEND に1バイトのデータ、チャンク名 `1DAT`
     - 長さ 0x80000000、`maxPixels` 超え、`maxBytes` 超え
     - 描画用の上限（`viewport_render_*`）でも同じ照合をする

3. **C の「素材ごとに別の承認」が強制されていない。**
   - **場所:** `intake.ts:313`、`lib/design-agent/artifact/schema.ts:206-207`
   - **再現（scratchpad）:** 次の条件をすべて満たす C のパッケージが、`render_pair_complete` になった。2つの素材は `handoff.files` に入る。
     - 2つの `ai_concept` 素材が、同じ `approval_id` を持つ
     - その値は、本体の実行の `generation.approval_id` とも同じ
     - `image_outcome` は `TOOL_NOT_CALLED`
     - 片方の素材（A2）は、どの section からも参照されない
   - **原因:** 検査は `approval_id !== null` だけである。
   - **影響:**
     - 要件5の「C = B の構造 + 別途承認された画像素材」は、文字列があることしか確かめていない。
     - 素材の `approval_id` は実行プログラムの申告である。それなのに、記録の `runner_reported` に載らず、状態の判定だけに使われる。
   - **修正案:**
     - `ai_concept` 素材の `approval_id` が、互いに異なり、本体の `generation.approval_id` とも異なることを要求する。
     - 参照されない素材を拒否する（または handoff から外す）。
     - 素材の承認 ID を `runner_reported` に出し、「形式だけ、承認の証明ではない」と notes と文書に明記する。

4. **`chatgpt_owner_upload_compat` の出所が整合していない。**
   - **場所:** `intake.ts:216`・`:303`・`:306-309`・`:390`、`docs/design/design-artifact-v1.md:34`
   - **再現（scratchpad）:**
     - オーナーアップロードの A が `concept_only` になるのは、`generation.tool: "codex_cli"`・`approval_id`・`prompt_sha256`・`run_id` などの Codex 実行の事実が、すべて埋まっているときだけである。
     - どれか1つでも `null` なら `incomplete` になる（例: `generation_unverified:tool`）。
     - また、`image_outcome: "IMAGE_SAVED"` のオーナーアップロードも通る。
   - **影響:**
     - fail-open ではない。concept_only は handoff を持たないし、不明は incomplete 側に倒れる。
     - しかし、文書（「オーナーのアップロードとして技術検証を通過 → concept_only」）とコードが食い違う。
     - concept_only に届くには、実行プログラムが存在しない Codex 実行を申告するしかない。これは要件3の「データの出所で区別する」に反する。
   - **修正案:** 次のどちらかにする。
     - オーナーアップロードでは `generation.tool`・`image_outcome` を `null`・`not_applicable` に固定する。生成情報の必須欄を、アップロード用の別の集合（取り込み実行の ID・時刻など）にする。
     - オーナーアップロードは常に `incomplete` とし、文書をそう直す。

## 確認したこと（要件ごと）

1. **検証状態と承認の分離:**
   - **状態の導き方:** `render_pair_complete` / `concept_only` / `incomplete` は `intake.ts:386-397` で毎回導く。どこからも読まない。
   - **handoff の条件:** handoff は `render_pair_complete` のときだけである。
   - **render_pair_complete の条件:** 両方の原本が present、かつ `viewport_render`、かつ理由0件のときだけ成立する。
   - **A と B/C の混在:** 経路の検査では、`viewport_render` は A 以外、`concept_image` は A だけに限られる。そのため、A と B/C の混在や、片方だけが描画という状態は作れない。
   - **A の扱い:** A は理由0件でも concept_only である。handoff は空で、`concept_images_are_not_pc_sp_renders` が付く。1440×2000 の構想画像でも concept_only だった（scratchpad）。
   - **人のゲート:** `human_gates` は定数の `not_done` である。承認を作る・確定するコードはない。

2. **viewport_render:**
   - 幅は 1440 / 390 ちょうど、高さは spec の `page_height`（`Px` で 16000 以下）と一致する必要がある。
   - PNG の上限: `maxSide` 16000、`maxPixels` は幅×16000。
   - 2倍描画（780×6000）は、`maxPixels` 以内だが幅で `ARTIFACT_VIEWPORT_MISMATCH` になる。意図した理由で止まっている。
   - `observed.render.device_scale_factor` は `z.literal(1)` である。
   - `MAX_RENDER_HEIGHT` と comp-impl の `MAX_PAGE_HEIGHT` の一致は、テストで固定されている。
   - 画素数・バイト数の**強制**のテストがない点は、High 1 のとおりである。

3. **スキーマ:**
   - `schema.ts` は `z.strictObject` だけを使う。`z.object`・`passthrough`・`catchall` は0件である。
   - `DeclaredDesign`（`omit`）も、余分なキーを拒否する（テストあり）。
   - JSON の `__proto__` キーは、`DesignArtifact`・`CodexDesign` のどちらでも拒否された（scratchpad）。
   - `CodexDesign` には、状態・承認・検証・ファイル・SHA の欄がない。
   - 判定は型と欄だけで行う。「approved」を含む説明文は通る（テストあり）。
   - observed（実行プログラムの報告）は、記録で `runner_reported` に分けて出る。
   - 保存された記録を読む処理はない。パッケージ内の `gate-record.json` は未宣言ファイルとして止まる（テストあり）。

4. **ファイルの安全性:**
   - **パスの形:** RelPath は、`..`・絶対パス・バックスラッシュ・末尾ドット・非 ASCII・空白・4階層以上を拒否する（scratchpad で確認）。
   - **走査:** リンクをたどらない。ファイルのリンク・親のリンク・ハードリンク・FIFO・未宣言ファイルは、すべてテストで止まる。
   - **読み込み:** 開くときは `O_NOFOLLOW|O_NONBLOCK` を使う。読むのは、確かめたサイズ+1 バイトの範囲だけである。SHA は必ず再計算する。
   - **TOCTOU:** 理屈は健全だが、テストがない（Medium 1）。
   - **handoff:** `role !== "prototype"` で絞り、quarantine を含まないことをテストしている。
     - 試作を `original`/`asset` の役割で紛れ込ませることはできない。役割ディレクトリの接頭辞、`.png` 拡張子、PNG の構造検査が掛かるためである。
   - **OS レベルの分離:** コード・`INTAKE_NOTES`・文書§9・tasks.json のいずれも、Phase 2e であり未実装と書いている。

5. **経路 A/B/C:**
   - **A:** 試作・描画条件・素材を持たない。codex_generated で画像があれば `IMAGE_SAVED` が必要である。
   - **B:** 試作が必須である。素材はプレースホルダーだけで、`image_outcome` は `not_applicable` である。
   - **C:** `ai_concept` に承認 ID が必要である（ただし Medium 3）。
   - **オーナーアップロード:** A だけが許される（ただし Medium 4）。
   - **試作の上限:** HTML 384 KiB + CSS 256 KiB で、1 MiB より小さい。`codex.ts` の `1024 * 1024` は変わっていない（テストで固定）。
   - **共通の形式:** 停止・欠落・SHA は3経路で同じ形である。語彙は design-image の `PocStopClass`・`IMAGE_OUTCOMES` と一致する（テストで固定）。

6. **範囲:**
   - 変更は9ファイルで、すべて allowed_scope 内にある。
   - `png.ts`・comp-impl・design-image・`codex.ts`・worker・pipeline・`.github`・`package.json` は、変更していない。
   - isolation テストが、import の許可リスト（zod・node の組み込みだけ）、書き込み API がないこと、自分の CLI からしか import されないことを固定している。

7. **テストの無効化:** skip・only・削除はない。品質やセキュリティの上限を緩める変更もない。
