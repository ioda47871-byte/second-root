# DEV-027 — Instagram reply send RPCs: one lock order (thread → draft → send)

Branch: `feature/dev-027-ig-send-lock-order` → develop. Migration: `20260929000000_sales_ig_send_lock_order.sql`.

## Bug

- `sales_ig_begin_send` locked draft → thread → send; `sales_ig_finish_send` / `sales_ig_resolve_unknown` locked send → draft.
- On a double tap, the second `begin_send` (holding the draft, waiting for the send) overlapped the first call's `finish_send` (holding the send, waiting for the draft). Postgres aborted one of them with 40P01. When that was `finish_send`, `lib/instagram/reply.ts` returned `record_failed`, and a reply Meta had delivered became `unknown`.
- CI evidence: `ig-send.test.ts` "[idempotency] never sends twice on a double tap or retry" failed intermittently with `expected ['in_flight','record_failed'] to contain "sent"` (PR #41, integration job 109266706032).

## Fresh Review (independent context), round 1: **FAIL (High 1)**

Critical 0 / High 1 / Medium 2 / Low 5. Round 1 reviewed the first fix, which only reordered `finish_send` / `resolve_unknown` to draft → send.

- **High**: `begin_send` (draft → thread) against `sales_ig_save_draft` (thread → drafts). This is the same kind of deadlock, hit when the drafting job saves a draft while the admin taps send. **Fixed**: `begin_send` now locks the thread first.
- **Medium**: `sales_ig_resolve_thread`'s ignore path (thread → drafts) against `begin_send`. **Fixed** by the same change.
- **Medium**: `finish_send`'s outbound message insert takes a key-share lock on the thread after the draft, while `save_draft` locks thread → draft. **Fixed**: `finish_send` takes the thread key-share lock first.
- Low, fixed:
  - The double-tap loop now only accepts `{sent, in_flight}` / `{sent, already_sent}`, so a `refused` victim fails it too.
  - The lock helper reports the RPC's own result if the RPC did not wait.
  - The locked re-read of the send also requires `draft_id = <the locked draft>`.
- Low, accepted: replay calls now also wait for the locks. They are short transactions with no data impact, and the migration header documents it.

## Fresh Review (independent context), round 2: **PASS**

Critical 0 / High 0 / Medium 3 / Low 6.

Reviewer's checks:
- (1) The migration matches 001100 apart from when locks are taken. That covers security definer, `search_path = ''`, `sales_assert_admin()`, error codes and their order, replay rules including the 2-minute stale → `unknown` path, `stale_draft`, `follow`, the outbound insert, return shapes, and revoke/grant.
- (2) These functions all follow thread → draft → send, or a subset: `begin_send`, `finish_send`, `resolve_unknown`, `save_draft`, `resolve_thread`, `match_thread`, `update_draft`, `snooze_draft`, and `purge`'s cascade.
- (3) The unlocked pre-reads are safe. Nothing ever updates `thread_id` / `draft_id`, and every value used afterwards comes from the locked re-read. A row deleted in between gives `not_found`.
- (4) The four lock tests are deterministic. Each waits on `pg_blocking_pids` before it takes the second lock.

Findings and what was done:
1. Medium: no test runs a real `begin_send` holding the thread against `finish_send`. **Accepted.** An RPC cannot be paused mid-transaction, so each function is tested against a hand-written holder in the canonical order instead. If `begin_send` went back to draft-before-thread, "begin_send behind the drafting job" would deadlock. If `finish_send` took the thread after the draft, "finish_send behind the drafting job" would deadlock.
2. Medium, pre-existing and outside this task: `sales_ig_ingest` can lock two threads in opposite orders in two concurrent webhook deliveries (thread ↔ thread). **Follow-up proposed**; the header's claim was narrowed to the send RPCs.
3. Medium, pre-existing and outside this task: `sales_ig_purge` (thread → messages) against ingest's unsend path (message → thread). **Follow-up proposed.**
4. Low: `begin_send` now takes the thread `for update` on replay and refusal paths too. **Accepted and documented.** Transactions are short, and this is not a deadlock.
5. Low: `finish_send` replays wait for the draft lock. **Accepted**, same reason.
6. Low: the 20× loop does not reliably reproduce the race. **Accepted.** The deterministic tests are the guard, and the loop is the requested smoke check (about 3 s).
7. Low: the lock helper did not await the RPC on error paths. **Fixed.**
8. Low: the pre-reads copied whole rows. **Fixed**: they now read only `thread_id` / `draft_id` into scalars.
9. Low: docs did not mention the lock order. **Fixed** in `docs/INSTAGRAM_MESSAGING.md` §6.
