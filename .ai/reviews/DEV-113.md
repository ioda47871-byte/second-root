## 判定: PASS（Critical 0 / High 0 / Medium 1 / Low 6）

台帳が成功や承認を作る経路は見つからなかった。strict が返る経路もない。phase1_compat の出力は、develop と1バイトも違わない。Medium は、版ラベルの出所が矛盾していても通る1件だけである。成功は作らないが、要件1の「版ラベルの整合検査」に穴がある。

### Medium

1. **manifest にない案件の版が、manifest 由来のラベルを名乗れる。**
   - **場所:** `lib/design-agent/intelligence/ledger.ts:235`
   - **原因:** `if (!m)` の分岐は、選定状態の有無しか見ていない。`version_label_source` の検査は、manifest にある案件の分岐（`else`）にしかない。
   - **再現:** 架空の台帳で、CP-950（不採用のみ・manifest にない）の版に `version_label_source: "manifest_approved_version"` を付けた。partial はそのまま通った。報告には `label_is_internal_identifier: false` と出る。つまり、manifest に存在しない承認版ラベルを持つかのように表示される。
   - **影響:** 成功は作らない（選定状態はすでに `LEDGER_CONTRADICTS_MANIFEST` で止まる）。ただし、ラベルの出所の自己申告が素通りする。読み手が「manifest が承認版として名指しした版」と誤読しうる。
   - **修正案:** `!m` のとき、`ledger_assigned` 以外の出所を持つ版は `VERSION_LABEL_MISMATCH` で停止する。停止コードのテストを1件追加する。

### Low

1. **manifest の2つのラベル欄の食い違いを検出しない。**
   - **場所:** `ledger.ts:243-245`
   - **再現:** manifest の同じ記録に `approved_version: RAIL_v2` と `owner_approved_version: RAIL_vX` があるとする。台帳が RAIL_v2 を選定していれば通る。RAIL_vX は、どの版にも現れない限り検査されない。
   - **補足:** 実データでは、両方の欄を持つ記録は0件だった。
   - **修正案:** 両方あるなら一致を要求し、食い違えば停止する。または、選定版が両方と一致することを要求する。

2. **ラベル欄の値が文字列でないとき、「ラベルなし」として扱われる。**
   - **場所:** `ledger.ts:245`
   - **原因:** `ManifestRecord` は `approved_version` の型を検査しない。数値などの非文字列は filter で落ちる。
   - **再現:** `approved_version: 2` のとき、選定版が `ledger_assigned` のラベルでも通った。manifest の承認版を台帳が自前のラベルで置き換えられる（fail-open）。
   - **補足:** 実データの値は、すべて文字列だった。
   - **修正案:** 欄が存在して空でない文字列でなければ、停止する。

3. **同じ SHA 値が2つの欄にあれば、別々の版を同じバイト列に紐付けられる。**
   - **場所:** `ledger.ts:228`
   - **原因:** 重複検査は欄名単位だけである。
   - **補足:** 実データでは、同じ値を持つ欄は0件だった。
   - **修正案:** 同じ案件の中で、SHA 値の重複も拒否する。

4. **ヘッダーの説明が、根拠の確認を実際より強く書いている。**
   - **場所:** `ledger.ts:26`
   - **内容:** 「chosen because a cited record says so」とある。しかし `evidence_ref` は形式（`design-library/...md`）しか検査していない。記録が実在するか、その欄を名指ししているかは見ていない。実際には、どの欄がどの版かを決めるのは台帳を書いた人の申告である。
     - 例：選定版と不採用版の anchor を入れ替えても通る。
   - **評価:** 名前から推測しないという要件は守られている（`first_*` の欄を選定版に、`approved_rejected_*` の欄を非選定版に結べることを確認した）。`verification` にも「検証済み」がないので、害は限定的である。計画書の「manifest の値と一致するかだけを見る」は正確だった。
   - **修正案:** コメントを「the ledger cites a record (format-checked only; not verified here)」程度に弱める。記録の実在・内容の照合は後続に回すと明記する。

5. **CLI の引数の誤りが、黙って phase1_compat になる。**
   - **場所:** `scripts/design-intelligence/brief.ts:26-35`
   - **再現:**
     - `--summary --mode`（値なし）と `--summary --mode=partial --ledger=/nope.json` は、どちらも exit 0 で compat の出力になった。
     - `--mode strict --mode partial` は、最初の値を使う。
   - **評価:** 成功や台帳報告を捏造はしない（`ledger` キーは出ない）。ただ、partial を意図した利用者が、検査されたと誤解しうる。
   - **補足:** usage 行は strict を他のモードと並べて列挙している。「always stops」の注記を添えるとより安全である。
   - **修正案:** 値のない `--mode`/`--ledger`、`=` 形式、未知の引数、重複フラグを、usage エラー（exit 2）にする。

6. **大文字小文字だけが違う版ラベル（`RAIL_v2` と `rail_v2`）が、別の版として通る。**
   - **場所:** `ledger.ts:209`
   - **評価:** 版の取り違えの温床になりうる。
   - **修正案:** 重複判定を大文字小文字を区別しない比較にする。

## 確認したこと（要件ごと）

1. **スキーマ:**
   - `selection_ledger_v1` は zod の `.strict()` で、全階層で余分なキーを拒否する。
     - JSON の `__proto__` キーも `LEDGER_SCHEMA_INVALID` になることを確認した。
   - 状態6種と quote_kind 6種は、許可リストで照合する。未知の値は `LEDGER_UNKNOWN_STATUS` / `LEDGER_QUOTE_KIND_MISMATCH` になる。
   - オーナー発言（`owner_decision_evidence`）と分析者分類（`analyst_classification`、`classified_by: analyst_not_owner`）は別の欄にある。混入はスキーマ違反になる。
   - 版ラベルの一致（両方の出所）、非選定版への manifest ラベル付与の拒否、manifest にラベルがあるときの `ledger_assigned` 置き換えの拒否は、いずれも動作する。

2. **3モード:**
   - **phase1_compat（develop と比較）:**
     - 実データ（efe269f）で、CLI の `--summary` と架空店舗の `--shop` の出力を比べた。既定でも `--mode phase1_compat` でも、develop 版（`git archive` で取り出した）と**バイト単位で一致**した。
     - `phase1-compat.golden.json` は、develop 版のコードを架空 fixture と `GOLDEN_SHOPS` で動かした出力と一致した。正しく pre-DEV-113 の出力を固定している。
   - **phase1_compat（台帳の扱い）:**
     - 台帳を渡すと `CORPUS_MODE_INVALID` になる（buildCorpus、loadResearchCorpus、CLI の `--ledger` のいずれでも）。
     - 研究ファイルの SHA 一覧は6件のまま、台帳を含まない。
   - **partial:**
     - 台帳必須（`LEDGER_MISSING`）で、記録のない成功案件を `unledgered_success_cases` に列挙する。
     - 実データで実行すると、正しく `LEDGER_MISSING: partial`（exit 2）で止まった。
   - **strict:**
     - `validateLedger` は、ループの後で strict なら必ず throw する。返る経路はない。
     - 変異実験で throw を無効にすると、3つのテスト（buildCorpus、validateLedger 直呼び、CLI）が失敗した。
     - コード、計画書（「安全な未実装状態であり、稼働する strict モードではない」）、CLI のコメント、tasks.json のいずれも、strict を稼働・完成とは書いていない。

3. **循環依存:**
   - `ledger.ts` は `zod` だけを import する。
   - 変異実験で `import type { ResearchCorpus } from "./corpus"` を足すと、許可リストと循環検査の2テストが失敗した（型だけの import も検出する）。
   - 循環検査は、許可リストの全ファイルから DFS で辿る。小さなグラフでは健全である。

4. **ResearchCorpus に生データを載せない:**
   - ResearchCorpus は、ラベルや `*_sha256` 欄を持たない。追加の欄を持つ manifest でも、compat の出力は golden と一致する（テストあり）。
   - 検証器は `byId`（passthrough で parse した生の記録）を展開した `fields` を参照する。
   - **プロトタイプ汚染:** manifest に JSON の `__proto__` で `approved_version` や SHA を潜ませても、`fields` から見えず、安全側で止まることを確認した。`manifest_field` は `_sha256` で終わる必要があるため、`Object.prototype` のプロパティにも届かない。
   - **実データの適合:** 実データの SHA 欄名と値は、すべて anchor の正規表現に適合した。

5. **台帳は成功・承認を作らない:**
   - 選定状態は、manifest の成功案件で1件ちょうど、かつ条件付きかどうかが manifest と一致する必要がある。
   - manifest にない案件の選定、0件・2件の選定、通常と条件付きの取り違えは、すべて停止する。
   - partial でも `successes` と `counts` は変わらない。
   - 選定版の `ledger_assigned` ラベルに引用がなければ、`LEDGER_ASSIGNED_LABEL_AS_APPROVAL` で停止する。
   - 報告は、引用本文も分析コードも出さない。
   - `verification` は `recorded_unverified` / `original_unavailable` の2つだけで、検証済みを表す値はない。

6. **範囲:**
   - 変更は11ファイルで、すべて allowed_scope 内にある。
   - `.github`・`package.json`・品質閾値・worker・pipeline・comp-impl・design-image・本番は、変更していない。
   - DEV-114 以降（research_set、署名、鍵管理）の先行実装はない。
   - テストデータは架空のものだけである。

7. **テストの無効化:** skip・only・削除はない。
