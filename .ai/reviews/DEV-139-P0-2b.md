## Findings

### M1 (Medium): labels are attached to facts without checking where they sit, so a swapped label passes as verified fact

- Where: `lib/sales/b-route/derive-copy.ts:73-82` (label → fact binding) and `:100-103` (the item is written with `claim_type: "fact"` and `owner_review_needed: false`).
- What happens: a free-standing label (営業時間, 定休日, 所在地 …) is bound to the single fact of the matching key that appears *anywhere* on the page. Nothing checks that the label sits next to that fact. The existing `checkArtifactCopy` cannot see adjacency either: it compares sets of texts. Before this PR, a person wrote each label binding by hand. Now the derivation makes the claim automatically and marks it as needing no owner review.
- Failure scenario (reproduced with a temporary probe test, real_shop_proposal lane): facts hours=`10:00〜19:00`, closed_days=`月曜`. The generated page shows `<dt>営業時間</dt><dd>月曜</dd><dt>定休日</dt><dd>10:00〜19:00</dd>`. `deriveBRouteCopy` succeeds and produces `[営業時間] 10:00〜19:00 fact` and `[定休日] 月曜 fact`, all with `owner_review_needed: false`. The page tells a prospect that the shop opens "月曜" and is closed "10:00〜19:00", yet the ledger records both lines as verified facts that need no review.
- Suggested fix: bind a label only when its text node is immediately followed by the fact text in the same block (dt/dd pair, or the same parent / next sibling). Record that position from the parse tree; `checkArtifactHtml` only returns a flat text list, so the position has to come from a structural walk in derive-copy. Otherwise STOP, or at least set `owner_review_needed: true` on every label-derived item. Add a regression test with the swapped dt/dd case above.
