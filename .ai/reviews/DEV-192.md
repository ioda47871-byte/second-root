## 1. 承認の連鎖 (誰が何で止めるか)

1. **コード (worker の checkout):** ジョブの schema は `shop_id` を `AUTORUN_SHOP_IDS` の enum、page・写真 ID 6つ・`brief_sha256` を固定値と完全一致で確かめる (自由文・path・URL・shell の欄は無い、strict)。
   `buildBicycleRunPrompt` が checkout の本文から実行プロンプトを組み直し、本文の SHA・バイト・各写真の SHA、組んだプロンプトの SHA・文字数を pin と照合する。1つでも違えば空を返し、worker は**予約の前**に `REFUSED_JOB_INVALID` (生成0回、テストあり)。
2. **root の switch (`/etc/sr-design-worker/image-autorun.json`、root 所有):** オーナーが実行の直前に1件だけ書く。承認 ID・**job_id**・shop・max_images 6・max_jobs 1・24時間以内の期限 (シートは2時間)。
3. **root の cycle.sh (変更は allowlist だけ):** 照合 → 使用済みのつぐ手 ID の拒否 → jail の Claude が停止かつ無効・`sr-designgen` のプロセス0・pgrep の fail closed → 承認 ID と job_id の**原子的な使用記録** → その job のバイトの SHA と今の boot に結んだ **20分の grant**。
4. **worker の hook:** 期限・24時間の上限・一回限りの台帳・STOPPED・switch・entry・grant を確かめてから予約 (原子的な mkdir)、生成は1回だけ、失敗すれば STOPPED で以後拒否 (再試行なし)。
5. **intake:** worker は **job の承認 ID だけ** を渡す (つぐ手と同じ)。生成器の名前・デモのラベル・両方のプロンプトの SHA・6枚の順・寸法・SHA を確かめる。

**実行の承認 ID をコードに書かなかった理由:** 承認 ID は使い捨てで、オーナーが実行の直前に決める (GO の指示)。コードに書くと、(a) 実行前に PR で公開され、(b) その ID が使えなくなったとき (20分超えなど) にコードの変更が要る。1回限りを確定させているのはコードの ID ではなく、root の entry (1つの job_id)・root の使用記録・20分の grant・worker の台帳である (つぐ手の auto-run のジョブと同じ)。`BICYCLE_RUN_APPROVAL_ID` は null のままで、intake を承認 ID なしで呼ぶと何も受け付けない (既定は閉じたまま)。
