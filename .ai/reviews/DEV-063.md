## Findings

1. **Medium — the tests do not enforce two of the script's main security rules.** The rules: the value never reaches the argv of *any* process, and every write in the bridge user's directory happens *as the bridge user*. (`tests/unit/design-bridge-bypass-setup.test.ts:41-50`, `:90-96`, `:621-629`)
   - **How the fake world checks:** it records argv and environment only for `runuser` and `curl`. It runs as one user, so the fake `runuser` is a plain `exec`. The static test only looks for `export … BYPASS_VALUE` and `curl … BYPASS_VALUE`.
   - **Mutations I ran, both of which pass all 69 tests:**
     - **M1:** in `WRITE_VALUE` (`setup-vercel-bypass.sh:180`), `printf "%s" "$v" >"$tmp"` → `/usr/bin/printf "%s" "$v" >"$tmp"`. The value is now in `/proc/<pid>/cmdline` of an external process, readable by any local user through `ps`. **69/69 pass.**
     - **M7:** at `:330`, `printf '%s' "$BYPASS_VALUE" | as_bridge bash -c "$WRITE_VALUE" …` → `… | bash -c "$WRITE_VALUE" …`, which drops `as_bridge`. Root then does `mktemp`, `ln` and `mv` in `~sr-designbridge/.config/second-root`, a directory the bridge user controls. That opens the symlink and hard-link attacks the script is built to avoid, and leaves a root-owned file that `bypass_file_ok` only catches afterwards. **69/69 pass.**
   - Acceptance criterion 2 and required test 1 ("argv/env に出ない") are only partly covered, because the guard is the code review, not the test.
   - **Suggestion (any of these would kill M1 and M7):**
     - Add a test that runs the script under `strace -f -qq -e trace=execve -s 4096` (skip it if `strace` is missing) and asserts that the value appears in no `execve` line.
     - Make the fake `runuser` export a marker such as `SR_FAKE_AS_BRIDGE=1`. Then wrap `mktemp`, `ln`, `mv`, `chmod` and `tail` in PATH shims that fail without that marker.
     - Add a static check that every line touching `$BYPASS_FILE`, `$BRIDGE_ENV` or `$CONF_DIR` for writing goes through `as_bridge`.
2. **Low — the probe's curl reads the bridge user's `~/.curlrc`.** (`setup-vercel-bypass.sh:195-201`)
   - `as_bridge` sets `HOME=$BRIDGE_HOME`, and curl loads `$HOME/.curlrc` unless `-q` / `--disable` is its **first** argument.
   - **Verified locally (curl 8.5.0):** a `.curlrc` with `trace-ascii = "<file>"` made the same `printf … | curl … -H @- <url>` write `x-vercel-protection-bypass: <value>` into that trace file. With `-q`, no trace file was written.
   - **Other directives that change the probe:**
     - `proxy`, `insecure` or `connect-to` would send the header to another endpoint.
     - `include` would prepend headers, so `json.loads` fails and the result is the false `PROTECTION_NOT_ON`.
     - A `header = Authorization: …` line would break the rule that the probe never sends the bridge token.
   - Only the bridge user (or root) can write that file, and the bridge user already owns the secret, so this is not an escalation. It is still a place where the value can leave the one file, and where a leftover rc file can make the check unreliable. The real bridge (Node fetch) ignores `.curlrc`, so the probe should too.
   - **Suggestion:** start both curl calls with `-q`.
3. **Low — `PROTECTION_NOT_ON` is reported for any answer to the no-header probe that is not Vercel's protection 401.** (`setup-vercel-bypass.sh:220-221`, `:367-371`)
   - **Failure scenario:** these answers all print "Vercel Authentication may be OFF" and exit 6 with `PROTECTION_NOT_ON`:
     - a Vercel 404 `DEPLOYMENT_NOT_FOUND` (alias moved);
     - a 502 or 504 edge error;
     - a 429 or an HTML challenge page (Attack Challenge Mode);
     - a body broken by `.curlrc` (finding 2).
   - That sends the person to check Deployment Protection when the real cause is elsewhere. It fails safe, because it stops, but the label is wrong. A real "past Vercel" answer has the app's JSON shape (`{"error":"design_bridge_disabled"|"unauthorized"|…}`).
   - **Suggestion:**
     - Report `PROTECTION_NOT_ON` only when the no-header probe gets an app-shaped JSON `error` string. Report `PROBE_FAILED` for everything else.
     - Add a test for a 404 HTML answer and a 502 answer to the no-header probe. Today only the "with" side has those cases (`test:452-458`).
4. **Low — a temporary file holding the value can be left behind, and later runs never remove it.** (`setup-vercel-bypass.sh:178-189`)
   - **The cleanup:** `WRITE_VALUE` relies on `trap 'rm -f "$tmp"' EXIT`.
   - **Checked locally:** bash runs EXIT traps on SIGTERM but **not on SIGHUP** (rc 129, trap not run). Closing the WSL terminal window sends SIGHUP to the foreground group, and so does SIGKILL or a WSL shutdown.
   - **Failure scenario:** a SIGHUP or SIGKILL that lands between `printf … >"$tmp"` (`:180`) and `ln` / `mv` (`:184` / `:186`) leaves `.design-bridge.vercel-bypass.XXXXXX`. That file holds the value, is 0600 and belongs to the bridge user.
   - The window is microseconds, and the file sits in the same private directory as the real one. But it is a second copy that `--replace` and the §8 revoke step (`shred -u` of the one file) do not cover.
   - **Suggestion:**
     - Add `trap … HUP INT TERM` next to the EXIT trap in `WRITE_VALUE`.
     - In step 3, have the bridge user remove (or at least report) stale `.design-bridge.vercel-bypass.*` files.
     - Mention them in §8's revoke row.

### Nits

- N1 — `read -r -s -t 600` (`:314-316`): when it times out, bash keeps the partial input in the variable, and the script then goes on with it. For example, a value pasted without Enter is accepted after 10 minutes. Treat rc > 128 as no input.
- N2 — `$(<file)` drops NUL bytes (`:162`, `:166`, `:197`). A hand-made bypass file with a NUL passes `CHECK_EXISTING` and the probe, but `vercel-bypass.ts:105-106` refuses it (`BRIDGE_BYPASS_UNSAFE`). The same applies to a leading BOM: JS `trim()` removes it, while bash rejects it. Only hand-made files are affected.
- N3 — `ln -T … 2>/dev/null || exit 5` (`:186`) reports every `ln` error (ENOSPC, EIO, …) as `BYPASS_FILE_PRESENT_RACE` ("appeared meanwhile"). That race path is also untested.
- N4 — `BYPASS_REJECTED` (`:222-223`) is given for any status with a `protection` key, including a 403 or 429. "Wrong or revoked value, run --replace" could then make someone replace a good value. Require `status == "401"` here as well.
- N5 — `BRIDGE_HOME` comes from `getent` (`:104`), but `cycle.sh:139` and the systemd unit hard-code `/home/sr-designbridge`. If the home ever differs, the script writes env lines that the cycle checks under a different path. Refuse a home other than `/home/sr-designbridge`, or note it in the docs.

## Checked and fine (reviewer)

- **Value handling:**
  - The value is read from `/dev/tty` with `-s` (fd 3/4; stdin only in the test world with `tty-is-stdin` under `SR_BYPASS_SETUP_TEST_ROOT`).
  - It is kept in an unexported variable of a shell restarted with `env -i`. So `SHELLOPTS`, `BASHOPTS`, `BASH_ENV` and exported functions cannot bring back xtrace or override `printf`. `sudo bash -x` traces only the pre-restart part, before the value exists.
  - It passes on through the `printf` builtin in a pipeline subshell (fork, no exec) to `runuser … env -i … bash -c "$WRITE_VALUE"` on stdin. The argv holds only code and paths.
  - On the bridge side, `valid`, `is_token` and `trim` are functions. `$(<…)` is bash's own read, and `printf >"$tmp"` is a builtin.
  - The probe header is built by the `printf` builtin and given to curl on stdin (`-H @-`). curl's stderr goes to `/dev/null`; there is no `-v`. Python (`-I`) prints only a code, never the body.
  - Here-strings (`<<<`) carry only `stat` output and the env text, never the value.
  - `unset BYPASS_VALUE` runs on every path, including `finish`.
- **Ctrl-C at the hidden prompt:** checked on a pty. The INT trap exits 40, and the terminal's `echo` is restored afterwards.
- **Root and bridge-user paths:**
  - Root only `stat`s and tests paths under `~sr-designbridge`.
  - Root reads the env file through `as_bridge cat`. It reads the token only in the bridge user's shell (`is_token`).
  - The bypass file is written in that shell: `mktemp` (0600, O_EXCL) → `chmod 600` → `ln -T` for a new file (fails if one appeared) or `mv -fT` for `--replace` (an atomic rename that replaces even a planted symlink, without following it). Afterwards root checks it with `bypass_file_ok`.
  - The env lines are appended in the bridge user's shell.
  - A link planted by the bridge user can therefore only make the bridge user write its own files.
  - Root writes in one place only: `/etc/second-root/design-cycle.conf`, after `-f`, `! -L`, owner root, no g/o write and `trusted_path`.

  - The classes match the Vercel 401 shape in `design-bridge-access.md` §1 (`{"protection":…}`) and the app's `{"error":"design_bridge_disabled"}` (503) and `{"error":"unauthorized"}` (401). Vercel's own `error` object never matches the app's tuple.
  - `PROTECTION_NOT_ON` stops before the header is ever sent.

  - The conf is changed only when it is present and has no switch line. It is never created, and `--no-dry-run` leaves it alone.
  - A second run changes nothing (same inode and mtime, same env).
  - The test hook is refused in `/root/sr-capture-admin`, and the script refuses to run there as non-root (checked by the unshare test).

  - The `protectionBypass` keys are collected before anything is printed, and every line is redacted of them and of `VERCEL_TOKEN`.
