## push しない復旧の設計

- **期限を過ぎた deployment は off になる。**
  - 期限は request ごとに判定される: `aiDesignEnabled(env = process.env, now = Date.now())` の default 引数は呼び出しのたびに評価される。呼び出し側は route・Server Action・動的 page・ingest で、DEV-064 で確認済み。
  - `on` は期限を先に書く。だから flag が `true` の deployment は、必ず期限を持つ。
  - 復旧 session が書けなかった（FAILED・credential が無い）・起きなかった・skip した場合でも、期限を過ぎた時点で今の deployment は off。
- **後の deployment が `true` を有効なまま運ぶ経路:**
  - 復旧が `OFF_WRITTEN` なら record は `false` なので、後の deployment は `false`。
  - 復旧が失敗して record が `true` のまま残っても、期限の record も過去の値のまま残る。後の deployment（push・Redeploy・merge）は「`true` + 過去の期限」を運ぶので、app は off。
  - `OFF_SKIPPED_OTHER_WINDOW` は、期限が別の有効な時刻のときだけ起きる。`on` は flag が `false` でない間は拒否するので、script だけでは別の window はできない。人が画面で期限を延ばした場合はその人の判断で、期限で閉じる。
  - 有効な `true` を運ぶ経路は、人が画面で期限を消す（`none`）か、遠い未来に書き換える場合だけ。これは DEV-064 で doc §5 に記載済みで、範囲外。
- **`verify --expect off` との関係:**
  - 復旧の後、今の deployment は `built BEFORE`。`verify` は新しい push の後でしか通らない。
  - doc §4 の後の注記と §5 の新しい行は、この点で code と一致する。

## Findings

1. **Medium — 承認条件の「1 回だけ」「one-shot」を担う予行の prompt の文面が、doc に無い。**（`docs/operations/design-flag-window.md` §2 の予行の項・§6）

   - **失敗シナリオ:**
     - 予行の prompt を作る Claude が §4 を写して、write-check にも再実行の規則を付ける。
     - 1 回目の PATCH は成功した。ところが読み戻し（`read()`）で通信が切れて `FAILED` になる。
     - 新しい session は規則どおり write-check を再実行し、2 回目・3 回目の PATCH を送る。
   - 書く値は常に `"false"` なので、安全性は崩れない。ただ「1 回だけ」という人の承認条件は破れる。

     - write-check は 1 回だけ実行する。`FAILED`・`WRITE_DENIED` でも再実行しない。
     - `status` が `flag=false` でなければ write-check を実行しない。
     - 失敗したら出力を報告して止まる（権限・設定を変えない）。push・PR・Production・Authentication・DB・WSL には触れない。
   - あわせて、scheduled task は `run_once_at` の one-shot にし、発火後は `run_once_fired` で無効になったことを確かめる。これも手順に入れる。

  - push・PR・Production・Authentication・DB・WSL・timer に触れない。

  - 失敗しても権限を広げずに止まる。
  - 再実行は `off`（`"false"` だけを書く。冪等）に限られる。
