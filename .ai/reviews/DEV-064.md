## 確かめて問題なかったこと（reviewer）

- **Production への書き込み:**
  - request は guard を通る。PATCH の id は `read()` が返す `isOurs`（target `["preview"]`・gitBranch `develop`・plain）の record のものだけ。
  - POST は key・plain・`["preview"]`・`develop`・形を guard が強制する。
  - deployment の作成・promote・env の削除・target の変更をする request は無い。
  - production branch が `main` でないとき、および strays があるときは、最初の書き込みより前に止まる（test あり）。
- **allowlist の URL:**
  - GET は完全一致の文字列比較。PATCH の末尾は `^[A-Za-z0-9]{8,64}$` なので、`?`・`#`・`/`・`..`・`%2e` はすべて落ちる。
  - `redirect: "error"`。base は固定の `https://api.vercel.com`。
  - body の key 判定は、送る文字列と同じものを parse している（重複 key も Vercel 側と同じ「後勝ち」）。
- **期限なしで flag が `true` になる経路:**
  - `on` は期限を書いて読み戻し、一致を確かめてから flag を PATCH する。期限の書き込みが 403 なら flag は `false` のまま（test あり）。
  - `off` は期限を残すが、flag が `false` なので無害。
  - 既存の期限（過去の値）がある場合も、`on` は先にそれを上書きする。
- **日付の判定:**
  - `\d` は u flag なしで ASCII だけ。JS の `$` は末尾の改行を許さない。
  - round-trip で `2026-02-31`（V8 は 3/3 に繰り上げる）や `T24:00:00`（翌日 00:00 に繰り上げる）を NaN にする。`23:59:60` は Date.parse が NaN。いずれも node で確認した。
  - `now < until` なので境界の時刻ちょうどで無効になる。NaN との比較は false なので fail closed。
- **request ごとの評価:** `aiDesignEnabled` の呼び出し側は 7 か所。
  - `app/api/internal/sales-design/jobs/route.ts`（POST の中で `authorizeBridge(…, process.env)`）
  - `lib/sales/demo-data.ts`（`app/demo/[publicToken]/page.tsx` が `await connection()` の後に呼ぶ）
  - `app/admin/preview/[prospectId]/page.tsx`・`app/admin/sales/page.tsx`（`requireAdminPage()` の後で動的）
  - `app/admin/sales/_actions/send.ts`（Server Action）
  - `lib/sales/ingest.ts`、`lib/admin/history.ts`・`lib/admin/today.ts`（default 引数は呼び出し時に評価される）
  - module の top-level での評価も `"use cache"` も無い。`process.env[...]` の動的参照なので build 時の inline も無い。
- **出力への値の漏れ:**
  - `call()` の error は method・pathname・status だけで、body を引用しない。
  - strays の message は key・target・gitBranch・type だけ（`envs` は先に 2 つの key に絞られる）。
  - `VERCEL_TOKEN` は長さの判定だけ。
  - mock の `SUPABASE_SERVICE_ROLE_KEY` が出力に出ないことを test が確かめている。
- **`verify`:**
  - `off` は flag 自身が `false` であることを要求する（期限切れだけでは off としない）。
  - `on` は期限が設定されていることを要求する。
  - READY・commit 一致・env の変更後の作成を確かめる。
- **復旧の文面:** `ALREADY_OFF` で verify が `VERIFIED_OFF` なら何も push しない。冪等で、secret を表示しない指示もある。develop は保護されておらず（`protected: false`）、記録の commit を直接 push する既存の運用と合っている。
- **doc と code:** doc の内容はすべて実装と一致している。§1 の request 一覧、`--until` の 30 分〜4 時間、最終行の形式、`status` の `passed` 表示、strays の条件。
