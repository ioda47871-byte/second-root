# DEV-029 — Photo art direction (local preview only)

Branch `feature/dev-029-photo-art-direction`, cut from DEV-028's head (192fd1a). Decisions fixed by people on 2026-10-02 are in `.ai/tasks.json` (DEV-029).

## Stage 1 — schema / types / intake (2026-10-02, self-review)

**Added**
- `lib/design-agent/assets/types.ts`: branded `PublicAssetId` and `ReferenceImagePath`. A plain string, or one kind, is not accepted where the other is expected (pinned with `@ts-expect-error` in the tests, checked by `tsc`).
- `lib/design-agent/assets/manifest.ts`: `AssetManifest` (version 1, ≤ 3 assets, unique ids and pixel hashes, file named after the id). Sources `approved_real` (consent: id, by, at, scopes `local_preview` / `public_demo`) and `generated_concept` (`human_upload` only). `people` is the literal `"none"`. `PUBLIC_DEMO_ASSETS_ENABLED = false`: no photo on the public demo, whatever the consent says (MVP_SPEC §7 unchanged).
- `lib/design-agent/assets/analysis.ts`: `PhotoAnalysis`, enums and numbers only (no free text from a photo can reach the page).
- `lib/design-agent/assets/direction.ts`: `ImageDirection` (layouts none / split_hero / framed_hero / type_hero_feature_band; feature slots about / visit only, no menu slot) and `checkImageDirection`: ids exist and are analysed, no asset twice, every asset used or rejected, layout ↔ photos, one photo per slot, consent for the scope, no people, no near-duplicate pair. Any failure means no photos (the DEV-028 page).
- `lib/design-agent/assets/intake.ts` + `scripts/sales-design-assets/assets.ts` (`npm run -s sales:design-assets -- add | list`): a person adds a photo to a job. Checks: job id, store location (absolute, outside the repository, temp and reference places, also after resolving links, before anything is written), source location (refuses the capture spool, the capture user's home, worker / Codex temp roots, the preview output), no symlink (lstat, then `O_NOFOLLOW` and the same inode), size, extension and magic bytes (PNG / JPEG / WebP; ISO-BMFF `ftyp` such as HEIC refused), "no people" confirmed, consent for approved photos. The photo is decoded and drawn again by Chromium into a PNG (≤ 2400 px, ≥ 320 px short side): nothing of the original file survives. Files 0600 in a 0700 job directory, written by temp + rename.

**Self-review fixes before commit:** a symlink swapped in after the lstat (now `O_NOFOLLOW` + inode check); a store root that is a link into the repository (now resolved and checked before anything is written); a broken manifest gave a generic error (now `MANIFEST_INVALID`).

**Tests** (`tests/unit/design-agent/assets.test.ts`, 20): photos drawn by the test (gradients and shapes; portrait / landscape / square, quiet / busy; PNG / JPEG / WebP), with an EXIF APP1 segment and a PNG tEXt chunk carrying a marker. The stored PNG has only IHDR / IDAT / IEND and no marker. Also: HEIC refused (by extension and by content), signature mismatch, symlink, empty, small, scaled down, 3-photo limit, duplicate, people not confirmed, consent missing or malformed, scopes kept apart, reference locations refused, store location checks, broken manifest. CLI checked by hand (add, refusals, list). Full unit suite 623 passed.

**Known limits:** two intakes of the same job at the same moment could lose one manifest entry (a person runs one command at a time; no lock yet). If writing the manifest fails after the PNG is written, the PNG stays as an orphan (not listed, so never used). The asset store is not yet in `workerProtectedPaths` (Codex sees no asset until stage 3; it will get copies only, like references).

## Stage 2 — renderer (2026-10-02, self-review)

**Added / changed**
- `lib/design-agent/assets/resolve.ts`: `resolvePhotos()` turns a direction, the manifest and the analyses into `RenderPhotos`, or null. Null for: no direction, no manifest, no or invalid analyses, any `checkImageDirection` problem (bad or unknown id, undecided asset, duplicates, consent, people, near duplicates), layout `none`, a feature slot whose section the page does not draw (`about` needs a description, `visit` at least one visit row), an id that does not resolve. Ids leave it as `PublicAssetId` only.
- `lib/design-agent/assets/serve.ts` + `app/design-preview/[runId]/asset/[assetId]/route.ts`: the only way a photo reaches a page. The URL carries a run id and an asset id, never a path. Run id → the run's `assets.json` (`{ jobId }`, nothing else) → store root (checked again: outside the repository, temp and reference places) → manifest → `toPublicAssetId` → listed → `assetUsableIn(local_preview)` → path from the manifest's own `file` → lstat (no link, plain file, size), `O_NOFOLLOW` open with the same inode, PNG signature, sha256 equal to the manifest. Anything else is a 404 (no-store). `image/png`, `Cache-Control: no-store`, `nosniff`; the existing `/design-preview/:path*` headers (noindex, no-referrer, private) apply. 404 where `SR_DESIGN_PREVIEW_ROOT` is unset (Vercel, the e2e server). No route reads a run's other files, and none reads reference screenshots.
- `lib/design-agent/preview.ts`: `loadPreviewRun` also returns `photos` for a valid candidate profile (`<candidate>.images.json`, `photo-analyses.json`, `assets.json`); inside a try, so a broken input means no photos, never a broken page. The before template never gets photos.
- `ProfileRenderer` (`photos` prop, optional) and `profile.module.css`:
  - `split_hero`: a two-column grid (photo 5fr, type hero 7fr) from 720 px; photo above the type hero on phones.
  - `framed_hero`: an outlined frame in a hero row of its own (phones: between the motif row and the name) or a column of its own beside the name (desktop); folio and dek span both columns.
  - `type_hero_feature_band`: the DEV-028 hero; photo bands in the About and / or Visit section's content column.
  - Hero + features combine for 2–3 photos. Photos sit in grid cells of their own; no page text is drawn on them. `fit`, desktop / mobile focal (`object-position`), desktop / mobile aspect (`aspect-ratio`) and treatment (natural / warm / mono filters on the image only) applied. `alt=""`.
  - A generated image always carries `イメージ画像` (solid ground, palette text on background, ≥ 4.5:1 by the profile check), drawn by the renderer; no input switches it off. Approved photos carry no label.
  - No photos: the markup is byte-for-byte what DEV-028 drew (tested).

**Found and fixed by the new browser test:** on desktop the split photo had `width: 100%` plus a left margin and reached 56 px into the type hero's column (no text was hit, so only a new "split photo never overlaps the type hero" check caught it; it fails on the old CSS).

**Tests**

Each photo: loaded, no overlap with name, folio, dek, motifs, headings, lead, visit, menu, notice, footer or another photo; label iff generated, visible, inside the photo; `object-fit` and `object-position` as directed per device; aspect within 0.02; hero photos inside the hero, split photo not over the type hero; bands inside their section; no sideways scroll. ## Stage 3 — Codex photo analysis / image direction (2026-10-02, self-review)

Not wired into the worker (stage 4). No run-directory files are written in production yet.

**Hiding the asset store from Codex**
- `lib/design-agent/assets/store-root.ts`: `assetStoreRoot(env)` alone, with no imports, shared by intake (re-exported), the preview route and `protected-paths.ts` (no import cycle).
- `workerProtectedPaths()` now lists `assetStoreRoot(env)`, default or `SR_DESIGN_ASSETS_ROOT`. The sandbox hides it (inside the home: the home is hidden; elsewhere: hidden on its own) and its probe checks it before every call. Real-bubblewrap test: a custom store in /var/lib and the default store in the home are both invisible to a Codex that looks for them, while the attached copies are readable. With the store left out of the list, the same test sees the custom store (checked by hand).

**How a photo reaches Codex**
- `lib/design-agent/assets/read.ts` `readVerifiedAsset()` (now also used by the preview route): manifest record allowed for `local_preview`, path from the manifest's own file name, job dir and file not links, `O_NOFOLLOW` open with the same inode, PNG with the manifest's width / height / byte count and sha256.
- `photo-codex.ts` `loadPhotoInputs()` reads every photo of the manifest that way (any failure: `PHOTO_INPUT_REJECTED`, no photos).
- `runCodexJson({ imageBytes })` → `stageInputBytes()` writes the checked bytes as `<workDir>/inputs/photo-N.png`; `--image=` names only those copies. The store path is never in the prompt, the arguments or the schema.

**Calls**
- `photo-prompts.ts` (new; `prompts.ts` untouched): analysis and direction prompts. They carry the attachment order ↔ asset id, pixel sizes, the category, which sections exist, the analyses and the profile without its rationale. No path, job id, consent record, hash or shop text. Text inside a photo is declared material, never an instruction; no file reading; JSON only.
- `analyzePhotos()`: 0 photos → no call. Else the answer must parse (`PhotoAnalysesSchema`, strict) and then match the attached photos: each exactly once, no unknown id, no duplicate, `nearDuplicateOf` another attached photo or null (not itself), orientation consistent with the pixel size (near-square shapes may be either). Otherwise `PHOTO_ANALYSIS_INVALID`.
- `directImages()`: 0 photos → `NO_IMAGES` without a call. Else the same copies are attached; the answer must pass `checkImageDirection(..., "local_preview")` and use only sections the page has. Otherwise `IMAGE_DIRECTION_INVALID`. No retry (stage 4).
- Codex failures come back as their fixed `CodexError` code; nothing new is logged; session cleanup, token-leak rejection and secret redaction are runCodexJson's, unchanged.

**Tests** (`photo-codex.test.ts`, 14): inputs (1/2/3, exact bytes, refusal for a changed file, a link, public-only consent, another job), analysis (1/2/3 with the prompt's id lines; no call for 0; duplicate / unknown / missing id, bad or self near-duplicate, wrong orientation, caption / OCR fields, a fourth photo), direction (valid, people, near-duplicate pair, missing section, menu slot, caption / alt fields, gallery, undecided photo; no call for 0; a failure leaves resolvePhotos with no photos), no free-text string anywhere in either JSON schema, prompts free of the store path, job id, consent id, approver, creator, hashes and file names, the full path through runCodexJson with the fake CLI (copies in `inputs/` with the assets' sha256, no API-key variables, session log removed), the protected-paths list, the real-bubblewrap store check, and snapshots of the DEV-028 brief / review prompts and their schemas (`prompts.ts`, `review.ts`, `profile.ts` and the pipeline are unchanged). Full unit suite 655 passed.
