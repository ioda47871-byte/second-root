# DEV-034 review

## Cause (Staging second PoC, 2026-10-15)

- The demo was captured and the brief and reviews passed the strict schema. Candidates 0 / 1 / 2 scored 15 → 13 → 13 (/25); the last review asked for a renderer change (responsive sizing of the Japanese shop name, a meaningful line break), so the job was blocked: `RENDERER_CHANGE_NEEDED`, no `design_profile`.
- Renderer: an unspaced Japanese name is one phrase. On phones the hero sized it to wrap (170cqi) with `overflow-wrap: anywhere`, so the browser broke it inside a word (ベー / カリー). No profile could fix that, which is why the reviewer kept marking mobile high and finally asked for a renderer change.
- Revision search: each revision was made from the current candidate's review. After 15 → 13, revision 2 came from the 13-point candidate-1.
- The reviewer had no history: each round was scored without knowing what the earlier rounds scored or what made them worse.

## Change

- Renderer (components/demo/profile):
  - An unspaced name is set from pieces that are never split: kanji with the kana after it, a katakana run, a Latin word, whatever follows a middle dot, a bracketed part. A long-vowel mark, small kana, ヶ and closing brackets stay with the character before them.
  - Phones: one line when it stays large; otherwise 2–3 balanced lines that break only between pieces. Each line is sized to the hero's width with letter-spacing counted per character, from an upper bound of the width (Latin as wide capitals, the widest face), so no face, case or tracking overflows. Desktop: one line, sized the same way, with no floor that could overflow.
  - Spaced names are unchanged. No shop name is hard-coded.
- Revision search (pipeline.ts, photo-pipeline.ts): the next revision always starts from the best-scored candidate so far. When a revision scores lower, the best one is reviewed again with its own screenshots, and that review's revised profile is used (`REVISION_FROM_BEST_n`). Tie: the later candidate leads, the same rule as the final choice. With less than 20 minutes left in the run, or when the run's clock runs out during that second look, the search stops and the best candidate is final (`REVISION_FROM_BEST_NO_TIME`); the job is not failed.
- Reviewer context (prompts.ts, photo-prompts.ts): from the second round on, the prompt lists the earlier rounds (candidate, verdict, the five scores, the total, problem area and severity) and the best so far, and says not to repeat a change that made a round score lower. Codex's own words and image content are not passed. The first round's prompt is byte-identical (DEV-028 snapshot).
- Unchanged: the score calculation, accept / revise, the revision limit (2), the review threshold, `needs_renderer_change` → BLOCKED, the final choice. Nothing is forced to accept.

## CI: where the diagnose test hangs (found with the bounded steps)

- 1381f09 `unit`: `li_auth_platform C did not finish in 60 s (lines so far: C headless+no-interception HTTP_OTHER CHALLENGE_PRESENT)`.
- Where: in mode C (no interception), the `request` handler's `refuse()` closes the page (`void p.close()`) while its navigation is in flight. `runMode` then awaits `page.close()` on the wall branch, and `runDiagnose` awaits `context.close()`. On a loaded runner, one of those closes never settles.
- This is in `lib/design-agent/browser/diagnose.ts` (DEV-033, the capture helper's diagnose tool), which this task may not change. It affects only the human-run diagnose command, not capture.
- Proposed patch (for a separate, approved change):
  - in `refuse()`, record the stop and let the run close the page once `goto` has returned, rather than closing it inside the request handler;
  - bound `page.close()` / `context.close()` with a short timeout, then kill the browser.
