## Findings

1. **Medium — a Playwright disconnect is weaker evidence than the old "process closed" signal. When it wins the race, no kill is tried and nothing is reported.** (`lib/design-agent/browser/diagnose.ts:300-310`)
   - **The two signals differ (Playwright 1.62.1):**
     - Client `browser.close()` resolves only after the server's `browserProcess.close()`. That waits for `waitForCleanup`, which resolves on the launched process's Node `close` event: the process has exited **and** all its stdio pipes are closed (`playwright-core/lib/coreBundle.js` ~8945-8953, 52365-52370).
     - `disconnected` fires as soon as the CDP pipe reaches EOF (the CR connection is `Disconnected`, then the server Browser runs `_didClose`, then the client `_didClose`).
     - Chromium shuts the DevTools pipe down before it destroys the profile, so in a graceful shutdown the disconnect normally comes *before* the cookie and LevelDB flush and the process exit.
   - **What the PR does with that:** `Promise.race([..., gone])` (`:308`) returns `"killed"` as soon as the pipe is gone. `killProfileBrowser` is never reached, so nothing checks whether the process is still alive.
   - **Failure scenario:**
     - The CI hang may be a browser whose pipe closed but which never "closes" for Node. For example, it is slow to exit on a slow disk, or a descendant still holds stdout/stderr, so `close` never fires and `browser.close()` never settles.
     - The PR turns that into a green `"killed"`. Before, it was a `BROWSER_STUCK`.
     - In production, the next mode then calls `launchPersistent` on the same profile while the old Chromium may still hold `SingletonLock` and be writing to the profile. Expect a `BROWSER_ERROR` or a handoff to the dying instance, not a clean run.
     - The CI flake would also disappear without anyone learning which of the two causes it was (see DEV-060 finding 1).
   - **Suggestion:**
     - When `gone` wins but `browser.close()` has not settled, still run `killProfileBrowser(profileDir)`. This is cheap and safe, since the run holds `browser.lock` and only the exact browser main process matches. Or require that it finds 0 matches before reporting the browser as ended.
     - Also keep the three outcomes apart internally (graceful close / disconnect only / killed), at least in a test hook or a debug log, so the CI flake can be explained.
2. **Low — the JSDoc and the docs say Playwright never force-kills. It does, after 30 s.** (`diagnose.ts:284-285`; `docs/operations/design-browser-wsl.md:138` 「Playwright の close は process の終了を待つだけで強制終了はしない」)
   - Server `Browser._close()` calls `browserProcess.close()`, which is `closeOrKill(DEFAULT_PLAYWRIGHT_TIMEOUT = 30 000)`. On timeout it calls `kill()`, which is `process.kill(-pid, "SIGKILL")` on the browser's **process group** (coreBundle.js ~4264, 39571-39589, 8979-8996).
   - For a persistent context, `context.close()` reaches that path through `doClose()` and then `"close-browser"` (~38492-38495, 51601-51603).
   - So in production a stuck Chromium is SIGKILLed by Playwright about 30 s after the close began. This PR's kill (about 10 s context + 10 s browser = 20 s) comes first. That is a valid reason for the PR, but the stated rationale is wrong.
   - DEV-060 finding 3 was wrong on this point too.
   - **Suggestion:** reword both places to "Playwright kills it only after 30 s; diagnose ends it sooner".
3. **Low — test coverage of the kill path is thin.** (`tests/unit/design-agent/browser.test.ts:998-1026`)
   - **What the new tests do catch:** the three new tests do fail on develop's `diagnose.ts` (checked: `stuck` ≠ `killed` ×2, and `killProfileBrowser is not a function`). The spawn test's `${profile}-other` sibling does guard against prefix matching.
   - **Gaps:**
     - The test titled "killProfileBrowser matches … exactly, never by prefix" (`:1024`) only checks that a non-existent directory gives 0. It does not test prefix matching.
     - Nothing covers the uid filter, the `path.resolve` variant, or a real Chromium.
   - **Suggestion:** add a test with a real persistent Chromium. `SIGSTOP` its browser process (found by the exact argument), patch `context.close` to hang, and expect `"killed"`, `isConnected() === false`, and no process left with the profile argument.
4. **Low — a SIGKILL can lose the latest cookie and session writes for the signed-in profile.**
   - SQLite (the Cookies DB) is crash-safe, so the file is not corrupted. But changes that Chromium has not flushed yet are lost. That includes cookies Instagram rotated in the last ~30 s, which could make a later run look signed out.
   - The leftover `SingletonLock` / `SingletonSocket` / `SingletonCookie` stay behind (seen locally). Chromium takes a stale lock over once its pid is dead. On a rare pid reuse, the next launch may see the profile as in use.
   - The same risk already exists with Playwright's own 30 s SIGKILL (finding 2), and with no kill at all the next mode cannot use the profile anyway. So this is acceptable. It is worth a line in the docs ("after BROWSER_STUCK/kill, a re-login may be needed").
5. **Low — diagnosability (follows DEV-060 finding 1).**
   - The CI root cause (Chromium 1234) is still not shown, and the PR records no timing or path for how the browser ended.
   - **If the flake comes back as `BROWSER_STUCK`:** the kill matched nothing. Either `profileDir` did not match the argument, or the browser main process had already exited while `close` was still pending, which is finding 1's case.
   - **Suggestion:** a one-line `say`-free debug hook (or test-only callback) would answer this on the next CI run.

## Checked and fine (reviewer)

- **Kill scope, checked against a real Chromium 1194 persistent context:** only the **browser main process** has `--user-data-dir=<dir>` as a separate argument.
  - Its children (zygote ×2, gpu, utility network/storage, renderers) rewrite their title into one NUL-free string, so they never match exactly.
  - Killing only the main process ended all 11 Chromium processes within 1.5 s. Playwright reported `disconnected` 22 ms after the kill.
  - So the JSDoc's "its renderers end with it" holds, and the match cannot hit a different profile (exact `Set.has`, no prefix).
- **Concurrent users of the profile:**
  - `runLogin`, `runSignedInCapture` (also used by the capture helper, which additionally takes `capture-helper.lock`) and `runDiagnose` all take `browser.lock` in the same state directory (`~/.local/state/sr-capture`) before launching. The diagnose CLI's state directory is documented as shared with the helper.
  - `closeBrowser` runs before `lock.release()`, and the modes run sequentially. So no other legitimate Chromium can be on the profile at kill time.
  - Chromium's ProcessSingleton also allows only one browser process per profile.
- **Path matching:** Playwright passes an absolute `userDataDir` as is and resolves a relative one (`coreBundle.js` ~62902). `wanted` covers both forms.
- **uid check:** it reads the real uid (first `Uid:` field) and compares it with `process.getuid()`.
  - Production cannot run as root: `checkProfileLocation` refuses with `WRONG_USER` unless the user is the dedicated browser user.
  - As root (tests, containers) the uid check limits the kill to root's own exact-match processes.
  - The pid-reuse window between reading `/proc/<pid>` and `kill` is microseconds, and a reused pid would also need the exact argument.
- **Non-Linux:** `readdir("/proc")` fails, so 0 processes match and the result is `"stuck"` (the old behaviour). The browser was never meant for Windows or macOS here.
- **`context.browser()` for a persistent context** is non-null in 1.62.1 (the client `_didCreateContext` sets `_browser`; verified locally: `browser() true`). So the kill path is reachable in production.
- **`browser.close().catch(() => undefined)`:** `settlesWithin` already counted a rejection as settled, so the change is neutral. `gone` resolves at once when the browser is already disconnected.
- **Production bounds:** at most 10 s (context) + 10 s (browser) + 3 s (wait after the kill) per mode, which adds 3 s to the worst case only when the kill fires.
- **Test guarantees:** no assertion removed or loosened. The DEV-060 tests were adapted to the new fake with the same expectations.
- **Scope:** `diagnose.ts`, its test and one docs line. No Protected Scope change, and no Staging or Production change.
