## Findings

1. **Medium — cwd matters for a second, bigger reason that the PR does not name: tsx finds `tsconfig.json` (and its `@/*` paths) from the current directory, and the bridge's import chain needs them.** (`scripts/sales-design-bridge/run.sh:44-46`, `docs/operations/design-bridge.md:116`, `tests/unit/design-agent/bridge.test.ts:668-691`)
   - **Where the alias is used:** `bridge.ts` imports only relative paths. But it pulls in `lib/sales/design-bridge-schema.ts:2-3` and `lib/sales/design.ts:1-2`. Those use **value** imports from `@/lib/design-agent/profile` and `@/lib/design-agent/review-summary`, and these have been there since DEV-030.
   - **How tsx looks for the config:** tsx 4.23.15 calls `getTsconfig(process.cwd())`. That search walks up from the current directory.
   - **What I ran:** the real `tsx bridge.ts --deliver-only` on develop's code, with no API URL set:
     - From `/` and from `/tmp`, it fails with `Error: Cannot find module '@/lib/design-agent/profile'` (`MODULE_NOT_FOUND`).
     - From the checkout, it gives `stopped: BRIDGE_NOT_CONFIGURED`.
   - **What that means:**
     - On develop, starting the bridge from anywhere outside the checkout breaks it, even when esbuild can spawn. That includes a `/mnt/c/...` path once its EACCES is out of the way.
     - **cycle.sh is affected.** It does `cd /` (`scripts/sales-design-worker/cycle.sh:54`), then calls the bridge through `runuser -u` (`:158`, `:402`), which does not change directory. So on develop, every bridge pass of the cycle would fail with `MODULE_NOT_FOUND`.
     - `design-worker-cycle.test.ts` replaces the bridge's `run.sh` with a stub, so it cannot catch this. The cycle is not installed yet (HUMAN-010), so this has not hit production.
     - The systemd unit was never affected, because it sets `WorkingDirectory=` to the checkout.
   - **The PR fixes all of these.** The open issue is the record and the guard:
     - The run.sh comment and the docs note explain the change only by the esbuild EACCES.
     - The new test checks `$PWD` with a stubbed tsx, so it never loads the real module graph.
     - A later change that moves tsx or esbuild elsewhere, or adds a `cd` back in the wrong place, would only be caught if it happens to change `$PWD`.
   - **Suggestion:**
     - Say "tsx reads tsconfig.json (the `@/` paths) and spawns esbuild from the current directory" in both the comment and the docs.
     - Note in the cycle runbook and progress that this PR also unblocks the cycle's bridge passes.
     - Add a cheap real-module test: run the real `run.sh` (with `id` stubbed) from `/` or a temp directory, with no `SR_DESIGN_BRIDGE_API_URL`, and expect `stopped: BRIDGE_NOT_CONFIGURED` and exit 3. It needs no network and takes about 1 s.
2. **Low — relative paths in the allowlisted environment now resolve against the checkout instead of the start directory.** (`run.sh:47-51`; `bridge.ts:51`, `:73-74`)
   - These variables are affected: `XDG_STATE_HOME`, `SR_DESIGN_BRIDGE_SPOOL` and `SR_DESIGN_BRIDGE_TOKEN_FILE`. `SR_DESIGN_BRIDGE_VERCEL_BYPASS_FILE` is not, because it must already be absolute (`vercel-bypass.ts:84`).
   - Before and after the change, `run.sh`'s lock and `bridge.ts` agree with each other, so locking stays consistent.
   - **Failure scenario:**
     - A relative `XDG_STATE_HOME` (which the XDG spec says to ignore) would now put `run.lock` and `ledger.json` inside the git checkout.
     - That makes the tree dirty, so cycle.sh's clean-checkout check fails, and the ledger then sits in a clone.
   - Every documented value is absolute, so this is an edge case.
   - **Suggestion:** reject non-absolute values with a fixed code, or note in the docs that these values must be absolute.
3. **Low — the regression test reads `$PWD`, not the physical directory.** (`bridge.test.ts:677`)
   - `$PWD` is the variable that bash's `cd` exports. A `run.sh` that only exported `PWD=...` would also pass.
   - `pwd -P` in the stub (or `readlink /proc/$$/cwd`) would check the real directory. Not blocking: the test does fail on develop's `run.sh` (verified below).
4. **Low — the test leaves its temp directory behind.** (`bridge.test.ts:671`)
   - Each run leaves one small `sr-bridge-cwd-*` directory with a few files, and nothing removes it.
   - This matches the file's existing `beforeEach` `mkdtemp` (`:33`), which is not cleaned up either. A `try/finally` `rm(root, { recursive: true, force: true })` would be tidy.

## Checked and fine (reviewer)

- **The esbuild spawn really uses the current directory:** `node_modules/esbuild/lib/main.js:2266` sets `var defaultWD = process.cwd()`, and `:2275`/`:2377` pass it as `cwd: defaultWD` to the service `spawn`. If the bridge user cannot search the start directory, the child's chdir fails, and Node reports that as spawn `EACCES`. The owner's diagnosis holds as far as it goes (see finding 1 for the rest).
- **Order and security:**
  - The order is: env scrub and re-exec (`:22-33`), then the user check (`:35-40`), then `umask`, then `REPO` and `cd` (`:42-47`), then the state directory, the lock and tsx.
  - The `cd` happens only after the clean-environment re-exec and after the refusal of root, sr-designgen and sr-igcapture. The env allowlist is unchanged.
  - `REPO` comes from `BASH_SOURCE` with `pwd -P`, which is the same value already used for the tsx path. The `cd` adds no new trust in any path.
  - `CDPATH` is not in the allowlist, and the path is absolute anyway, so `cd` prints nothing.
  - A failing `cd` under `set -euo pipefail` (inside the `{ … }` block) exits non-zero before the lock is taken and before tsx starts. It can only fail on a race, because `REPO` was just computed with the same `cd`.
- **What the new directory loads:** tsx and Node do not load `.env` files from it unless asked (`--env-file`). The `tsconfig.json` they now read belongs to the bridge user's own checkout, which is exactly what the systemd unit already did. So running by hand or from the cycle now behaves the same as the service.
- **systemd** (`scripts/sales-design-bridge/systemd/sr-design-bridge.service`): `WorkingDirectory=` is already the checkout, so the `cd` changes nothing there. `ProtectHome=read-only` only needs search permission for the `cd`.
- **Consistency:** all other tsx entry scripts (`sales-design-worker/run.sh`, `photo-poc.sh`, `sales-design-capture/run.sh`) already `cd` to their checkout. The bridge was the only one that did not.
- **The test is meaningful and portable:**
  - It copies `run.sh` into a temp checkout and stubs `id`, so the user check passes as root and as a non-root CI user.
  - It uses a temp `HOME`, does not pass `XDG_STATE_HOME` from the outer environment, and needs only `flock`/`timeout` from util-linux/coreutils.
  - `realpath` covers a symlinked tmpdir (macOS `/private/tmp`).
- **9f8c3ee:** the `as unknown as NodeJS.ProcessEnv` cast is needed, because Next's types make `NODE_ENV` required in `ProcessEnv`. The cast is type-only, so nothing changes at runtime. `tsc --noEmit -p .` shows no error in the test files. The only errors are the `PageProps`/`LayoutProps` ones, which come from missing `.next` generated types locally.
- **Scope:** `run.sh`, one test and one docs paragraph. No Protected Scope change, and no Staging, Production or Vercel action.

### New or remaining Low findings

A. **Low — an empty value passes the check, and `bridge.ts` then resolves it as a relative path.** (`run.sh:53`; `bridge.ts:73-74`)
   - `[ -n "$value" ]` skips empty values. `run.sh` itself treats an empty `XDG_STATE_HOME` as unset (`${XDG_STATE_HOME:-…}`), but `bridge.ts` uses `??`, which keeps `""`.
   - **Empty `XDG_STATE_HOME`:**
     - `run.sh` locks `$HOME/.local/state/sr-design-bridge/run.lock`.
     - `bridge.ts` puts the ledger in `join("", "sr-design-bridge")`, which is now `<checkout>/sr-design-bridge/ledger.json`.
     - The result: a fresh, empty ledger, so jobs already open in the real ledger are lost track of; a dirty tree, because that path is not git-ignored, so cycle.sh's clean check fails; and the lock and the ledger in different places.
   - **Empty `SR_DESIGN_BRIDGE_SPOOL`:** the spool root becomes `""`, so job files go to `<checkout>/to-worker`, where the worker never sees them.
   - **Where it bites:**
     - Under systemd, `ProtectHome=read-only` makes such a write fail instead.
     - cycle.sh always passes a non-empty spool.
     - So this only affects a run by hand, with a line like `SR_DESIGN_BRIDGE_SPOOL=` or `XDG_STATE_HOME=` in `design-bridge.env`. An empty token file or bypass file only fails with the existing codes.
   - The same `""` handling existed before this PR, but then it resolved against the start directory. The `cd` is what makes it land in the checkout.
   - **Suggestion:** refuse a set-but-empty value too (`[ -n "${!name+x}" ]` together with "starts with /"). Or make `bridge.ts` treat `""` as unset (`|| undefined`).
B. **Low — the new code is missing from the code table.** `BRIDGE_PATH_NOT_ABSOLUTE` is in the §5 paragraph (`design-bridge.md:116`) but has no row in the §7 table, next to `BRIDGE_WRONG_USER` (`:154`). The table is where a person looks up a `stopped:` code.
