## Findings and responses

1. **Low — the new `exception when check_violation` maps every check violation in the submit UPDATE to `invalid_result`, not only the summary's.**
   - Location: `supabase/migrations/20261020120000_sales_design_review.sql:109-123`.
   - Before, a check violation from another column raised a raw 23514. Examples are a `design_profile` over 8192 bytes, or a `design_worker_commit` that fails the regex. The server's `errorCode()` did not recognise that error, so it answered 503. The bridge then stopped (`BRIDGE_DISABLED`) and resent later.
   - Now the same row answers 400. The bridge closes the result as `refused`, and the demo goes to its next attempt after the lease.
   - The server's Zod schemas make these violations unreachable in practice, and refusing a value that can never fit is arguably better than retrying it forever. Still, it is a behaviour change. The header says "every guard of 20261009000000 unchanged" but does not mention it. The inline comment ("or any value") does.
   - **Response:** (for the author) keep it, and note the change in the header or in ARCHITECTURE §10.1. Or narrow the handler to the two `design_review` constraints.
2. **Low — rollout depends only on human ordering. A wrong order can make finished designs fail permanently.**
   - Scenario A: the worker is updated before the bridge. The old bridge's `WorkerResultSchema` is a `strictObject` (develop `lib/design-agent/bridge/spool.ts:54-55`), so every ready / `QUALITY_NOT_ACCEPTED` result with a `review` is `refused`.
   - Scenario B: the WSL bridge and worker run the DEV-058 commit, but `SR_DESIGN_BRIDGE_API_URL` points at a server deployment that predates DEV-058. For example, Production still on the previous release while the WSL checkout moved to the approved develop commit. The old server's strict `submitBody` answers 400 `invalid_request`, and the bridge closes the result as `refused`.
   - In both scenarios the demo stays `processing` until the 2 h lease, then is retried. After 3 attempts it is `failed`, permanently, and uses the template. Each attempt costs a full Codex run.
   - Nothing automated catches this. The DEV-052 cycle checks the bridge SHA, not the server's version. It is documented: `docs/operations/design-bridge.md` §10 gives the order migration → server → bridge → worker, and ARCHITECTURE §10.5 says the same.
   - The opposite order is safe. A server deployed before the migration answers 503 to a submit with `p_review` (PostgREST cannot find the function). The bridge stops before it claims, and the stale sweep runs only inside `sales_design_claim`, so the job keeps its id. The result is delivered once the migration lands. I verified this from the code, not by test.
   - **Response:** (for the author) acceptable as a documented human step. Optionally gate the worker's summary behind an env switch that is turned on last, or have the DEV-052 cycle confirm the target server accepts `review`.
3. **Low — the DB check is looser than `ReviewSummarySchema` on number representation and cross-field rules.**
   - I checked 32 shapes against the exact check expression on local Postgres.
   - Every type bypass is refused: strings, arrays (lax-mode unwrap), objects, JSON null, `null` fields, extra keys at top level or in `scores`, a case-changed verdict, out-of-range values, fractional scores and totals, and 1e400.
   - The check accepts `19.0`, `4.0`, `version: 1.0`, `max: 25.0`, and a `confidence` of any precision. `1e-400` is stored as a long decimal and parses to `0` in JS.
   - The check also does not enforce `total == f(scores)` or `qualityNotAccepted == (verdict != accept)`.
   - None of this is reachable through the server, which runs Zod first. The admin read path re-validates and hides anything that fails, and none of it can carry text.
   - **Response:** informational. No change needed.
4. **Low (tests) — the size bound is not tested on its own.**
   - The "long text (also over the size limit)" case is refused by the verdict enum first, so `pg_column_size(design_review) <= 512` is never exercised alone.
   - With fixed keys, enums and integers, the only way to reach 512 bytes is a very long `confidence` numeral.
   - **Response:** (for the author) optionally add one case: a valid summary whose confidence has about 600 digits.
