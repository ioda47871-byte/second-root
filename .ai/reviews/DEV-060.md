## Findings

1. **Medium — the root cause is plausible but not shown. The PR body's "even though the browser did end" is not backed by evidence.**
   - **CI evidence:** in the failing CI job (run 39197127588, job `unit`, PR #69 head cf62928), the test failed at the `not.toContain("C BROWSER_STUCK")` assertion (test line 628). That is before the `browser ended` assertion (`isConnected() === false`), so CI never recorded whether the browser actually exited later. The log has no timing for the kill phase.
   - **Local measurement:** I timed the kill phase (`settlesWithin(Promise.all([cdp, browser.close()]), killMs)`, `lib/design-agent/browser/diagnose.ts:292`) with temporary instrumentation, since reverted. Over 3 runs of the target test (9 kill phases) it took **78–102 ms**. Under 12 busy-loop processes on 4 cores it took **126–288 ms**. CI needed more than 1 000 ms, which is over 3× the worst stressed figure here. Either CI is much slower (disk or parallel Chromiums rather than CPU), or Chromium really did not exit.
   - **Failure scenario:** if it was a real hang, Chromium never finishes its graceful exit, and the 5 s floor does not hide it: the run still says `BROWSER_STUCK` after 5 s and the test still fails. So the floor **does not mask a hang**; it only tolerates slow exits of 1–5 s. If the flake comes back with the floor, treat it as a hang, not as load.
   - **DEV-055 checked as a cause and ruled out for this test.** The test replaces `closeTarget` with a promise that never settles, so the `Target.closeTarget` resends (`diagnose.ts:201-208`) never run here. The only DEV-055 effect is timing: `closePageBounded` with `now` gives up after 1 × `ms` instead of 2 × `ms`. So `Browser.close` is sent about 1 s sooner after the off-site hop (`/elsewhere/` on the same local server, which does not keep requesting). In production, a leftover targeted close (`readTargetId` / `newBrowserCDPSession` / `Target.getTargets` are unbounded) can still be awaiting a CDP reply after `closePageBounded` returns. Such a call rejects on disconnect and sends nothing after `deadline`, so it does not hold `Browser.close` back.
   - **Suggestion:** the mitigation can stay as is. To tell the two cases apart if it recurs, the test could record the kill-phase duration, or check `isConnected()` a few seconds after a `BROWSER_STUCK`. The new code comment (`diagnose.ts:83-88`) and the PR body should also stop stating "although it did end" as fact.
2. **Low — the "keeps the production bound" unit test does not prove what its title says.** (`tests/unit/design-agent/browser.test.ts`, the last `closeBrowser` test)
   - The fake browser ends after 100 ms, so the test passes with any `killMs` ≥ ~0.2 s, including a 5 s floor overriding 10 s.
   - It also spends a real 10 s waiting for the never-settling `context.close()`.
   - **Suggestion:** an exit after ~6–7 s would separate 10 s from 5 s. Fake timers would also remove the ~13 s of real waiting across the three new tests.
   - The other two tests are sound. With a 1 s bound and a 2 s exit, the old code returns `stuck` and the new code returns `killed`. An explicit `killMs` that is too short still returns `stuck`.
3. **Low (pre-existing, made more visible by the new naming) — nothing kills a Chromium that does not answer.**
   - **What the docs claim:** `closeBrowser`'s JSDoc (`diagnose.ts:278-283`) says an unresponsive browser "is killed by Playwright's own close (SIGKILL after its timeout)". `docs/operations/design-browser-wsl.md:138` says 「応答しない browser は Playwright 自身が後で強制終了する」.
   - **What Playwright 1.62.1 does:** `browser.close()` calls `gracefullyClose()` (`playwright-core/lib/coreBundle.js` ~8966). That sends `Browser.close` and waits for the process to exit, with **no timeout**. SIGKILL is used only on a *second* `gracefullyClose` call, or when the Node process exits (`killSet`).
   - **Effect:** in the test, `context.close` is patched on the client, so `browser.close()` is a purely graceful close. In production, the real `context.close()` has already started that close, so `browser.close()` only waits for `Disconnected`. Either way, the `"killed"` result and "kill phase" / `killMs` describe a graceful wait, not a kill. A hung Chromium stays until the diagnose process exits.
   - Behaviour is unchanged by this PR, but the wording should be corrected in a follow-up.
4. **Low — doc details.**
   - The `closeBrowser` JSDoc does not mention `killMs` or the floor.
   - `DiagnoseOptions.closeTimeoutMs` ("how long a close may take") no longer bounds ending the browser below 5 s.
   - `docs/operations/design-browser-wsl.md:138` still describes production correctly (10 s, above the floor), so it needs no change for this PR.
