### Low

**L1. `quota_or_rate_limit` 分類は `runCodexJson` 経由では到達しない（文書の記述とのずれ）**
`lib/design-agent/codex.ts:611-614`。`QUOTA_SIGN` に当たる場合は先に `CODEX_QUOTA` が throw されるため、`CODEX_EXEC_FAILED` の `diagnostic.class` が `quota_or_rate_limit` になることはない。`docs/design/phase2f-live.md` の「authentication → quota_or_rate_limit → …の順」という記述は `classifyCodexExit` 単体としては正しいが、実運用で記録される値としては誤解を招きうる。害はない（既存の `CODEX_QUOTA` が優先されるのは正しい）。

**L2. 広めの正規表現による誤分類（診断値の精度のみの問題）**
`lib/design-agent/codex.ts:217-221`。
- シナリオ a: 社内プロキシ／CDN が `403 Forbidden` を返した場合、ネットワーク起因でも `forbidden` に当たり `authentication` になる。
- シナリオ b: 本当の失敗原因がどの規則にも当たらず、stderr に無関係な警告（例: モデル一覧更新や telemetry の `timed out` / `error sending request` / `certificate`）が混ざっていると、`other_nonzero_exit` ではなく `network_or_transport` になる。
- シナリオ c: `invalid_request_error` は context 長超過などスキーマ以外の要求エラーも含むため `schema_or_arguments` に寄る。
- `model_unavailable` が `schema_or_arguments` より先だが、正規表現は「model」の後に否定句が続く形だけなので、典型的な `Invalid schema for response_format … 'not' is not permitted` を奪うことはない。
いずれも保存されるのは固定語のみで、挙動・承認・漏洩に影響しない。分類は「手掛かり」として扱う運用であれば許容範囲。必要なら将来、一致した規則が複数ある場合のフラグ等を検討（今回は不要）。

**L3. `minLength` 除去による空文字回答の可能性**
`lib/design-agent/phase2f/prompt.ts:49`。Codex が `choice`・`ui_label`・`prototype.html` に `""` を返すと Zod が拒否し、承認1回を消費する。
評価: 発生確率は低い。(1) Structured Outputs の厳格デコードでも必須の説明文フィールドを空にする動機が乏しく、プロンプトは内容を明示的に要求している。(2) 元々 Zod 側は `trim().min(1)` で、空白だけの文字列は JSON Schema の `minLength:1` でも通っていたため、`minLength` は完全な防壁ではなかった。(3) 一方 `minLength` は本番 worker のスキーマで実績がなく、Structured Outputs で非対応と扱われると今回と同じ「承認を使って即失敗」を再発させる。原因を一つに絞る目的からも、実績のあるキーワード集合に揃える判断は妥当。受容可能。

**L4. 型の緩さ**
`lib/design-agent/phase2f-live/design-call.ts:61`。`DesignCallResult.diagnostic.class` が `string` で、`CodexExitClass` を使っていない。実害なし（値は常に固定語）。

**L5. 画像呼び出し側は診断を残さない（スコープ外の確認事項）**
`lib/design-agent/phase2f-live/image-call.ts:139` は `diagnostic` を記録しない。DEV-119 の範囲（B の設計呼び出し）としては正しいが、C 方式の画像呼び出しで同様の失敗が起きた場合は原因が残らない。必要なら別 Task。
