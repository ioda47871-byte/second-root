### ロック

- すべての送信関数は最初に outreach の行を `FOR UPDATE` で取る (同じ outreach の承認・開く・送信済み・編集・取り消しは直列)。続いて `sales_send_guards` が prospect の行を `FOR UPDATE` (DNC の設定 `sales_set_dnc` と直列。待った後は確定した DNC を必ず見る)、demo の行を `FOR UPDATE`。
- 除外リスト: `sales_send_guards` が advisory lock `second_root_sales_exclusions` を共有で、`sales_add_exclusion` が排他で取る。先に確定した除外は必ず見え、後から追加する除外は進行中の送信の終わりを待つ。
- 二重の承認は outreach のロックで直列になり、同じ snapshot なら replay、違う snapshot は未オープンの承認を `superseded(reapproved)` にする (開いた承認があれば `approval_open` で拒否)。index が最後の砦。二重の送信済みは outreach のロックで直列になり、2つ目は replay (同じ `sent_at`)。

## 手動送信の状態

```
(drafted の下書き) ──この内容で送信を承認──▶ approved ──送信画面を開く──▶ send_opened ──手動で送信済みにする──▶ sent
                                              │        (mailto / IG / コピー)    │                         (outreach: drafted→sent、
                                              └────────── superseded ◀───────────┘                          デモの30日が始まる)
                                       (文面の編集 / 再承認 / 送らなかった)
```

- 承認は送信ではない。開くのも送信ではない (outreach は drafted、デモは非公開のまま)。送信済みはオーナー自身の確認で、表示は「手動で送信済み」。「自動送信済み」はどこにも無い (unit test で確認)。
- 送信済みにできるのは `send_opened` の承認だけで、承認した版・宛先・デモの版 (`sales_demo_version`) が今と同じとき (`sales_approval_is_current`)。違えば `stale_snapshot` (もう一度承認)。
- 設計の理由: 「承認」と「送信済み」の間で文面・宛先・デモが変わると、記録 (何を送ったか) と実際に送ったものが食い違う。そこで (1) 承認には表示した文面そのもの (server が DB から組み立て直し、表示と一致したものだけ) と版・デモの指紋を残し、(2) 文面のあらゆる変更で版を進め (trigger)、(3) 送信済みは同じ版・同じ指紋の承認だけを受け付ける。mailto / クリップボードには承認した文面を渡す。開いた後は編集を拒否する (送ったかもしれない文面を黙って差し替えないため)。

## オーナーの要件 1〜6

1. **文面の編集**: 「詳細」の「文面を編集」(`DraftEditor`) → server action `editDraft` (`lib/sales/draft.ts` の `checkDraftMessage` = prepare と同じ規則: 本文 1〜1200・件名 100 まで (空なら既定)・メールアドレス / URL 不可・HTML / 鍵の形不可、さらに mailto に収まること) → `sales_update_outreach_draft` (drafted の初回だけ・版の一致・開いた承認が無いこと・同じ境界を DB でも検査)。履歴は `sales_outreach_draft_edits`、`edited_at` / `edited_by` も。配信停止の文・注記・デモ URL・署名は保存する文面に含まれず、組み立て時に付くので消せない。DB は承認時にそれらが本文にあることを確かめる。
2. **送信の承認の記録**: `sales_outreach_approvals` に承認者 (auth uid)・宛先 (メール / IG handle)・表示した件名と本文そのまま・チャネル・デモ (token・design_status・design_updated_at・`demo_version`)・方式 (`manual`。`api` は予約のみ)・時刻 (承認・開いた・送信済み・取り消し)。RLS は admin read、書き込みは SECURITY DEFINER の関数だけ、クライアントからの直接書き込みは grant も無い。
3. **DB の照合と同時実行**: 承認・開く・送信済みのたびに `sales_send_guards` が DNC・連絡経路の条件・推奨チャネル・除外リスト (保存済みキー4種: handle・domain・保存済みメールの digest・正規化店名+住所、persist と同じ digest 方式)・宛先の重複 (ほかの outreach の生きている承認)・デモの有無と無効化・AIデザイン待ち (`p_design_enabled`、server が flag を渡す) を照合。除外は `sales_assert_outreach_eligible` に入れたので、送信済みの遷移 trigger・フォローの記録 (`sales_mark_follow_up_sent`) でも効く (DEV-194 の穴を塞いだ)。同時実行はロックの節のとおりで、統合テストで「同じ snapshot の3並列の承認 → 1行・replay 2」「2並列の送信済み → 1回・replay 1」「送信済みが待っている間に確定した除外 → 拒否」「承認が待っている間に確定した DNC → 拒否」「承認と編集の競合 → 古い文面の生きた承認は残らない」「関数を通らない2つ目の生きた承認 → unique index で拒否」を確かめた。
4. **手動送信の2段**: 上の状態のとおり。`markSent` は確認の段になり、開いた承認 (snapshot が一致) を要する。開く操作 (メールを作成・DMを送る・文面をコピー) は `send_opened` として記録するだけ。「送らなかった」で取り消せる。
5. **選んだ理由・改善の仮説**: `sales_prospect_insights` (出所: `ingest` + run_id / `owner` + written_by、written_at)。ingest は verified 候補の任意の `insights` (strict、無い payload はそのまま通る。長すぎ・連絡先・URL・HTML のものは捨てるだけで候補は拒否しない)。管理画面の折りたたみで値と出所 (JST) を表示し、オーナーが記入・編集・削除できる。無ければ「未確認」。`lib/sales/evidence.ts` は保存値を使う (`hypothesis` と `insights`)。値を作ることは無い。

## merge で migration が自動で適用されるか

- **GitHub Actions**: `ci.yml` だけ。integration / e2e-sales は CI の中の使い捨てのローカル Supabase (`npx supabase start`) に適用するだけで、hosted の project には触れない。`supabase db push` / `link` / Management API を呼ぶ workflow は無い。
- **Staging への適用**: 手動の `npm run staging:apply -- --project-ref … --confirm-ref … --apply` (`SUPABASE_ACCESS_TOKEN` が要る) だけ (`docs/STAGING.md` §3)。
- **Supabase の GitHub 連携 (branching)**: repo に設定の痕跡は無い (`supabase/config.toml` に branching 設定なし、文書は Management API による手動適用だけを記す)。Dashboard 側の設定はこの環境からは確認できない。
- **Vercel**: develop への merge で develop の Preview (Staging、`second-root-git-develop-brot-yanagi.vercel.app`) が自動でデプロイされる (`docs/STAGING.md` §5)。**migration は適用されない**。この PR のコードは新しい表・関数を前提にするので、Staging DB に migration が無いまま develop の Preview がデプロイされると、「今日」は「今日の一覧を読み込めませんでした」になり、承認・送信済みも動かない (他の画面は影響なし)。

## 残るリスク・限界

- AIデザインの flag は DB から見えないので、デザイン待ちの拒否は server が渡す `p_design_enabled` に依る (管理者本人が false で RPC を直接呼ぶ場合だけ通る。従来の server action だけの抑止より強くなった)。
- 宛先の重複は、生きている承認同士でしか見ない (DEV-195 より前に送信済みの outreach には承認が無い)。prospect の dedupe キーは表で unique なので、通常は同じ宛先の2店舗は存在しない。
- テストの fixture (DB の superuser で直接 `status = 'sent'` にするもの) は API role の経路ではないので、承認の要件の対象外。API role には表への書き込み権限が無い。
- 除外の照合で、候補が提出したが保存しなかった (第一者でない) メールは、送信時には照合できない (persist の時点では照合済み)。

- L3 (受け入れ): `sales_approve_outreach` の `strpos(p_body, o.body)` は、RPC を直接呼ぶ管理者なら、保存された下書きに任意の文を足した本文も承認できる。server action は DB から組み立て直した文面そのものしか渡さず、表示と違えば承認しないので、管理者本人だけの経路。承認の記録には実際の本文がそのまま残る。
- L5 (受け入れ): persist の後に登録された「第一者でないメール」の除外の digest は、そのメールを保存していないため送信時には照合できない。persist は準備の時点で候補の提出したメールの digest と照合済み。
- L6 (受け入れ、表示だけ): `sales_mark_sent` の replay は outreach が `sent` の間だけ。`replied` 以降の二度押しは `invalid_transition` になる (記録は変わらない)。

### CI `unit (1/2)` の timeout (`guardrails.test.ts` › keeps real shop data out of the repository)

- 原因はこの branch ではない (環境と元の重さ): develop の CI での同じテストの時間は 4504 ms (56a6a3b)・**5011 ms で失敗** (35fe85c、push run 42361067879)・4472 / 3559 / 4626 / 4845 ms。この branch (4264dda) は 5171 ms で失敗。
