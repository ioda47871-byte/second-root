## What I confirmed

- No migrations, RLS changes, grants, workflow or package changes. The diff is three files: the lib module, a unit test and a doc. Protected Scope is untouched.
- Pack selection: it uses the newest row by `seq`. That is the system's defined "current facts pack" (migration 20261115000000 §1). The send-time recheck (`sales_copy_send_block`), `import.ts storedFactsPack` and `demo-version-upload.ts demoForUpload` use the same rule. The demo does not name a pack id; it names the sha256 (`content.facts_pack_sha256`), and the function checks that through `assertDemoContentFromFacts`. The function also requires `stored.demo_id === demo.id`. On these points it is the same as or stricter than the importer and upload paths (it adds the DNC, disabled-demo and registry-identity checks).
- Races: the reads are not in one transaction. The DB trigger ties each pack's sha and shop to the demo content at insert time, and the function compares the demo content it read against the pack bytes it read. So an interleaving with a concurrent registration or content change either stops or returns a consistent earlier state. After the function returns, the importer reloads the store and the send gate checks the facts again.
- `sales_demos.prospect_id` is unique, so `maybeSingle` is sound. `sales_prospects(id, name, address, do_not_contact)` and `sales_demos(id, prospect_id, content, disabled_at)` exist in 20260927000000. The DB hash (`sha256(convert_to(text,'UTF8'))`) matches `TextEncoder` + sha256.

  - stale content -> TRUSTED_FACTS_CONTENT_MISMATCH

  - name mismatch -> PROSPECT_FACTS_IDENTITY_HOLD
  - bad UUID -> PROSPECT_ID_INVALID

## Findings

### M1 (Medium): the exclusion list is not checked, unlike the send gate
- Where: lib/sales/b-route/verified-generation-facts.ts:87-90
- What: only `sales_prospects.do_not_contact` is checked. The send gate blocks on `sales_outreach_block_reason`, which returns `do_not_contact` and then `excluded` (`sales_prospect_excluded`, migration 20261107000000 l.259-297). Every outreach path does the same check (`sales_assert_outreach_eligible`, and 20261111000000 l.1321). DEV-049 says an excluded shop (existing customer, partner) is one "the admin never wants prepared for sales".
- Failure scenario: a shop is ingested. Later the admin adds it to `sales_exclusions` as an existing customer, and `do_not_contact` stays false. This preflight still returns `factsBytes`, so the planned unattended B-route generation (doc "next PR" 1-2) prepares a sales design for an existing customer. The send gate rejects it only at the end. This is exactly the divergence the gate design avoids: generation accepts a prospect that the send gate rejects.
- Fix: fail closed on an exclusion match as well (for example `PROSPECT_EXCLUDED_OR_UNKNOWN`). Read `sales_exclusions` under the admin client's RLS and match on the same keys as `sales_prospect_excluded`: instagram_handle, website_domain, normalized name+address, and the email digest of `public_email` / first-party `sales_sources` email (reuse `lib/sales/exclusions.ts` / `email-digest.ts`). Stop when the read fails. Add a test. If a read-only DB helper is preferred, that needs a migration and its own approval.

### L1 (Low): the tests assert weakly and miss branches
- Where: tests/unit/sales/verified-generation-facts.test.ts:202-211 (loop asserts only `toBeInstanceOf(GenerationFactsStop)`). No test covers: unknown prospect, invalid UUID, `do_not_contact` null, shop_id mismatch, malformed JSON, the FactsStoreError code mapping, or a name mismatch (only the address is tested, while the doc claims 候補名/住所). The mock ignores the column and filter arguments of `eq`/`select`, so `.eq("id")` vs `.eq("prospect_id")` mistakes would pass. The mock row has `recorded_via: "owner"`, which the CHECK constraint forbids (harmless but not real).
- Scenario: someone swaps the order of the checks or the `eq` column in a refactor, and the tests stay green.
- Fix: assert specific codes for each case, record and assert the `(table, column, value)` passed to `eq`, add the missing cases, and use `recorded_via: "admin_session"`.

### L2 (Low): exact name and address equality will hold many real shops
- Where: verified-generation-facts.ts:114-116
- What: exact equality is far stricter than onboarding's `near()` (lib/sales/facts-onboarding.ts:63-84), which tolerates a prefecture prefix and containment. Raw prospect addresses come from ingest and only have to contain 名古屋市. A pack written as 名古屋市... will HOLD against 愛知県名古屋市...
- The PR documents this as intentional and it fails closed, so it is not a safety issue. Expect a high hold rate; consider surfacing the hold reason to the admin.

### L3 (Low): the trusted-client requirement is in comments only
- Where: verified-generation-facts.ts:49-51 and 85
- What: the signature accepts a service-role client just as well. RLS only protects when the caller passes the admin session client.
- Fix: in the next PR (the first caller), call it only from an admin-authenticated server path, for example after `sales_assert_admin`/`requireAdmin`, and add a test or contract that the caller uses the session client.

### L4 (Low): `expires_at` is not considered
- Where: verified-generation-facts.ts:95
- What: a demo that was sent and has since expired (`expires_at <= now()` and not `keep_alive`) still passes. Pre-send demos have a null `expires_at`, so the impact is small.
- Fix: decide and document whether generation for an expired demo is allowed.

### L5 (Low): eslint warnings
- Where: tests/unit/sales/verified-generation-facts.test.ts:35-38
- What: six `no-unused-vars` warnings for the `_`-prefixed mock parameters.
- Fix: drop the parameters or record them, which L1 also wants.

### New Low findings
- **L-a: two exclusion paths have no committed tests.** tests/unit/sales/verified-generation-facts.test.ts:117-131 has no case for the email-digest path (public_email or a source email) or for the 50-row cap. My probe confirmed both behave correctly. Fix: add both cases so a future refactor of the key building cannot drop the email side unnoticed.
- **L-b: a non-array `sources` does not stop.** verified-generation-facts.ts:64. If `sources` is not an array, only the public email is checked and the function proceeds. PostgREST returns `[]` for a one-to-many embed, so this is theoretical. Fix: stop with `PROSPECT_EXCLUDED_OR_UNKNOWN` when `sources` is not an array.
- **L-c: Postgres `lower()` and the JS `NFKC().trim().toLowerCase()` can differ for some non-ASCII characters.** Example: U+0130 lowercases to `i` under glibc but to `i` + combining dot in JS, so `normalizeEmail` returns null. SQL could therefore match a source email such as `İnfo@...` that TS misses. This needs a non-normalized non-ASCII source email value. The send gate still blocks such a shop. Fix (optional): also digest the plain `toLowerCase()` of each source email value when it passes `EMAIL_PATTERN`, or document the gap.
- **L-d: `keep_alive` is ignored.** verified-generation-facts.ts:75. A `keep_alive` demo past `expires_at` stops, while SQL treats it as live (`keep_alive or expires_at > now()`). This is stricter and fails closed. Document it or mirror the SQL rule.
