# DEV-039 investigation (read-only)

The bakery demo still ends as `RENDERER_CHANGE_NEEDED` after DEV-038 (18 / 18 / 18). This note investigates why. No code changed.

## What the reviewer is given

- **Screenshots:** `screenshotPage` (`lib/design-agent/preview-server.ts`) renders the phone page at a 390 × 844 CSS px viewport with `deviceScaleFactor: 2`, as a full page capped at 3200 CSS px. The PNG is therefore 780 px wide.
- **Prompt:** `buildReviewPrompt` (`lib/design-agent/prompts.ts`) calls it "mobile (390px wide)". It never says the image is at 2×.
- **No size reference:** the prompt gives neither the renderer's current constants nor any other size reference. The reviewer can only estimate sizes from pixels. A 12 px notice is 24 image pixels.
- **The note itself:** "If the fix needs something the renderer cannot do … set needs_renderer_change = true". The note is free text with no evidence or target format. It is not checked against what the renderer already does.

## Findings

1. **The font, line-height and padding the reviewer asked for are already met.**
   - Notice and footer text is 12 px, footer line-height 1.6, footer padding 16 / 20 px, heading → content 16 px, folio 11.2 px.
   - The note asking for them again is consistent with a scale misread: the prompt calls the image 390 px wide, but it is 780 px wide.
   - The reviewer also has no record of current values to compare against.
2. **A real footprint remains.**
   - The disclaimer is fixed wording: two sentences on separate lines, plus a long link. At 390 px it wraps to 6 lines.
   - With the notice, that is about 215 CSS px, roughly a fifth of a sparse page.
   - This is measurable whatever the font size. A sparse page makes the fixed chrome proportionally large.
3. **Section top padding is 32 px against the requested about 24 px.** That is a real but small difference: 3 × 8 = 24 px over the page.
4. **Folio tracking (0.26em) and area-label tracking (0.12em) are style choices, not density defects.** Together they take one 35 px row and the label rows.

## Structural convergence (six sparse runs)

- The two PoC runs, the two first reruns and the two final reruns all converge on `centered_cover / medium / editorial_12 / ruled_list / hairline / tight`. The one exception is the earlier ready bakery, which used `stacked_oversized / medium`.
- Direction, type, palette and motifs vary between runs.
- The structure is not re-evaluated here. That was deferred until after the DEV-038 rerun and is now due.

## Classification: C (both)

- **Objective part:** the fixed-wording footer plus notice take about 21 % of a sparse phone page, and section top padding is 32 px against 24.
- **Variability / non-actionable part:**
  - Half the final note restates values that are already met.
  - The review input invites px estimates from 2× images with a "390px wide" label and no reference values.
  - Nothing checks a renderer note against what the renderer already does.
- **Smallest generic CSS delta (proposal, not implemented):** phones, profile demos, `tight` only.
  - Footer: padding 12 / 16 px, line-height 1.5, paragraph gap 4 px. Estimated 166 → about 145 px with no wording change.
  - Section top padding: `--gap` 32 → 24 px. This changes DEV-036, and the geometry above (32 vs 24) is the evidence. Estimated −24 px over 3 sections.
  - Folio tracking (0.26em) left as is.
- **Making `needs_renderer_change` evidence-based (proposal, not implemented):** no change to the score, thresholds, blocking or max revisions.
  1. The review prompt states the real image scale ("the mobile image is 780 px wide: 2× of a 390 px CSS viewport") and lists the renderer's current measured values for the elements a note may name (section padding, heading gap, notice / footer font, line-height and padding, row padding).
  2. `renderer_change_note` names an element, a property and a target. When every named target is already met by the measured geometry, the pipeline asks the same reviewer once more with those measurements, like the DEV-034 second look, before blocking.
  3. A note that still names an unmet, measurable gap, or a capability the renderer lacks, blocks exactly as today.

## Implementation (feature/dev-039-review-scale): scale calibration only

- `lib/design-agent/shot-viewports.ts` is the single source of the screenshot viewports: desktop 1440 × 900 at 1×, mobile 390 × 844 at 2×.
  - `screenshotPage` / `capturePage` take their values from it. They are the same values as before; desktop's `deviceScaleFactor: 1` is now explicit.
  - Both review prompts take their scale line from it as well.
- Both review prompts (without photos / with photos):
  - say "desktop (1440 CSS px wide), then mobile (390 CSS px wide)";
  - add the scale line: "the mobile image shows a 390 CSS px wide viewport at deviceScaleFactor 2, so the image is 780 px wide and 1 CSS px = 2 image px … Judge type sizes and spacing in CSS px … never in raw image pixels";
  - add the renderer-change rule: only when the profile vocabulary and the renderer's current behaviour cannot reach the correction; no CSS target from raw image pixels; no renderer change to reach a size or spacing the page already has.
- Unchanged: CSS, schema / enums, scores, accept / revise, blocking, MAX_REVISIONS, the brief threshold, and the screenshots themselves.
- **Follow-up, not in DEV-039 — measured context:**
  - Today the renderer constants exist only as CSS. The geometry tests measure them in Chromium.
  - Giving the reviewer the current values without a second copy would mean measuring the rendered preview page during the worker's screenshot step (a page script next to `PAGE_INFO_SCRIPT`) and passing a compact block to the prompt.
  - That touches the capture path, the page scripts, the prompt and their tests. It is left as its own task.
