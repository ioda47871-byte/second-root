## Findings
### H1 owner 選定の判定が fail-open — controller.ts:88-89
`pending` と `rejected` だけを止め、それ以外はすべて実装へ進む。実測: ownerSelection が undefined / "" / "approved" / "SELECTED" を返すと implement → owner_review。approval・identity・package は「期待値以外は停止」なのにここだけ逆。型で守られるのは mock だけで、2g の目的（実ポート接続時のゲート）に反する。受入基準「オーナーの選定前は実装しない」の実行時違反。
修正: `if (selection !== "selected") return end(selection === "pending" ? "awaiting_owner_selection" : "stopped", ...)`（未知値は stopped+owner_check, 例 `OWNER_SELECTION_INVALID`）+ 未知値のテスト。

### M1 isolation テストの抜け — controller.test.ts:95-97
仕込み確認: `import {x} from "node:fs"` / `import type` / lib・app からの参照 → 検出（OK）。
すり抜け: `export { readFileSync } from "node:fs"`、`export * from "../intelligence/ledger"`、`() => import("node:fs")`（動的 import）、`lib/design-agent/loop/real-ports.ts` から `./controller` を import（`:!lib/design-agent/loop/**` 除外のため）。
修正: `/^\s*(import|export)\b[^;]*\bfrom\s/m` と `/\bimport\s*\(/` も禁止、loop/ 配下は controller.ts と（必要なら）テスト以外のファイルが無いことを確認。

### L1 実行されない修正がイベントに残る — controller.ts:105-110
3回目の比較で新原因 C → `fix:C:1` を記録してから RETRY_BUDGET_EXHAUSTED。監査ログ上「修正した」と読める。修正: 予算チェックを fix 記録の前に（attempts >= 上限なら fix を記録せず終了）。
### L2 fixesPerCause は現在の LIMITS では独立に効かない
3回上限下では修正は計2回までなので、SAME_CAUSE_FIX_LIMIT は「3回目も同じ原因」の時の停止コード名の違いでしかない。害はない（多重防御）が、テスト名「同じ原因の3回目の修正で止まる」は実質 attempt 上限と同時。コメントで明記を推奨。
### L3 原因コードの検証なし
`""` → `fix::1`、`"X,Y"` → events の区切りと衝突（`compare:1:X,Y` が2原因と区別不能）。修正: `/^[A-Z0-9_]+$/` 以外は stopped(output, owner)。
### L4 ポート例外・不正形状は throw
`{ok:"no"}` や compare の throw はそのまま例外（events 消失）。課金再試行は起きない（fail-closed）が、`stopped:PORT_THREW` + owner_check に正規化すると記録が残る。
### L5 テストの穴
stopClass "policy" の owner_check、implement/compare 失敗時の非修正、approval 拒否と保留の区別なし（`pending` しか無く、オーナーが拒否しても awaiting_approval のまま）。計画 2g の「費用の上限」は模擬版では承認1件=1呼び出しで代替している旨を tasks.json/note に残すとよい。
