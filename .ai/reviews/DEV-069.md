## Findings

1. **Medium — Instagram の UI 色の除外が、website の参考と post の中身にも効く。店の brand 色・料理の色が消え、「neutral」と誤って伝わる。**（`lib/design-agent/reference-colours.ts`、`INTERFACE` と `dist(c, rgb) < 30`）
   - **現状:**
     - `observeColours` は参考の種類を知らない。8 色（IG の青 3 色と、story ring の黄・橙・マゼンタ・紫・青紫）から RGB 距離 30 以内の画素を、すべての参考で捨てる。
     - prompt は website の参考でも「Instagram's own interface colours are left out」と書く。
   - **再現（一時 test で確認）:**
     - website 風の画像で、上 30% が橙の帯（`[245,120,35]`。story ring の橙 `[250,126,30]` から距離 約 9）、残りが白。
     - 結果は `{"colours":[],"colourfulShare":0}`。prompt の行は「almost no colourful pixels (0%); the material is neutral (white, grey, black)」。
     - 橙の brand の店に「素材は無彩色」という証拠を渡す。brief と review の両方に入る。
     - Instagram でも、カスタード・プリン色（`[248,214,125]`。黄 `[254,218,117]` から距離 約 11）の post の半分が消える。残る茶色が 100% と出る。
     - 名古屋の飲食店で、橙・黄・ピンクは珍しくない。
   - **補足:** story ring はアバターを囲む細い輪なので、面積は小さい。しかもアバターは media の矩形として pixelate される。除外の効果は小さく、誤除外の害の方が大きい。
   - **提案:**
     - `observeColours(pngs, kind)` にして、`INTERFACE` は `instagram` のときだけ使う。
     - 除外は IG の青（`#0095F6`・`#00376B`・`#4193EF`）に絞り、story ring の 5 色は外す。
     - 文面の「Instagram's own interface colours」も、instagram のときだけ書く。
     - website で橙の帯が残ることを test にする。

2. **Medium — 色の list が空なら、colourful な画素の割合に関係なく「almost no colourful pixels; the material is neutral」と書く。**（`observedColoursLine`、`observed.colours.length === 0` の分岐）
   - **現状:** 「neutral」と書く条件は、`MIN_SHARE`（4%）以上の group が無いことだけ。`colourfulShare` は見ていない。
   - **再現（一時 test で確認）:**
     - 彩りの多い grid（互いに 44 以上離れた 37 色、各 約 2.7%）。
     - 結果は `{"colours":[],"colourfulShare":0.98}`。prompt の行は「almost no colourful pixels (98%); the material is neutral (white, grey, black)」。
     - 自己矛盾した証拠が brief と review に入る。いろいろな料理の写真が並ぶ grid で起こりうる（ぼかしの後も色相がばらばらなとき）。
   - **低彩度の色も「neutral」になる:**
     - `MIN_CHROMA = 28`（max − min）なので、クリーム・ベージュ・クラフト（`[240,232,216]`、chroma 24）や濃い茶（`[60,45,36]`、chroma 24）は neutral として捨てられる。
     - 一時 test で、クリーム 75% と濃い茶 25% の画像 → `colours: []` →「the material is neutral (white, grey, black)」。
     - カフェ・パン屋で多い配色が「白・灰・黒」と伝わる（Low 2 と同根）。
   - **提案:**
     - 「neutral」と書くのは、`colourfulShare` が小さい（例: < 0.05）ときだけにする。
     - それ以外で list が空なら、「many different colours, none above 4% of the colourful pixels」のような固定文にする。
     - 文面は「white, grey, black」ではなく「near-neutral (white, cream, grey, black and other low-saturation tones)」にする。
     - 上の 2 つの筋書きを test にする。

3. **Low — 写真の review（`buildPhotoReviewPrompt`）には色が渡らない。**（`photo-prompts.ts`・`photo-pipeline.ts`）
   - 写真の loop でも、review は `revised_profile`（palette を含む）を返す。そのため、写真ありの job では revision の根拠が brief と review で揃わない。
   - 害は「証拠が無い」だけで、従来と同じ。gate も変わらない。
   - **提案:** `PhotoPipelineInput` 経由で同じ行を渡す。今回入れないなら、blockers に次の作業として記す。

4. **Low — 中立色の扱いが、website の白黒の brand を伝えない。**
   - 白・黒が brand の website（例: 黒地に白文字の bar）では、中立は全部捨てられる。prompt に残るのは「Colourful pixels are N% …」だけで、明るい／暗いのどちらが優勢かは出ない。
   - Codex は画像そのものも見ているので、害は小さい。それでも「measurements」としては片側だけになる。
   - **提案:** 中立の画素を「light」（例: max ≥ 200）と「dark」（max ≤ 60）の割合に分けて、1 句添える（例: `neutral: 70% light, 12% dark`）。hex を増やさずに済む。

5. **Low — test の穴。**（`tests/unit/design-agent/reference-colours.test.ts`）

   - 「colourful は多いが list は空」の test が無い。Medium 2 があっても通る。
   - palette・16-bit・interlaced の PNG → null（skip）の test が無い（一時 test では null を確認した）。
   - colour type 2（RGB、3 channel）の PNG の test が無い。
   - `worker.test.ts` は、`reference_colours` の形（`colourfulShare` が number、hex の書式）だけを見る。

### Nits

- N1 — brief では、色の行が「Attached images: the first N are …」と「The last 2 show the current generic demo …」の間に入る。画像の説明が 2 つに割れる。「The last 2 …」の後に置く方が読みやすい。
- N2 — Instagram の dark mode の link 色（`#E0F1FF`、chroma 31）は colourful として数えられる。面積は小さいので、`MIN_SHARE` でほぼ落ちる。public capture は light の既定で撮るので、実害は無い。
- N3 — `reference_colours` は report の `codex` の中にあり、prompt に「何を伝えたか」の記録になる。ただし Medium 1・2 を直した後は、文面の分岐（neutral／多色）も判断できるように、`neutralShare` などを併記すると後の調査に役立つ。

## 確かめて問題なかったこと（reviewer）

- 読む file は、`checkReferenceImages` が名前・拡張子・symlink・owner・mode・大きさ（≤ 8 MB）・signature を確かめた同じ `refs` だけ。`readFile` の失敗は `Buffer.alloc(0)` → `decodePng` の RangeError → skip。
- `decodePng` が壊れた入力で throw せずに返す場合（IDAT が短いなど）も、`out` は全長で確保される（足りない値は 0）。NaN や `#NaN…` の hex にはならない。chunk の length が大きくても `at += 12 + length` で必ず進むので、無限 loop にならない。
- jpg・webp の参考（`SIGNATURES` は許す）は `decodePng` が throw → null → prompt は従来どおり。今の capture は PNG だけ。
- bucket の key（各 channel の上位 4 bit）と merge（数の多い順の greedy、重み付き平均）は正しい。`near.rgb * near.n + b.r`（b.r は合計）で重みが合う。shares は colourful な画素に対する割合で、filter（≥ 4%）→ 上位 5 の順。並びは多い順。
- hex は 0–255 の平均を丸めたものを 2 桁の大文字にする。`#RRGGBB` の外には出ない。
- alpha < 200 の画素は数えない（参考は不透明なので影響は無い）。
- 計算は同期だが、最大 6 枚 × 1280×1000 で 約 1 s 以内。job の時間の予算に比べて小さい。

## 対応（実装者、merge 前）

- Medium 1: `observeColours(pngs, kind)`。除外は Instagram の参考だけ、かつ Instagram の青（ボタン・リンク・認証）だけ。story ring の色は除外しない（カスタード色の投稿が残る test）。website では中立色以外は何も除かない（白地の橙のヘッダーが残る test、同じ画像を Instagram として測ると青だけが消える test）。prompt の文面も参考の種類ごと（website では Instagram に触れない）
- Medium 2: 空の一覧の文面は `colourfulShare` を見る（10% 未満だけ「neutral」、それ以外は「many colours, none above 4%」）。中立の言い方を「neutral or near-neutral (white, cream, grey, dark brown, black)」に。両方の test
- Low（写真の review）: `buildPhotoReviewPrompt` にも同じ任意の引数を渡す（null なら prompt は従来どおり、snapshot は不変）。photo-pipeline の ctx・pipeline から渡す
- Low（白黒の brand）: `lightNeutralShare` / `darkNeutralShare` を ObservedColours・prompt の行・report に
- Low（test）: website・色の多い空の一覧・palette / 16-bit / interlaced → null・RGB 3 channel の test。worker の test は 3 つの割合の和 ≈ 1・色は 5 つまで・各 4% 以上・hex の形まで確かめる
