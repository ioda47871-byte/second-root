# DEV-045: why the brief prefers centered_cover / tall / editorial_12 / ruled_list / generous (research only, 2026-10-17)

Trigger: the saved low-confidence brief of the last bakery run (0.46) chose `centered_cover / tall / left / editorial_12 / ruled_list / generous`, the bakery category default's structure (DEV-043 / DEV-044 step 0).

Sources: repo code at develop `ceefde5` and `.ai/reviews/DEV-029…044.md`. No screenshots, Instagram content, cookies, HTML, URLs or session data were opened. Only one brief's structure is known; the others are recorded as finals or directions only.

## What the brief sees (repo facts)

- `buildBriefPrompt` (`lib/design-agent/prompts.ts:71-86`): role line, `VOCABULARY`, `RULES`, the reference images (blurred and pixelated, `referencesLine`), 2 screenshots of the current generic demo "to move away from", an optional team hint, and the fact-only `factsBlock`.
- **No category default reaches the brief.**
  - `prompts.ts` does not import `defaults.ts`.
  - The production worker never passes `hint` (`worker/run.ts:516-522`); only the dev script `scripts/sales-design/design-demo.ts` has `--hint`.
  - The default and the brief agree because they read the same vocabulary the same way, not because one leaks into the other.
- **The current generic bakery demo already has a centred hero** (`components/demo/bakery.module.css:9`, `BakeryTemplate.tsx`). "Move away from it" therefore does not push toward a centred cover.
- **Enum order in the JSON schema Codex receives** (`z.toJSONSchema`, the same order as `profile.ts` and `VOCABULARY`):

| Field | Order | Brief's choice | Position |
|---|---|---|---|
| `heroLayout.layout` | split_crop, stacked_oversized, centered_cover | centered_cover | last |

- **Only some values are described in `VOCABULARY`** (`prompts.ts:9-34`).
  - Each hero layout gets a sentence. `split_crop`'s example is a two-word Latin name ("EXAMPLE" / "BAKE"). `stacked_oversized` is "as large as the width allows". `centered_cover` is "a magazine cover".
  - `editorial_12` is described ("label column + wide text column"), while `asymmetric_7_5` and `single_column` have no description.
  - `ruled_list` and `colophon` are described.
  - `height`, `alignment` and `spacing` are bare lists.
- **Sparse-evidence instruction** (`prompts.ts:41`): "If the material says little about the shop's style, choose a calm direction that suits the category and set confidence below 0.5."
- **The brief never sees what the layouts look like.** It gets text descriptions only; no rendered example of each structure is attached.

## Causes, separated

1. **Prompt bias: real, moderate.**
   - "Choose a calm direction" on sparse evidence steers the structure, not only the direction. Among the three heroes, the balanced, symmetric "magazine cover" is the calm one. `stacked_oversized` ("as large as the width allows") and `split_crop` (cropped, pushed right) read as bold. For spacing, `generous` and `tall` read as calm.
   - `split_crop`'s only example is a spaced Latin name. For a short Japanese name, the model can fairly conclude it does not apply. That is in fact true of the renderer (DEV-042 cause 5 / DEV-043 notes), so the example is accurate, but it removes one of three options for most shops here.
2. **Enum / order bias: likely for the secondary fields, not for the hero layout.**
   - grid, infoStyle, spacing and divider all landed on the first-listed value, which is also the only described or most described one (`editorial_12`, `ruled_list`). When nothing distinguishes the options, first-listed and described is the usual pick.
   - The hero layout picked the last-listed value, so order does not explain it. Description and "calm" do.
   - `tall` is the middle of three heights, a typical compromise choice.
3. **Sparse-evidence rational choice: real.** With blurred references, few facts and no visual examples of the options, the lowest-risk structure is the classic, symmetric one. The category default (hand-made by a person reading the same vocabulary) made the same choice. This is not a defect: with no evidence, a stable choice is reasonable.
4. **Lack of information to tell the structures apart: real, and the root.**
   - The structural fields do not depend on the shop's style as much as direction, palette and type do.
   - The material rarely says anything about layout.
   - The brief cannot see renders of the alternatives.
   - For a sparse demo the structures differ mostly in hero size and rhythm, which the prompt describes only for the hero.
   - So the choice falls to the prompt's framing (1) and list order (2).

## Conclusion

- **Closed as research only. No code change.** No single small, generic change is clearly justified:
  - every candidate changes what the model chooses (prompt wording, attached examples, or the order Codex sees), so it is a design-policy decision;
  - each one's effect could only be judged by controlled reruns;
  - reordering the schema's enums is close to the forbidden "schema enums" scope.
- **DEV-043 runtime validation keeps waiting** for a naturally occurring run, or a future test case, whose brief selects `stacked_oversized` or `split_crop`.
- **Candidate follow-ups (backlog; a person decides; each needs a controlled rerun to evaluate):**
  - **DEV-046, brief structure guidance:**
    - keep "calm" for direction, palette and type only, and say that structure should follow the shop's content shape (name length and script, how many facts) and that all three heroes are valid for sparse pages;
    - describe the undescribed grid, info and spacing values neutrally;
    - drop or balance the Latin-only `split_crop` example. Prompt-only.
  - **DEV-047, rendered examples for the brief:** attach small renders of the same fictional sparse demo in each hero layout (our own renderer, no shop material), so the choice is visual rather than text-only. A larger change (worker inputs, image count, timing).
  - **Pre-existing, separate:** `heroLayout.alignment` is described as visible but has no CSS (DEV-044 notes). Either implement or describe it as inert.
