# DEV-197: 送信の3状態と、表示・処理・記録の一致 (DEV-195 最終レビュー L1〜L3)

2026-11-10。DEV-195 (PR #239、develop 6443d99) の最終独立レビュー (C0/H0/M0/L3) の Low 3件を、オーナーの指示どおり1つの PR で直す。branch `feature/dev-197-send-state-consistency` (`origin/develop` 6443d99 から)。

**原則 (オーナー)**: 送信できるか判定できないときは安全側に倒し、表示・サーバーの処理・保存した記録を食い違わせない。

## 変更

### L1: 「未確認」を「送れない」と表示していた

- 原因: カードは `!evidence.contact.sendable` だけで「送れない状態になりました・事後記録・フォローは出ません（禁止）」を出していた。`sendable` は DNC・除外と無関係の照合が未確認 (例: 除外リストを読めない) でも false になる。DB は取引の中で DNC・除外を照合し、当たらなければ通常の送信 (`blocked_after_open = null`) として記録し、5日後にフォローが出る。画面の文言と保存した記録が食い違っていた。
- 修正:
  - `lib/sales/evidence.ts`: `ContactVerdict.state` = `sendable` / `blocked` (確定した ng がある) / `unknown` (ng は無いが未確認がある)。`ContactVerdict.block` = `confirmed` (DNC か除外が確定) / `unknown` (どちらかが未確認) / `clear`。
  - 新しい送信 (未オープン): `sendable` 以外は従来どおり送信の操作を出さない (fail closed)。`unknown` は「送信できるか確認できませんでした（上の「未確認」の項目）。再読み込みしてください。確認できるまで送信の操作は出しません。」(`send-blocked` に `data-send-state`)。
  - 開いた承認: 「事後記録」「フォローは出ません（禁止）」の文言 (`approval-blocked`) は `block === "confirmed"` のときだけ。それ以外で送れない / 確認できないとき (`approval-unknown` / `approval-check-failed`) は、ブロックを主張しない文言で「送信済みの事実を記録」だけを出し (開く・メール・DM・コピーは出さない)、「通常の送信か事後記録かはサーバーが確かめ、記録した内容を表示します」と書く。
  - 送信済みの後: `markSent` は `sales_mark_sent` の結果 (`blocked_after_open`・`stale_at_send`・`replayed`) を `recorded` として返す (`lib/sales/approval.ts` の `recordedSend`)。カードは一覧から消えるので、`components/admin/SendRecordNotice.tsx` (「今日」の一覧の上、ページ全体を包む client の provider) が DB の保存した状態を出す: 「手動で送信済みとして記録しました（通常の送信）」/「送信済みの事実を事後記録しました。…『営業不要（DNC）』/『除外リストに一致』になっていたことも記録…フォローは出ません」/ 古い snapshot の注記。結果の形が想定外なら「記録の内容を確認できませんでした。履歴で確認してください」と言い、通常の送信と推測しない。

### L2: ブロックかつ古い snapshot だと、送った事実を記録できなかった

- 原因: 開いた承認がブロック (DNC / 除外) かつ snapshot が古い (開いた後にデモの AI デザインや宛先が変わった) と、画面は確認ボタンを隠し、DB は `stale_snapshot` で拒否した。実際に送ったオーナーは「送らなかった」しか押せず、送信の事実が失われた。MVP_SPEC §4 の「ブロック後でも実際の送信は記録できる」と矛盾。
- DB の変更が要る (`sales_mark_sent` が `stale_snapshot` を先に返すため)。新しい forward-only migration `supabase/migrations/20261110000000_sales_send_stale_after_block.sql` (既存の migration は編集していない):
  - `sales_outreach_approvals.stale_at_send boolean not null default false` と check `sales_outreach_approvals_stale_at_send` (`not stale_at_send or (state = 'sent' and blocked_after_open is not null)`)。送信済みの承認は最終 (`approval_final_immutable`) なので、`send_opened → sent` の時に1度だけ書かれ、変えられない。
  - `sales_mark_sent(uuid, uuid, boolean)` を同じ引数で `create or replace` (grant は保持され、同じ revoke / grant を書き直した)。古い snapshot を受け付けるのは **send_opened・取引の中で DNC / 除外が見つかった・文面の版とチャネルが承認と同じ** ときだけ。記録は承認の snapshot (開いて送った内容) のまま、`blocked_after_open` と `stale_at_send = true` を残す。結果の jsonb に `stale_at_send` を足した (replay も)。
  - そのまま残した照合: ブロック無しの古い snapshot は `stale_snapshot`。文面の版・チャネルが変わった承認は (ブロック後でも) `stale_snapshot` (outreach の文面と承認の文面が食い違わないように)。未オープン (`not_opened`)・superseded・管理者・宛先の重複・連絡経路・推奨チャネル・デモ無し / 無効 (DNC による無効を除く、従来どおり)・AIデザイン待ちは `sales_send_guards(..., true)` のまま。フォローは `blocked_after_open` で従来どおり禁止。新しい送信の経路は無い。
  - 画面: ブロック確定 (または DNC / 除外が未確認) で、古い理由がデモ・宛先だけ (`ApprovalView.textStale === false`) なら「送信済みの事実を記録（事後記録）」を出し、「承認した内容のまま記録でき、変わっていたことも記録されます」と書く。文面が変わった承認・ブロックの可能性が無い古い承認には出さない (`textStale` が無ければ変わったものとして扱う)。画面から見えない変化 (デモの内容・デザイン) は、DB が古いと判定して `stale_at_send` を記録し、画面は通知でそれを出す。

## 影響の再評価 (表示と記録の食い違い: 監査と営業判断)

**誤って記録されえたもの (修正前のコード + DEV-195 の migration の環境)**

- 条件: 送信画面を開いた承認があり、その後に読み込んだ「今日」で DNC・除外以外の照合が「未確認」になる (除外リストの読み取りの失敗、`do_not_contact` / 住所 / 業種 / `website_status` / 出典の欠け)。
- 監査の記録: DB の記録そのものは正しかった。DB は取引の中で DNC・除外を照合して `blocked_after_open` を決め、`sales_check_outreach_update` が店舗の今の状態との一致を確かめる。つまり「通常の送信 (`blocked_after_open = null`)」と記録された送信は、DB の時点で本当に DNC でも除外でもなかった。食い違っていたのは**画面の文言** (「送れない状態になりました」「フォローは出ません（禁止）」「事後記録」) で、記録 (`sales_outreaches` / `sales_outreach_approvals`) は誤っていない。
- 営業判断への影響: オーナーが画面を信じると、(1) 実は送れる店舗を送れないと思い、送った事実を「送らなかった」で取り消す (送信の事実の欠落)、(2) 5日後に出たフォローを「禁止のはず」と混乱する、または (3) 本来出るべきフォローを自分で控える、ことがありえた。逆向き (送れない店舗に送れると表示) は起きない: 新しい送信は未確認でも fail closed のまま、DB も DNC・除外を拒否する。
- L2 の側: ブロックかつ古い snapshot の場合は、実際の送信が記録されない (outreach は `drafted` のまま、承認は取り消し) ことがありえた。この場合、ファネルの送信数・デモの30日の開始・「この店舗へは送った」という記録が欠け、同じ店舗にもう一度承認・送信を試みる余地が残る (ただし DNC / 除外の店舗なので、DB が新しい承認と開くを拒否する)。

**実データへの影響**

- Staging: DEV-195 の migration は 2026-11-10 に適用。outreach は 3 件で、新しい流れ (承認 → 開く → 送信済み) で送った outreach は無い (`sales_outreach_approvals` 0 行、適用時の確認)。したがって、食い違いの文言の下で記録された送信も、L2 で失われた送信も無い。
- Production: DEV-195 の migration が無い (承認の流れ自体が無い)。影響なし。
- 本 PR の migration 20261110000000 は**どの hosted DB にも適用していない**。Staging には DEV-195 と同じく別承認で適用する。適用までの間 (merge 後の Staging): `sales_mark_sent` の結果に `stale_at_send` が無いので画面は「古い snapshot ではない」と読む (旧関数は古い snapshot を記録しないので正しい)。画面がブロック後の古い承認に事後記録を出しても、旧関数は `stale_snapshot` で拒否し、理由を表示する (誤った記録はできない)。コードは新しい列を読まない。

## 残るリスク・限界

- ブロック後でも、AIデザインの生成中 (pending / processing、step ON) は `design_pending` で拒否する (オーナー指示: ほかの照合は残す)。生成が終われば古い snapshot として事後記録できる。
- ブロック後でも、連絡経路の条件が崩れた (公開メールの出典が消えた等) 場合と、文面の版が変わった場合は記録できない (開いた承認がある間は文面の編集を DB が拒否するので、版が変わるのは DB への直接の書き込みだけ)。
- 通知は画面の一時的な表示 (再読み込みで消える)。保存した状態そのものは DB (`sales_outreaches.blocked_after_open`、`sales_outreach_approvals.blocked_after_open` / `stale_at_send`) にある。

## 独立レビュー 1回目 (a232e1f: C0 H0 M0 L2) と対応

### L1. ブロック後でも、店舗の今の宛先で送った事実が失われた (修正)

- 原因: 事後記録の経路も `sales_send_guards(o, …, true)` を通り、店舗の**今の**宛先を照合していた。開いて送った後に DNC になり、公開メールが消えた / ほかの営業の承認と同じ宛先に変わると、`recipient_missing` / `duplicate_recipient` (メールが消えた場合は先に `email_not_eligible`) で古い snapshot の分岐の前に断られ、送信の事実が失われた。画面と MVP_SPEC は「宛先が変わっていても記録できる」と言っていた。
- 修正 (migration 20261110000000 を同じ PR の中で修正。どの DB にも未適用):
  - `sales_mark_sent`: 先に (sales_send_guards と同じ順で) 除外の共有 lock・prospect の行 lock を取り、DNC / 除外を読む。
    - ブロック無し (通常の送信): `sales_send_guards` と現在の snapshot の照合を 20261107000000 のまま。
    - ブロックあり (事後記録): 店舗の今の宛先の有無・重複は照合しない。記録するのは承認の宛先 (開いた時に有無と重複を照合済み、送った宛先)。連絡経路の条件は**承認の宛先**で判定する新しい内部関数 `sales_assert_recorded_channel` (メール: その宛先の店舗自身の出典行がある / Instagram: 公式サイトなし)。推奨チャネルは照合しない (新しい送信のチャネルを決めるもので、表の check が公開メールと結び付いているため、宛先が消えると必ず変わる)。文面の版・チャネルの一致、デモ (無い / DNC 以外の無効)、デザイン待ちは断る。
  - trigger `sales_check_outreach_update` (create or replace): `blocked_after_open` つきの送信済みは、店舗の今の宛先の代わりに、その outreach の送信済みの承認の宛先で `sales_assert_recorded_channel` を確かめる (送信済みの承認が無ければ `approval_required`)。そのため `sales_mark_sent` は承認を先に更新する。状態の一致 (`blocked_after_open_mismatch`)・遷移の時だけ書けることは不変。
  - 残した照合 (安全のため): 承認の宛先の出典が消えたメールは事後記録も断る (`email_not_eligible`)。既存の DEV-195 のテスト (DNC + メールの出典を削除 → `email_not_eligible`) はそのまま通る。
- テスト (統合、新規 3): 公開メールが消えた後の事後記録 (承認の宛先・`blocked_after_open`・`stale_at_send`・フォローなし) / ほかの営業の承認と同じ宛先に変わった後 (ブロック前は断る、除外の後は記録、相手の承認は不変、フォローなし) / 限界 (出典が消えたら `email_not_eligible`、送信済みの承認なしの flag つき遷移は trigger が `approval_required`)。
