2. **Low — the shop name and address fields could carry an email.**

   - Integration test added: a stale digest still matches by the first-party email.
   - Staging has no checkpoint with `email_digest` at all, checked read-only: 3 runs, last on 10/16, none running.
4. **Low — drift detection compares only migration versions.**

   - This catches a database that applied the first DEV-049 version. `staging:apply` / `staging:verify` run it after applying. Any old local stack needs `supabase db reset`.
5. **Low — the e2e page-HTML check ran only after removal.**

## Checked and fine (reviewer)

- **TS and SQL digest parity:** they match for ASCII and full-width or IDN input (prefix including `chr(10)`, UTF-8, lowercase hex).
- **Persist:** `public_email` and `email_digest` always refer to the same normalised email. The function differs from DEV-049 only in the email predicate. Order, idempotency, DNC, dedupe and the daily cap are unchanged. Grants are `service_role` only.
- **Add RPC:** the admin check comes first; SECURITY DEFINER, `search_path=''`, authenticated only. Check and unique violations are caught, so a failing row with an address is not logged. A unique DETAIL would show only the digest.
- **Email-shape guard:** TS and Postgres agree (`standard_conforming_strings`, `[:space:]`, NFKC first). Deliberate obfuscation such as `[at]` or `。` is an accepted residual.
- **UI:** shows only `hasEmail`, never the digest or the address. The form is cleared after saving, and the client module does not import `node:crypto`.
- **RLS, grants and Op Claude access:** unchanged. Docs state the SHA-256 dictionary limit and the HMAC next step.
