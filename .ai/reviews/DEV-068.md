## Findings

1. **Medium — 住所の weight の上限（600）が効かず、editorial_serif と mincho の bold / black では住所が Black / ExtraBold で描かれる。**（`profile.module.css` の `.addressValue { font-weight: min(var(--display-weight), 600) }` と、`fonts.ts` の weight 400/900・400/800）
   - **現状:**
     - `.addressValue` は `var(--display)` の書体を使い、weight は display weight と 600 の小さい方。CSS の comment に「The address is read, not a headline: … its own size and weight caps」とある。
     - 新しい静的書体の weight は 400 と 900（B1 は 800）だけ。CSS の font matching では、600 を求めると「500 より重い → より重い方から探す」。そのため 900 / 800 が選ばれる。
     - develop では `--font-display` = Shippori Mincho（400/600）なので、600 = SemiBold だった。
   - **実測（CDP、390px、名前は 23 字）:**

     | face / weight | 住所の computed weight | 実際に描いた font |
     |---|---|---|
     | editorial_serif / black | 600 | `ZenOldMincho-Black` |
     | editorial_serif / regular | 400 | `ZenOldMincho-Regular` |
     | mincho / black | 600 | `ShipporiMinchoB1-ExtraBold` |
     | mincho / regular | 400 | `ShipporiMinchoB1-Regular` |
     | condensed / light grotesk | – | `NotoSansJP`（`--font-body` に切り替わるので影響なし） |

   - **シナリオ:**
     - Codex が「力強い見出し」を狙い、`editorial_serif` + `displayWeight: "bold"` を選ぶ。
     - 来店情報の住所（`名古屋市千種区架空町1-2-3`、1.2〜1.9rem、line-height 1.5）が、Zen Old Mincho Black で組まれる。
     - 太い明朝の細かい画（「架」「種」など）は潰れやすい。電話番号・番地も Black になる。読む情報の可読性が下がる。
     - 見出しと同じ重さになり、上限を設けた設計意図（見出しと読む文字の差）も失われる。
   - **提案（どれか 1 つ）:**
     - (a) 上限を 500 にする（`min(var(--display-weight), 500)`）。500 を求めると「500 → 400 より軽い方」の順で 400 が選ばれる。住所は Regular になる。grotesk は `--font-body` なので影響しない。
     - (b) editorial / mincho の住所も、grotesk と同じくサイトの書体にする（`font-family: var(--font-display), serif`）。従来の Shippori Mincho 400/600 に戻る。
     - (c) 600 か 700 の weight を足す（静的 font が約 2.6〜5MB 増えるので、非推奨）。
     - どれを選んでも、「住所の描画 font が Black / ExtraBold でない」ことを実 build で確かめ、記録する。unit では、CSS の上限値を文字列で固定する程度でよい。

2. **Low — demo の 3 route に、使わない face の `@font-face` CSS も 4 書体分すべて載る。render-blocking な CSS は gzip で約 213KB 増え、約 1.9 倍になる。**（`fonts.ts` を ProfileRenderer が静的に import）
   - **実測（gzip -9）:**
     - Zen Old Mincho 59.8KB、Shippori Mincho B1 62.2KB、Zen Kaku Gothic New 59.7KB、M PLUS 1 30.9KB。
     - 頁が使う face は 1 つだけ。それでも CSS（各 120〜245 個の `@font-face`）は 4 つすべて読み込まれる。
     - develop の demo route の CSS は約 232KB（gzip）、本 PR の後は約 445KB。
   - font file そのものは unicode-range で必要な分しか取得されない。fonts.ts の comment のとおり。
   - **影響:** 見込み客が携帯で開く `/demo/[publicToken]` の初回描画が遅くなる。目安は 4G で数百 ms。
   - next/font は module 単位で CSS を付けるので、簡単には分けられない。少なくとも `.ai/tasks.json` の decision に、static font（build・WSL 側）の増分と並べて記録する。人の constraint「読み込み負荷を確認」の判断材料になる。

3. **Low — mincho の Shippori Mincho B1 の 400 は、サイトの Shippori Mincho 400 とほぼ同じ字形。mincho の light / regular は develop と見た目がほとんど変わらないのに、静的 font は 5.1MB 増える。**
   - **実測:**
     - glyph の面積（em² 比）: カ 0.1164 / 0.1167、珈 0.2693 / 0.2697、店 0.1873 / 0.1881。差は 1% 未満。
     - Latin の advance は同値（W 1.022、& 0.820）。
     - 差が出るのは bold / black（SemiBold 600 → ExtraBold 800）だけ。
   - **影響:** acceptance「4 つの face がそれぞれ別の日本語書体」は形式上満たしている。ただし「日本語店舗の選択肢を増やす」という目的では、mincho の regular の候補は実質増えていない。
   - B1 を stack に入れる以上、400 は weight matching のために要る（800 だけにすると regular も 800 になる）。
   - **提案:** mincho を develop と違う明朝にするか（候補は Kaisei 系・BIZ UD 明朝など。OFL か要確認）、「mincho は B1 の 800 を得るための選択」と記録して受け入れるかを、人に判断してもらう。

4. **Low — static な日本語書体では light = regular、bold = black になる。editorial_serif の日本語名では、light ↔ regular の修正で頁がまったく変わらない。** DEV-066 の visible の分類では `typography.displayWeight` を visible に数えるので、round を消費しうる（develop から続く問題で、本 PR で悪化はしていない）。
   - **実測（h1）:**
     - light / regular → `*-Regular`、bold / black → `*-Black`（B1 は ExtraBold）。
     - editorial の Latin（Playfair Display）は最小が 400 なので、light も 400 になる。
     - grotesk の Latin（Archivo 100–900）と M PLUS 1 は 4 段階が出る。
   - develop でも Shippori Mincho 400/600・Noto Sans JP 400–600 で、同じ縮退があった。本 PR は bold/black と regular の差を広げており、改善である。
   - 同じ種類の follow-up として、`lib/design-agent/prompts.ts` の語彙がある。「condensed_grotesk (tall, narrow, …)」「light_grotesk (wide …)」は日本語の字形には当てはまらない（日本語の書体はどちらも 1em の固定幅で、`wdth` 軸も無い）。
   - prompts.ts は本 PR の allowed_scope の外。別 task とし、DEV-066 の visibleChanges に「face と名前の文字種で、weight の差が見えるか」を足すかどうかも、そこで判断する。

   - 本 review に、実 font での実測（256 頁・描画 font・advance）を載せた。test の comment が指す先としては、これで足りる。

## Nit

1. `fonts.ts` の comment「at a third of the size of loading all four」は、数字が合わない。
   - 4 段階の weight を 2 つで済ませるのだから、比は半分。Zen Old の全 5 weight と比べても 2/5。
   - 「半分以下」か、実測の MB を書く。
2. `display-faces.test.ts` の weight の検査（`weight: [ … ]` が 2 要素）は、`fonts.ts` の文字列を正規表現で読む。書式が変わると検査が空振りする（0 件でも pass）。
   - 件数（静的な日本語書体 3 つ）も assert すると確実。
   - Medium 1 の修正では、住所の上限も同じ形で固定できる。
3. `subsets: ["latin"]` は `preload: false` では効果が無い。next/font は unicode-range の全 block を出力する。
   - 害は無い。ただ、comment に「subset は preload 用で、日本語はどのみち全 range」と一言あると、22MB の理由が読み手に伝わる。
