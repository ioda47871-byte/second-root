# DEV-037 review

## Cause

- `run.sh --once` runs deliver, then expire, then claim.
- In the Staging PoC, the run meant to deliver job 1's result also claimed job 2.
  - The next worker heartbeat then processed job 2.
  - The next "claim" run only delivered job 2 and printed `claimed none`, so the jobs could not be checked one at a time.

## Change

- `runBridgeOnce` takes `mode: "once" | "deliver-only"` (default `"once"`, unchanged).
  - In `deliver-only` it returns after delivery and expiry.
  - It never sends `action=claim` and never writes a job file to `to-worker/`.
- `bridge.ts` accepts exactly one of `--once` / `--deliver-only` (exit 2 otherwise).
  - In deliver-only it prints the fixed line `claimed none (BRIDGE_DELIVER_ONLY)`.
- `run.sh`: comments only. It still passes the argument through. The env allowlist, user refusal, flock and timeout are unchanged.
- Docs: §6 step 4 of `design-bridge.md` uses `--deliver-only`, the output-code table lists it, and `ARCHITECTURE.md` describes it.
- Unchanged: the token file checks, the HTTPS-only endpoint, spool modes and format, and the server claim / lease / attempts.

## Tests

- `bridge.test.ts` adds 4 tests:
  - With the next job pending on the server, deliver-only delivers, does not claim, and writes no job file. A later `--once` claims it.
  - Deliver-only still expires, and claims nothing.
  - The fixed stops are kept.
  - Argument validation through the real `bridge.ts`.
- The two behaviour tests fail on develop's client (it claims) and pass here.
- `design-bridge.test.ts` (integration, real route and DB): after deliver-only, the second demo stays pending with attempts 0 and job null. A later pass claims it.
