2. **Medium — doc の 1 コマンドは worker の timer を止めて戻す。これは §8.6（timer は禁止）と、HUMAN-017 の「範囲: … timer … には触れない」、doc の「しないこと: … timer … に触れない」と食い違う。そのうえ、中断されると timer は戻らない。そもそも timer を止める必要が無い。**
   - 筋書き:
     1. 比較は最長 58 分以上かかりうる。その途中で、人が端末を閉じるか ssh が切れる（SIGHUP）。
     2. `sudo bash -c '…'` の bash は SIGHUP の既定の動作で終わる。
     3. 最後の `[ "$W" = active ] && systemctl start sr-design-worker.timer` は実行されない。
     4. Ctrl-C でも同じことが起きうる。子が SIGINT で終われば、bash も SIGINT で終わる。
     5. 結果: timer は止まったまま。誰も気づかなければ worker の定期の run が来ない。
   - 失敗の exit code（STOP 20・3、exit 1）なら `; true` まで進むので戻る。戻らないのは中断のときだけ。
   - 止める必要が無い理由:
     - `compare-local.sh` は `run.lock` を取る。
     - timer から起きた run.sh は、lock が取れなければ「another run.sh is running; nothing to do」で exit 0 になる。
     - 先に worker が lock を持っていれば、比較が STOP（exit 3）する。
     - だから timer をそのままにしても、同時には走らない。
   - 直し方: doc のコマンドから timer の stop / start を消す。HUMAN-017 の (3) の「timer は止めて戻す」も消す。
   - 残すなら、`trap '[ "$W" = active ] && systemctl start sr-design-worker.timer' EXIT HUP INT TERM` を入れる。そのうえで、§8.6 との関係（「止めて戻すだけで、enable / 実行はしない」）を HUMAN-017 で人に明示して承認を得る。

## Nit

1. 参照 0 枚の prompt の文言は、次のように読める:
   - brief: 「Attached images: none of the shop (…). The last 2 show the current generic demo」
   - review: 「… The last two are the rendered demo」
   - 添付は demo の 2 枚だけなのに「last」と言っている。意味は通るが、「Two images are attached: …」のほうが正確。RULES の「Use the screenshots only to read mood」とは矛盾しない（「facts と category だけで判断」と言うので）。
2. `photo-prompts.ts` の「the first ${referenceCount} are …」は直していない。比較では写真を使わないので到達しない。将来、写真つきで比較するなら同じ分岐が要る。
3. `.ai/tasks.json` の decision の「PR は未作成（指示）」と、progress.md の「PR なし」が、PR を作った今は古い。
4. doc の「asset store を読み書きしない」は、厳密には違う。`jobPhotos` が、比較の run id（`cmp-…-<key>`）の manifest を asset store から読む（ENOENT なら空）。
   - 書き込みは無く、その id の asset は存在しえない（intake は承認つき）。
   - 正確に言うなら「読むのは比較の run id の manifest の有無だけ」。
5. 安全の検査（`SAFETY_SCRIPT`）について:
   - 大文字と小文字を区別して比べる。`displayCase: uppercase` の頁では、`innerText` が大文字になる。名前が hero にしか無い頁では「欠けた事実」と誤って出うる（安全側の誤り）。
   - 検査そのものが失敗したとき（非 200 など）は `null` になり、report には「–」と出る。NG とは出ない（合計の `safety_ok x/pages` では分かる）。
6. `compare-local.sh` には、run.sh の `MIN_WORKER_SECONDS` に当たる判定が無い。
   - npm ci などで残りが 129 s 以下になると `--budget-seconds` が 10 未満（または負）になり、TS が usage で exit 2 を返す。
   - 0 以下では `timeout` が exit 125 を返す。
   - 安全だが、表示が分かりにくい。

## 対応（2026-10-20、実装者）

- **Medium 1（予算と jail の 3500 秒）**: (a) と (c) の両方。
  - `compare-local.sh` と `compare.ts` の予算の上限を 3300 s にした（design の既定も 3300 s。run.sh と同じ。jail の `RuntimeMaxSec=3500` の中）。
  - 店は、残りが 10 分以上あるときだけ始める（`MIN_SHOP_MS`）。1 店の上限は min(50 分, 全体の残り)。
  - 止まるときも、それまでの report を書く:
    - loop の stop（environment failure・時間切れ）は従来どおり。
    - 例外の catch でも書く。
    - `compare.ts` の signal / watchdog の `stopNow` も、子を止めた後に report（sheet なし、20 s まで）を書いてから exit 1。
  - 止まったとき、shell は report の場所と `compare-report.ts` での作り直しを表示する。
  - doc と HUMAN-017 の「上限 3 時間」を 3300 秒に直した。残りの店は新しい compare id と `--shops` で流せることを書いた。
- **Medium 2（timer）**: doc の 1 コマンドから timer の stop / start を消した。
  - doc の冒頭・「しないこと」・HUMAN-017 に「worker の timer には一切触れない。同時に走らないことは run.lock で保つ」と明記した。
  - timer から起きた `run.sh` は lock が取れずに exit 0 になる。worker が先なら比較は exit 3。
- **Low 1（lock の外の checkout）**: doc のコマンドの事前の fetch / checkout を `flock -n <state>/run.lock` の中に入れた。lock が取れなければ何も変えずに exit 3。
- **Low 2（閲覧の build）**: doc に「worker の checkout では build しない」と書いた。
  - まず contact sheet と `page-*.png` を見る。
  - 実際の頁は `~/sr-design-compare/viewer` の別の clone（report の worker commit に detach）で build / start する。
- **Low 3（compare.ts の直接起動）**: shell が `SR_DESIGN_COMPARE_LOCKED=run.lock` を、lock を持った状態で `compare.ts` にだけ渡す。
  - それが無ければ `compare.ts` は `STOP`（exit 2、何も始めない）。
  - header の直接起動の例は消した。
  - test: 承認の flag があっても直接起動は止まる。shell は token を渡す。
- **Low 4（forbidden_scope）**: 例外として tasks.json の decision に記録した:
  - 変えたのは、参照 0 枚の分岐だけ（DEV-073 の比較専用）。
  - worker からは到達しない。
  - 参照 1 枚以上の prompt は 1 字も変わらない。
  - 既存の snapshot test は無変更で pass。
