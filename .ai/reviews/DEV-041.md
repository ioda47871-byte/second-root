# DEV-041 review

## Cause

- On CI (Playwright 1.62.1, Chromium 151), mode C's `page.close()` sometimes did not settle within 10 s while the page was in a cross-host navigation (127.0.0.1 → localhost).
- DEV-035's bounded close then reported `CLOSE_TIMEOUT`, and the diagnose tests in `browser.test.ts` failed. This happened twice on PR #53 (lines 518 and 544) and twice on PR #56 (518 and 464).
- It does not reproduce locally, where Chromium 141 is installed.

## Change (`lib/design-agent/browser/diagnose.ts`, final, after review 1)

- **`rememberTargetId(page)`:** right after the run opens a page, `runMode`'s `newPage` reads the page's own target id. It uses the page's own CDP session (`Target.getTargetInfo` with no id), then detaches, and is bounded at 2 s, best effort.
- **`closePageBounded(page, ms, closeTarget = closeTargetByCdp)`:**
  - `page.close()` within `ms`, as before.
  - If that does not settle, `closeTargetByCdp(page, deadline)`:
    - uses the remembered id, or reads it from the page's session if none was remembered;
    - sends `Target.closeTarget` for that id on a browser CDP session;
    - polls `Target.getTargets` until Chromium no longer lists the id, up to `deadline` (`ms` later).
  - It judges success by Chromium's own target list, not by Playwright's `close` event. `page.close()` already sends `Target.closeTarget` and waits for that event.
  - It returns `"closed"`, `"target_closed"` or `"timeout"`.
- **Target choice:** never by URL. A remembered id that Chromium no longer lists counts as closed: that is the lost-detach case.
- **Callers:** `runMode`'s `closePage` throws `CloseTimeout` only on `"timeout"`. `CLOSE_TIMEOUT`, `closeBrowser` and `BROWSER_STUCK` are unchanged.
- **Timing:**
  - One page close takes at most 2 × the close timeout (20 s in production), plus up to 2 s at open for the id.
  - Closes take at most about 1 minute per mode.
  - There is no new unbounded wait.
- **Tests only:** `DiagnoseOptions.closeTarget` can replace the targeted close.
- **Unchanged:** the Navigation Guard (the id is read after `guard.newPage()` has set up interception and before `goto`, and reading it enables no domain), challenge / login-wall handling, every stop code, cookies / session, the jail and helper permissions.

## Tests (`tests/unit/design-agent/browser.test.ts`)

- **`closePageBounded` on a real page:**
  - an ordinary close returns `"closed"`;
  - when `page.close()` never settles, it returns `"target_closed"`, the page is closed, and a second page with the same content stays open (exact target);
  - when the targeted close rejects, never settles, or resolves without a close event, it returns `"timeout"` within its bounds.
- **diagnose, `page.close()` never settles and the targeted close works:**
  - `li_offsite` C gives exactly `C STOPPED_OFF_SITE OFF_SITE_OTHER_HOST`;
  - `li_auth_platform` A gives the wall line and then `A SESSION_NOT_CHECKED`;
  - `li_shop` A gives the usual three lines;
  - there is no `CLOSE_TIMEOUT`, the browser ends, and each run stays bounded.
  - With the old close line restored, this test fails with `C CLOSE_TIMEOUT`.
- **DEV-035's "a close never settles" test:** it now also makes the targeted close hang (`closeTarget`), so it still ends with `CLOSE_TIMEOUT` and a bounded browser end. It also checks that `page.close()` was tried.
- `browser.test.ts` passed 63/63 twice locally before review 1; see the review sections for later counts.

## Fresh review 1 (subagent, 8a9669c)

- Critical 0. CI on 8a9669c was all green, including `unit`.
- **High 1 (fixed):** the fallback waited for the same thing `page.close()` waits for.
  - In Playwright 1.62.1, `Page._close` itself sends `Target.closeTarget` and then waits for `_didClose`. The `close` event the fallback waited on comes from that same `_didClose`.
  - So a close that Chromium completed but Playwright never noticed (a lost detach) would still have hung.
  - Now:
    - Each page's target id is read right after the run opens it (`rememberTargetId`, bounded and best effort; if it fails, the id is looked up later from the page's session).
    - The fallback closes that id through a browser CDP session.
    - It counts the page as closed once Chromium's own `Target.getTargets` no longer lists the id, polled up to the deadline. It does not wait for Playwright's event.
  - New tests:
    - a close event that never arrives (`isClosed` always false) still gives `target_closed` from Chromium's list;
    - a page that can no longer be attached to (`newCDPSession` refuses it) is still closed through the remembered id.
  - **Not proven locally:** whether this removes CI's Chromium 151 `CLOSE_TIMEOUT`. Local Chromium is 141, and the tests stub `page.close()` rather than reproducing the race. The fallback covers both possibilities: a hang before Playwright sends its close, and a close Playwright never notices. CI on this PR and later PRs (#56 after merging this) is the evidence.
- **Medium 1 (documented):** worst case.
  - One page close takes at most 2 × the close timeout (20 s in production).
  - One mode is at most about 1 minute: the target page and home page closes plus `closeBrowser`.
  - Stated in `docs/operations/design-browser-wsl.md`. `runDiagnose` has no outer timeout, so this changes timing only.
- **Medium 2 (fixed):** the exact-target test now runs with the first and with the second of two same-content pages stuck. The other page stays open both ways.
- Lows fixed:
  - the CDP sessions are detached without being awaited;
  - no `close` listener is left behind (success no longer depends on the event);
  - "already closed" now returns `"closed"`;
  - added cases: an already closed page, a synchronously throwing closer, a closer that returns false.
- Low noted: the DEV-035 "both hang" e2e test injects a hanging closer, so the production closer's own failure path is covered by the unit cases, not end to end.
