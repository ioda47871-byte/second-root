## Findings

1. **Low (doc accuracy) — the root switch does not gate every path. The doc says "どちらか一方では送らない", which is not true for every path.**
   - `docs/operations/design-bridge-access.md` §5 and `design-worker-cycle.md` say that two places must be written: the `design-bridge.env` lines and `SR_DESIGN_CYCLE_VERCEL_BYPASS=on`.
   - The root switch only gates `cycle.sh`. Other paths read `design-bridge.env` directly, and the two lines alone turn the bypass on for them:
     - `scripts/sales-design-bridge/systemd/sr-design-bridge.service` (`EnvironmentFile=…/design-bridge.env`)
     - the manual run in `design-bridge.md` (`env $(cat design-bridge.env) … run.sh`)
   - §6 step 2 writes the env lines before it writes the switch.
   - Impact is limited. The header still goes only to the configured origin, the bridge token is still required, and §8 row 2 ("design-bridge.env の 2 行を消す") is correct.
   - Risk: an operator who reads §5 may think `SR_DESIGN_CYCLE_VERCEL_BYPASS=off` stops all use.
   - **Suggest:** say that the switch applies to the cycle only, and that the env file is what controls the bridge itself.
2. **Low (human step) — §6 step 2 accepts an empty or mistyped value, and the dry-run still reports OK.**
   - The script writes whatever `read -rs` returned, including an empty Enter or a partial paste. It then appends `SR_DESIGN_CYCLE_VERCEL_BYPASS=on` and runs `cycle.sh --dry-run`.
   - The dry-run checks only the owner and mode (`private_file`, by design it never reads the value). It therefore prints `CYCLE_DRY_RUN_OK` and `vercel bypass: on`, which are the success criteria listed in the doc.
   - The bad value is found only at the first real bridge pass (`BRIDGE_BYPASS_UNSAFE`, or `BRIDGE_PROTECTION_BLOCKED` → `CYCLE_STOP_CLAIM`, phase `before_claim`). This fails closed.
   - The doc's "途中で失敗して空の file が残ったら" implies an empty file only appears on failure.
   - **Suggest:** check the length or shape in the snippet before writing, e.g. `[ ${#v} -ge 16 ] || { echo "value too short" >&2; exit 1; }`. Also say that §7.2, not the dry-run, is the proof that the value works.
3. **Low — `readBypassFile` checks the path with `lstat`, then reads it with `readFile`, which follows links (`vercel-bypass.ts:76-81`).**
   - There is a window to swap the file for a symlink between the two calls. Symlinked parent directories are also followed.
   - Exploiting this needs write access to `sr-designbridge`'s own config directory, which means the attacker already has the secret. `readTokenFile` uses the same pattern.
   - **Suggest (optional, for both files):** `open(path, O_RDONLY|O_NOFOLLOW)` + `fstat` on the handle + read from the handle.
4. **Low (consistency) — 0400 is accepted by the bridge but rejected by the cycle.**
   - `readBypassFile` accepts any mode without group/other bits, and §5 says "0600 か 0400".
   - `cycle.sh` `private_file` requires exactly `600`. A 0400 file therefore stops the cycle with `CHECK_BYPASS_FILE_UNSAFE`. This fails closed.
   - **Suggest:** align the doc to "0600", or relax `private_file` for this file.
5. **Low (test adequacy) — some regressions would not be caught.**
   - **Redaction test (`design-worker-cycle.test.ts`, "a child line with the bypass header is redacted"):** the test value `Vb<30 hex>` already matches the generic mixed-case 32+ character rule. Removing the new `bypass` keyword from `REDACT_PY` would not fail the test. Use an all-lowercase or short value (e.g. `x-vercel-protection-bypass: abcdefghijklmnopqrst`) to pin the keyword rule.
   - **`bridge.ts` happy path:** no test runs `bridge.ts` as a subprocess with a valid bypass. Such a test would check that exactly one extra line `vercel protection bypass in use (configured origin only)` is printed, that the exit is 0, and that the summary line is unchanged (the cycle's exact `summary_of` match depends on that).
   - **Cycle stop path:** no cycle test plays `stopped: BRIDGE_PROTECTION_BLOCKED` from the claim pass to show it ends `CYCLE_STOP_CLAIM phase=before_claim`. `BRIDGE_[A-Z_]+` covers it in `STOP_CODES`, but nothing pins this.
6. **Low (process) — changes outside allowed_scope.**
   - DEV-059's `allowed_scope` is `docs/`, `scripts/sales-design-worker/`, `lib/sales/design-bridge*`, `tests/`, `.ai/`.
   - The PR also changes `lib/design-agent/bridge/{client.ts,vercel-bypass.ts}` and `scripts/sales-design-bridge/{bridge.ts,run.sh}`.
   - These changes are needed to meet the criterion "コードを変える場合は既定で無効…送り先の host を固定". However, the PR touches no `.ai/` file, so the extension is not recorded in `.ai/progress.md` or in the task.
   - **Suggest:** record it there, as DEV-053 did.

## Checked and fine (reviewer)

- **Default off:**
  - Both env vars unset or empty → `loadVercelBypass` returns `null`. Nothing is read, nothing is printed, and `bypassHeaders` gives `{}`. The request headers match the pre-PR ones exactly (authorization + content-type, `redirect: "error"`).
  - With one setting only, the bridge stops before any request (`BRIDGE_BYPASS_NOT_CONFIGURED`).
  - In the cycle, a missing switch or `off` never forwards the vars, even when the env file has the lines (tested). The only output change is the line `cycle: vercel bypass: off`.
- **Host pinning:**
  - The configured origin must equal `new URL(x).origin` byte for byte. That requires https, lowercase, one DNS label under `.vercel.app`, and no port, path, query, fragment, userinfo, trailing slash or trailing dot. It must also equal the API URL's origin.
  - The client checks again that the endpoint origin equals the bypass origin before any request, and attaches the header only on exact origin equality.
  - Probed by hand: `:443`, uppercase, `u@`, `\@evil.com`, `%2e` and `#@evil` in the API URL all normalise (WHATWG) to the same host that fetch will contact. A trailing dot, whitespace or a leading `-` are refused.
  - Redirects are never followed (`redirect: "error"`, plus a real-fetch test showing the redirect target receives nothing). The Production custom domain is refused.
  - The cycle's bash check (`^(https://[^/]+)` == origin) is stricter than the TS check, so every mismatch fails closed.
- **Leakage:**
  - The value is never in an error (`BypassError` carries a fixed code), a log line, argv, or the environment. Only the path and origin pass through `run.sh`'s `env -i` allowlist and `runuser`, and the cycle never reads the file.
  - Fetch errors map to fixed codes. `bridge.ts` prints only codes, and the tests assert that the value, path and origin are absent.
  - `REDACT_PY` adds `bypass` as a key name, on top of the generic rules.
  - There is no xtrace in the scripts.
  - The value rule `^[\x21-\x7e]{16,256}$` after `trim()` rules out header injection (CR/LF). The value must also differ from the bridge token.
- **Shell:**
  - In `cycle.sh`, all new values are quoted. The path regex excludes whitespace and quotes, and the origin regex is anchored.
  - Line counts are enforced (exactly one of each). The root switch accepts only `on|off`, at most one line.
  - `env_text` is unset after the new block.
  - `bash -n` is clean on both scripts.
- **401 classification:**
  - The API's own 401 is exactly `{"error":"unauthorized"}` (`app/api/internal/sales-design/jobs/route.ts:48`). Any other 401, including non-JSON, is reported as `BRIDGE_PROTECTION_BLOCKED`. Both are stops.
  - The existing bridge tests use the exact body and still pass.
- **Doc / Vercel claims:**
  - The header name, multiple secrets per project, project-wide scope, immediate revoke and "not an env var → no redeploy" match Vercel's documented behaviour.
  - The exposure analysis is candid: the bypass opens every protected deployment, including Production `*.vercel.app` URLs, but the bridge token is still required.
  - Not reusing the Operational Claude secret or the `isEnvVar` secret is correct (`SECURITY.md` §1, one secret per caller).
  - §6 step 2 keeps the value off screen and out of argv (`read -rs`, then `printf` is a builtin), refuses to overwrite an existing file, and writes it under umask 077.
  - §7.2 passes the value through the builtin `printf` into `curl -H @-`, so it never appears in argv. It sends no bridge token, so nothing can be claimed.
  - The rollback and revoke steps are correct, apart from the note in finding 1.
- **Forbidden scope:** no Vercel, Supabase, Staging or Production change, no secret created, no timer enabled, and no test weakened.
