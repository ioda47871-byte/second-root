## Findings

1. **High — oldest-first plus `limit 100` hides newly sent outreaches, and with them the only 返信あり button.**
   - Where: `lib/admin/pipeline.ts:73-80` (`loadAwaitingReplies`: `.eq("status","sent").order("sent_at", { ascending: true }).limit(limit)`, `limit = 100`), used by `app/admin/sales/replies/page.tsx:25`.
   - Why it happens: an initial outreach stays `sent` until a reply is recorded. The state machine allows `sent → replied | lost`, but `sales_mark_lost` is offered only by `OutcomeActions`, and that component appears only on the 商談 tab for `replied` / `meeting` items. So unanswered outreaches pile up and never leave the list. `ReplyForm` (返信あり) is rendered only on this list.
   - Failure scenario:
     - At `LIMITS.dailyNewActionable = 5`, about 100 unanswered outreaches build up in roughly 20 sending days.
     - From then on, the 100 rows returned are the 100 *oldest*. Every outreach sent after them is missing from the 返信 tab.
     - A shop replies by email to a mail sent last week. The admin opens 返信 and cannot find the shop, so the reply cannot be recorded (`sales_record_reply` is reachable from no other screen). That blocks the `replied → meeting` flow, and the metrics drift.
     - The header still reads 「返信待ち 100 件」, which hides the truncation.
   - Before DEV-056, `loadPipeline(["sent"])` ordered by `sent_at desc`, so the newest 100 (the ones most likely to get a reply) stayed reachable. This change turns a display tweak into a functional regression after about a month of operation.
   - Fix direction (not applied):
     - Either drop or raise the cap for this list (one admin, small volume), or keep newest-first for the fetch and sort in memory.
     - Show "N 件中 100 件" when truncated, or count with `{ count: "exact", head: true }`.
     - Add an integration test with more than 100 sent rows.
2. **Medium — 「フォロー可能（今日の画面から送れます）」 and 「うちフォロー可能 M 件」 can promise more than 今日 offers.**
   - Where: `lib/sales/followup.ts:62-63` (label), `app/admin/sales/replies/page.tsx:38,84`.
   - Why it happens: 今日 shows at most `LIMITS.workQueue = 5` items (`lib/admin/today.ts:72` `.limit(limit)`, then `selectWorkQueue(..., 5)`), and due follow-ups share those slots.
   - Failure scenario:
     - 8 emails pass day 5 together, for example after a weekend. 返信 shows 「うちフォロー可能 8 件」 and 8 cards say 「今日の画面から送れます」.
     - 今日 lists only the 5 oldest, and no new initials. The other 3 cannot be sent from 今日 until earlier ones are marked 送信済み.
   - The server would *accept* those follow-ups (the RPC rules match), so this is a misleading promise, not a rule mismatch.
   - Suggested fix: reword to 「フォロー可能（今日の画面から順に送ります）」, or mark which items are currently in the 今日 queue.
3. **Low — `waiting` ignores demo visibility.**
   - Where: `lib/sales/followup.ts:52-55`.
   - What goes wrong: an email with a disabled or non-public demo still shows 「フォロー期限まで N 日」 / 「本日フォロー可能になります」. At day 5, the view and `sales_mark_follow_up_sent` will refuse it (`demo_unavailable`).
   - Today this is reachable only by disabling a demo by hand. `disabled_at` is set only by `sales_set_dnc_internal`, and DNC is checked earlier, so the `dnc` label wins. Expiry is sent + 30 days, which is after day 5.
   - A unit test pins the behaviour ("Before day 5 the demo state does not matter yet"). Consider returning `demo_unavailable` whenever `!demoPublic`.
4. **Low — wording: 「フォロー期限まで N 日」 counts down to the *earliest* moment a follow-up is allowed, not to a deadline.**
   - 「期限」 reads as "deadline", so an admin may think the follow-up chance expires after N days.
   - 「フォロー可能まで N 日」 is accurate. If it is changed, `docs/MVP_SPEC.md` §5 uses the same phrase and needs the same edit.
5. **Low — the purpose line in `.ai/tasks.json` mentions 「返信ありで次の操作がない項目」, and the 商談 tab only adds an elapsed-day badge.**
   - It keeps the existing `sent_at desc` order and does not highlight stale `replied` items.
   - The acceptance criteria require only the elapsed days, so this is not blocking. Record it as a known gap or follow-up.
6. **Low — when there is no demo row at all, `demoPublic` is false and the label says 「デモ公開終了のためフォローなし」 ("ended").**
   - This should be unreachable for a sent outreach, because `sales_mark_sent` requires a demo.

## Checked and fine (reviewer)

- **JST day math:**
  - `jstCalendarDaysBetween` diffs `jstDate()` strings parsed as UTC midnights, so the result is an exact multiple of a day and `Math.round` is safe. With no DST, the fixed +9h offset is exact.
  - 23:59:59 → 00:00 JST gives 1, and crossing a UTC date inside one JST date gives 0. Month and year ends and foreign DST changes are covered by tests.
  - `daysLeft` uses JST calendar days to `sent_at + 5d`, and 0 maps to 「本日フォロー可能になります」, which is correct on the due date before the due time.
- **`due` vs the server rules:**
  - `due` requires `isFollowUpDue` (`sent_at <= now - 5d`, email, `sent`, no sent follow-up, not DNC) plus `isDemoPublic` (`disabled_at null`, `expires_at` not null, `keep_alive || now < expires_at`).
  - That is the same predicate as view `sales_followup_due` (20260927000500) and the checks in `sales_mark_follow_up_sent`. The integration test compares against the view directly.
  - I found no case where the UI says `due` and the RPC refuses, or the reverse, apart from render-to-click time drift.
  - The `sent` state is detected the same way the view and RPC detect it (`kind = 'follow_up' and status = 'sent'` per prospect; the unique index allows one per shop).
- **Queries:**
  - It is one extra query, not N+1: `.in("prospect_id", ≤100 ids)`. At most one follow-up per prospect means at most 100 rows, under PostgREST `max_rows`.
  - The `sales_demos` embed is one-to-one (`prospect_id unique`), and the array/object shape is handled.
- **RLS / admin-only:** both queries use the admin's own session (`createAuthClient`), and the page calls `requireAdminPage()`. The integration test shows a signed-in non-admin gets `[]` from both loaders.
- **No state changes:**
  - There is no new RPC, migration, transition or DNC change. The page renders only server data and existing actions.
  - The e2e test asserts that viewing creates no follow-up row and changes no status.
- **PII:** only shop name, channel, dates and fixed labels are shown. No email address, message body or free text is added.
- **Mobile:** badges use the existing `.badges` (flex-wrap) and `.badge` / `.badgeWarn` styles, with short labels and no fixed widths.
- **Docs:** the MVP_SPEC §5 and §8 lines match the behaviour, apart from wording finding 4.

### Paging checks

- **Termination:** a page with fewer rows than the page size ends the loop. An exact multiple costs one extra, empty request.
- **RLS and short pages:** RLS and the `!inner` join filter rows before `LIMIT`/`OFFSET`. So a short page can only mean the end of the result.
  - A non-admin gets an empty first page and stops.
  - Stopping on a short page is correct as long as the server returns the full page size; see Low A.
- **Query cost:**
  - The 返信 tab makes ⌈sent / 500⌉ + ⌈sent follow-ups / 500⌉ requests, which is 2 requests at MVP volume.
  - The follow-up query now reads every sent follow-up rather than the ones for listed prospects. That is at most one per shop, so it stays small.
  - `sales_outreaches_status_idx (status, kind)` serves both filters.
- **No regressions found:**
  - The only callers are the 返信 page (`loadAwaitingReplies`) and the 商談 page (`loadPipeline` plus `byStageAge`).
  - There are no new RPCs, migrations, transitions or DNC changes.
  - The e2e check that the page shows no send action uses the real 今日 label 「フォローメールを作成」 (`app/admin/sales/page.tsx:28`), so it is not a no-op.

### New findings

- **Low A — `readAll` stops early if the server's `max_rows` is set below the page size** (`lib/admin/pipeline.ts`, `readAll`).
  - PostgREST quietly caps `.range(0, 499)` at its `max_rows`. If Staging or Production ever set `max_rows` below 500 (for example 100), the first page would come back short and the list would be cut off without any sign. That is the same symptom as the original High.
  - The local config and the hosted default (1000) are safe. Hardening options: stop only on an empty page, or request `count: "exact"` and compare against it.
- **Low B — offset paging is not a snapshot.**
  - Above 500 rows, a reply recorded or an outreach sent between two page requests can shift rows across a page boundary. One row could then appear twice, which would give a duplicate React key, or be skipped for one render.
  - New sends land at the end of the oldest-first list, so the 返信 tab is mostly immune. At MVP volume everything is a single page.
  - This is informational. Keyset paging on (`sent_at`, `id`) would remove it.
