## カードの表示 (節ごと)

1. **選んだ理由 (保存された項目から)**: 一文の要約 (例「名古屋市中区のパン屋。公式サイトが見つからず、推奨チャネルはInstagramの候補。」。送れるかどうかは書かない: review L3) と、地域・業種・公式サイト (あり(domain) / 見つからない(登録時に再検索済み) / 未確認)・推奨チャネル・メールの出所・Instagram。**改善の仮説は保存された列が無いので常に「未確認（保存されていません）」**。作った理由は書かない。
2. **出典**: 調査日 (`verified_at` の JST の日付、範囲なら `2026/10/01〜2026/10/03`)・登録日 (prospect の `created_at`)。行ごとに項目名・値 (80字で省略)・出典の種類・店舗自身か・日付・「出典を開く」(安全な http(s) のときだけ、`target=_blank rel="noopener noreferrer nofollow"`。サーバーは fetch しない)。店名・住所・業種・チャネルの項目 (email / instagram_url) で出典の無いものは「出典未確認: …」。
3. **連絡の可否**: チェックごとに OK / NG / 未確認 と理由。送る前に人が見ること (Instagram: プロフィールの「DM不可」「営業お断り」、メール: 出典ページの「営業お断り」) を未確認として常に表示 (送信可否は変えない。MVP_SPEC §4.1)。

## 送信の可否とサーバーの一致

`contactVerdict` のチェックは、送信済みにするときにサーバーが断る条件と1対1:

| check | サーバー側 |
|---|---|
| `outreach_state` | `sales_mark_sent`: initial かつ drafted / `sales_mark_follow_up_sent`: email の送信済み (5日・デモ公開はキューが判定済み) |
| `dnc` | `sales_assert_outreach_eligible`: `do_not_contact` |
| `recommended_channel` (initial) | 同: `recommended_channel is distinct from channel` |
| `channel_rule` | 同: instagram は `website_status = not_found`・handle あり・公開メールなし / email は公開メールと `sales_has_first_party_email` (field=email、`lower(value) = public_email`、第一者の source_type) |
| `design` (initial、AIデザインの step が ON のときだけ) | `markSent`: `initialSendAllowed` (pending / processing を拒否) |
| `target` | DB の check 制約 (名古屋市・3業種) を `checkTarget` (`lib/sales/eligibility.ts`) で表示 |

UI だけの上乗せ (どちらも厳しくする方向、`serverEnforced: false`):

- `demo_link`: デモが無い・無効なら文面を作れない (従来も操作は出なかった)。
- `exclusion`: 除外リストに一致 (persist は一致を拒否済みなので、作成**後**に登録された除外)。MVP_SPEC §3.5.1 は「既に営業準備済みの店舗には触れない」なので、DB の送信済み判定は除外を見ない。カードは送信不可にし、見送り / DNC を促す。照合のキーの種類は persist と同じ4つ (handle・domain・メールの digest・正規化店名+住所)。ただしメールは、persist が見る「候補が提出したメール」(第一者でなくても) は保存されていないので、保存されている `public_email` と `field = 'email'` の出典の値を正規化して digest したもので照合する (review L2)。一覧を読めなければ「未確認」= 送信不可 (§3.6 の fail-closed)。

`sendable` は全チェックが OK のときだけ true。null・読めない値は「未確認」で送信不可。テストは各サーバー規則を1つずつ破った入力で `sendable=false` を確かめ、ミラーしている SQL の文字列が migration に残っていることも確かめる (SQL が変わればテストが落ちる)。

## 読み取りの経路

- すべて `createAuthClient()` (admin のセッション) と既存の `requireAdminPage` / `requireAdmin` のまま。service role は使わない。`sales_sources`・`sales_exclusions` はどちらも admin read の RLS と `authenticated` への select の grant が既にある。
- メールの digest はサーバー (`lib/admin/today.ts` は `server-only`) で計算し、DB には何も送らない。除外リストの label / note は読まない (reason だけ)。

## CI `e2e-sales` の失敗 (c90e29d) と対応

- 原因: `tests/e2e/today.spec.ts:39` の `card.getByText("Instagram")` が、折りたたみの根拠 (推奨チャネル・Instagram の行・出典の種類・チェックの文) にも当たり、strict mode で7要素になった。同じ理由で `card.getByText("未送信")` も「未送信の下書き」(下書きの状態のチェック) に部分一致する。
- 対応: `TodayCard` のチャネルと状態のバッジに `data-testid="channel-badge"` / `"state-badge"` を付け、spec はそのバッジを直接見て `toBeVisible()` と `toHaveText("Instagram")` / `toHaveText("未送信")` を確かめる (意味は同じで、完全一致になった分むしろ厳しい)。
- ほかの `today-item` を見る spec (`email-send`・`follow-up`・`instagram-send`・`mobile-qa`) を DOM から確かめた: どれも role + 名前 (「メールを作成」「フォローメールを作成」「DMを送る」「送信済み」) か `hasText` の店名で当たり、根拠の欄にはその名前のリンク・ボタンも店名も無い (出典のリンクは「出典を開く」、要約に店名は入れていない)。`today.spec` の「詳細」は送信可のカードでは要約の `<summary>詳細</summary>` だけ (案内文の「詳細」は送信不可のカードにしか出ない。seed の Instagram / メールの下書きはどちらも送信可の条件を満たす: not_found・handle・推奨 instagram / present・第一者の出典・推奨 email)。メールの長文で mailto を作れないケースは送信可の判定のあとに従来の `cannotCompose` の alert が出るので変わらない。`mobile-qa` は details を全部開いて 320/375px のはみ出しを測るが、根拠の欄は `overflow-wrap: anywhere` で、店名 (LONG) は根拠の欄に出ない。
- e2e はローカルで実行できない (Docker daemon が無く Supabase を起動できない)。`npx playwright test --list tests/e2e/today.spec.ts` で 10 件が読み込まれることだけ確かめた。CI の `e2e-sales` で確認する。
