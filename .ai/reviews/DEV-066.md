## Findings

1. **Medium — retry の後に `leader.score` を上げると、leader と final の選び方がずれる。受け入れられた候補を捨てて BLOCKED になり、修正も 1 回分失われる。**（`lib/design-agent/pipeline.ts`、`if (base.name === leader.name && retryTotal >= leader.score) leader = { ...leader, score: retryTotal };`）
   - **現状:**
     - final の選択は `candidates`（各候補の初回の review の score。tie は後の候補）で行う。leader の score を上げても、`candidates` は更新しない。
     - 既存の DEV-034 の second look（`again`）は、leader の score を上げない。だから「leader = final と同じ規則」が保たれていた。
   - **再現（一時 test で確認）:**

     | 順 | review | total | verdict | 備考 |
     |---|---|---|---|---|
     | 1 | c0 | 18 | revise | revised は direction だけ |
     | 2 | c0 の retry | 19 | revise | visible な修正を返す。leader.score = 19 |
     | 3 | c1 | 18 | revise | leader.score が 19 なので leader は c0 のまま |
     | 4 | c0 の again | 20 | accept | `REVISION_FROM_BEST_2` → break |

     - final は `candidates` で c0 = 18、c1 = 18 の tie なので c1 になる。c1 の最新 verdict は revise なので `QUALITY_NOT_ACCEPTED`。
     - 実測: `notes ["REVISION_NOT_VISIBLE_1","REVISION_FROM_BEST_2","QUALITY_NOT_ACCEPTED"]`、`final "candidate-1"`、`status "blocked"`。
     - c0 は accept されたのに出荷されない。更新が無ければ、leader は c1（18 ≥ 18）。c1 から修正して c2 を作れたはずの 1 回も失われる。
     - prompt の `best` 行も、c0 の 19 を伝える。final の規則が使う 18 とは食い違う。
   - **gate を緩める方向には働かない。** final の選択と gate は `candidates` と最新の verdict を読むので、update が accept を増やすことは無い。害は、無駄な BLOCK と修正の損失。
   - **提案:** この行を削除する（second look と同じく、retry の score は leader に反映しない）。もし反映したいなら、`candidates` の score も同じ規則で更新し、final の選択と一致させる。削除したうえで、上の筋書きを test に入れる。

2. **Medium — `palette.surface` は写真の無い page で何も描かないのに、visible に分類されている。** 本 PR が防ぐ「同じ page を描いて round を使う」が残る。（`lib/design-agent/visible-profile.ts`、`prompts.ts` の語彙）
   - **現状:**
     - `--p-surface` を読む CSS は `.photo { background: var(--p-surface) }`（`profile.module.css` l.621）だけ。DemoFrame・他の CSS にも参照は無い。
     - 写真無しの pipeline では、surface の変更は screenshot に出ない。
     - 語彙は `surface = panels` と書いたまま。これは DEV-066 が正す対象の「事実でない語彙」と同じ種類の誤り。
   - **失敗シナリオ:**
     - review が revise で、revised_profile は `palette.surface` だけを変える（「panels を暖かく」）。
     - `visibleChanges` が `["palette.surface"]` を返し、candidate-1 として描かれる。
     - 同じ page が review され、修正 1 回分を使う。DEV-066 以前と同じ損失。
   - **提案:**
     - 写真無しの run では、`palette.surface` を NOT_IN_SCREENSHOTS 側に置く（visibleChanges に写真の有無を渡すか、写真無し用の一覧を持つ）。
     - 語彙の surface の説明を事実に合わせる（例: 「photo frames only; nothing else uses it」）。
     - `notVisibleLine` の列挙も同様に直す。
     - 「すべての schema の設定が分類済み」の test は、分類の正しさまでは見ていない。surface が見えないことを固定する test を足す。

3. **Low — 場合によっては見えない設定が、常に visible と数えられる。**（`visible-profile.ts`）
   - 判定は保守的に「visible」側へ倒れるので、品質基準には影響しない。ただし round の空費は残る:
     - `palette.accent`: 使うのは次の 4 つだけ。どれも無い profile では accent の変更は描かれない。語彙の「accent = monogram」も誤り（`.monogram` は `--p-primary`）。
       - `location_labels` の 2 個目以降の区切り
       - `dot_grid`
       - `stamp_ring`
       - `muffin_paper_svg`
     - `motifs` の `monogram`: `stamp_ring` があると描かれない（`motifs.has("monogram") && !motifs.has("stamp_ring")`）。
     - `typography.displayCase: uppercase`: 店名が日本語だけなら変化が無い。
   - **提案:** 最低限、語彙の accent と monogram の記述を事実に合わせる。判定への反映は DEV-067 以降でもよい（blockers に記録）。

4. **Low — not-visible の retry が `again: true` で記録され、DEV-034 の second look と区別できない。**（`record(base.name, retry, true)`）
   - report.json の `codex.rounds` だけを見ると、retry と second look が同じ形になる。区別できるのは notes と file 名（`review-<c>-not-visible-<n>.json`）だけ。
   - 次の controlled run の分析では、retry の頻度が知りたい数字になる。
   - **提案:** `notVisible: true`（または `kind: "not_visible"`）を round に足す。review-summary は非 strict なので互換性に問題は無い。

5. **Low — test の穴。**（`tests/unit/design-agent/pipeline-visible-revision.test.ts`）
   - 次の場合に test が無い:
     - revise from best の後の not-visible（base = leader、file 名 `review-candidate-0-not-visible-2.json`、比較元が leader の profile であること）
     - Medium 1 の筋書き
     - retry の各終わり方: `needs_renderer_change` → blocked、`revised_profile: null` → `NO_REVISED_PROFILE`、invalid → `REVISION_INVALID_n`
     - retry の失敗: `CodexError`（環境系 → `environment_failure`）、`DeadlineError` → `REVISION_NOT_VISIBLE_NO_TIME`、schema 不正 → `REVIEW_INVALID_<c>_NOT_VISIBLE`
     - 最大 review 数（6）の筋書きで、`buildReviewSummary` が `rounds: 6` を返し、DB の上限内に収まること
   - **提案:** 最低限、Medium 1 と「revise from best + not-visible」と「最大 review 数」を足す。

6. **Low — retry の accept が gate を通る（既存の second look と同じ性質）。**
   - retry は、直前に revise と言われたのと同じ screenshot をもう一度見せる。そこで accept が返れば、最新の verdict として出荷される。
   - 規則は変わっていない。DEV-066 以前でも、見えない修正は同じ page を candidate-n として描いて再 review していたので、同じ page の再判定 1 回は従来もあった。retry の文面は「visible な revised_profile を出せ」と求めており、accept を誘導しない。
   - ただし、1 run あたりの review 数の上限は 4 から 6 に増える。verdict の揺らぎで accept を引く機会も、わずかに増える。
   - **提案:** 意図した性質として DEV-066 の decision か pipeline の comment に明記する。より厳しくするなら、retry の verdict は記録だけにして gate の「最新」には数えない案もある（人の判断）。

### Nits

- N1 — `review-summary.ts` の `REVIEW_MAX_ROUNDS` の comment（「the first, 2 revisions, a second look at the best after each」）に not-visible の retry を足す。最大は 6 で、10 の範囲内。
- N2 — `base.name === leader.name` は常に真。base は current（= leader）か leader なので、条件は冗長。Medium 1 で行ごと消えるなら不要。
- N3 — 写真 pipeline（`photo-pipeline.ts`）には visible check が無い。語彙の 3 行は写真の prompt にも入るが、事実なので問題は無い。写真側への展開は範囲外で、blockers に一言残すとよい。
- N4 — 修正が、以前に描いた別の候補（例: 低かった c1）と visible に同一でも検出しない。同じ page を再び描きうる。頻度は低い。

## 確かめて問題なかったこと（reviewer）

- `direction`（`data-direction`）と `heroLayout.alignment`（`data-align`）を読む CSS・TSX の分岐は無い。`tokens()` も palette だけを読む。
- motion は、`@media (prefers-reduced-motion: no-preference)` の中の animation だけで使われる（`both` fill。初期の opacity も、この media の中だけ）。
- shot は通常の review も写真の review も、`screenshotPage` で撮る。どちらの shot も `reducedMotion: "reduce"` なので、motion は screenshot に一切出ない。
- confidence と rationale は描かれない。
- `composition.grid` は 720px 以上で効く。desktop の shot は 1440px なので、visible の扱いは正しい。infoStyle・divider・spacing・typography の各値には、CSS の分岐がある。
- motifs は renderer が `Set` で扱うので、順序を無視する判定は正しい。重複は `checkProfile` が拒否する。
- palette は hex の大小を区別しない比較で、正しい。
- `.ai/tasks.json` の DEV-066 について:
  - allowed_scope（`lib/design-agent/`・`tests/unit/design-agent/`・`.ai/`）は、変更した file と一致する。
  - forbidden_scope（閾値・gate の緩和、DB、flag、Production）にも触れていない。

## 対応（実装者、merge 前）

- Medium 1: 追加の review の後で leader の score を動かす行を削除（second look と同じく、leader と final は最初の score で選ぶ）。指摘の筋書きを test に（c0 18 → もう一度 19 → c1 18 は c1 が leader、c0 の second look は起きない）
- Medium 2: `palette.surface` は写真の無い頁では見えない設定として扱う（`visibleChanges(..., { photos: false })`、この loop は写真なし）。語彙も「写真の下地。写真の無い頁には出ない」に
- Low: accent は accent で描く motif（location_labels・dot_grid・stamp_ring・muffin_paper_svg）が前後どちらかにあるときだけ数える。語彙の「accent = monogram」を訂正（monogram は primary）。追加の review は round に `notVisible: true`（`again: true` も付けたまま、履歴では second look として出る）。test を追加: revise-from-best の後の見えない修正、追加の review の各終わり方（renderer change・null・不正な答え・CodexError）
- Low（追加の review の accept）: second look と同じ扱い（gate は最新の verdict を読む）。この PR の前は同じ頁を candidate として描き直して review していたので、accept の機会は増えていない（review の回数の上限は 4 → 6）。人の判断が要るときは blockers に記す
- Nit: REVIEW_MAX_ROUNDS の comment を更新。常に真の条件は行ごと削除。photo loop の見える確認・以前の低い候補と同じ修正の検出は対象外（blockers に）
