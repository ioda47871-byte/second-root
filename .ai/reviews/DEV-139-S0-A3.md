### M1 — The direction is not bound to the generation; a d2 design input is accepted with a d1 generation
- Where: scripts/sales/demo-version/from-generation.mjs:85-90 (pin.json is checked only against the CLI's own
  --facts/--directions/--direction-id) and :103 (the receipt is checked only against --expected-prompt-sha256).
  Nothing ties pin.json / design-input/direction.json to the prompt SHA. pin.json has no prompt SHA, and the result
  file does not record which --direction the packaging step was given.
- Failure scenario (reproduced in a scratch copy of the test, not committed): prepare-design-input for
  `d2-chain-links`. Then run the glue with `--design-input <d2> --direction-id d2-chain-links` and keep the d1
  generation, artifact and result plus d1's prompt SHA. It is NOT refused. It runs from-prototype, the copy audit
  and the PC/SP render, then stops at VISUAL_REVIEW_MISSING (exit 1). status.json records `direction_id:
  d2-chain-links` next to a generation made from the d1 prompt. The owner instruction asks for 2 directions per shop
  (6 runs), so the inputs of two directions of one shop will sit side by side. Facts and shop checks cannot catch a
  swap between them, and the docs table says "同じ方向案・同じ方向 ID" as if it were checked against the generation.
- Fix: bind the direction to the prompt SHA. Options: (a) with owner approval, let the glue rebuild the v2 prompt
  from facts + design-input/direction.json + references.json (phase2f/prompt) and require it to equal the receipt
  SHA. This widens the phase2f isolation allowlist, so it needs approval. (b) Have the packaging step's result record
  the SHA of the direction/references it used, and have the glue compare it with design-input/direction.json and
  references.json. This also changes phase2f-steps. (c) At minimum, record the printed pin (prompt SHA) in the
  design-input dir, check it in the glue, and mark `direction_prompt_binding: "operator_supplied"` in status.json.
  Correct the docs table either way. Add a refusal test for the swap.
