## Findings and responses

1. **Medium — `name_address` memory rows were never used for matching, and `no_eligible_channel` produced only such rows.** These rows were dead data holding names and addresses (possibly private homes) for 90 days.
   - **Fixed (3f0c93f):**
     - The `name_address` key type is removed from the table check, the SQL function, the TS code and the tests.
     - `no_eligible_channel` is no longer a durable reason.
     - The memory now holds only the Instagram handle and the website key, and only for `site_without_email`.
     - The docs (MVP_SPEC §3.5.2, ARCHITECTURE, SCHEDULE) state exactly what is stored and matched.
2. **Low — the screening oracle was understated in SECURITY.**
   - **Fixed:** SECURITY §3.3 now compares the two oracles. Discovery screening is cheaper and silent: up to 20 keys per request, repeatable, no side effects. But it does not say which list matched. Persist does say which list, but it is capped and leaves a visible prospect.
   - Kept as an accepted residual.
3. **Low — one bad key made the whole `sales_remember_rejections` call fail silently.**
   - **Fixed:**
     - TS validates each entry with the table's rules before sending (`isValidMemoryKey`, `validMemoryEntries`, at most 10 entries).
     - SQL skips a bad entry per key (`check_violation` / `not_null_violation`) instead of aborting the batch.
   - Tested in unit and integration.
4. **Low — a submission mistake could become a 90-day memory.**
   - **Fixed:** `site_without_email` is remembered only when no email was submitted at all. A wrong sourceType, another site or another subdomain is not remembered.
   - Tested.
5. **Low (process) — the integration suite had not been run on this branch's schema.**
   - **Response:** the coordinator ran it after `supabase db reset`:
     - ad32f21: 297 passed.
     - 3f0c93f (after the fixes): 299 passed, including `discovery-screening` with the new skip and email tests, db-security-audit and staging-checks.
     - e2e: 80 passed on ad32f21. The UI is unchanged since.

## Checked and fine (reviewer)

- **Key parity:** matching uses the same `parseInstagramProfile` handle and `websiteKey` as prepare / persist, with exact equality. No name or ward matching, so no new false-known path.
- **Leakage:** only keys are returned, never a reason or a list. A terminal or unknown run returns no new marks, and the timing difference is negligible.
- **Memory:** a key is recorded only if the run's checkpoint really rejected it for that reason. Writes are idempotent upserts, and expired rows are ignored and pruned. There is no email column.
- **Security:** RLS is on with an admin-read policy. Grants are explicit for Staging, and the functions are SECURITY INVOKER with `search_path=''`. The functions are service_role only and covered by the audit.
- **`sales_run_state`:** identical to the prior definition apart from `known_keys`, and the ACL is kept.
- **Fail-open screening:** a failure never blocks a run or loses checkpoint data, and persist stays the final authority.
- **API:** changes are additive, and the strict schema stops Op Claude from setting `known`.
- **RUN_PROMPT:** keeps every safety rule. `site:instagram.com` is an ordinary web search, so there is no new scraping surface.
- **Staging:** migration order and grants are fine.
