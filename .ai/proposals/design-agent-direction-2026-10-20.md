# AI デザインの方向の点検と設計変更の提案（2026-10-20）

人の問い（2026-10-20）: 目指しているのは「GPT/Codex が店舗の Instagram や参考画像を分析し、店舗ごとに独自のアートディレクションと Web デザインを考え、それを Claude 側が実際に動くサイトとして実装する仕組み」。既存テンプレートの色・フォント・レイアウトを AI が選ぶだけのシステムにはしたくない。今の開発がどれだけずれているかを率直に。

制約（変えない）: 画像生成 AI で架空の店舗写真を作らない・Instagram の写真を無断で転載しない・事実を創作しない・既存の安全対策と品質ゲートを保つ・実走 / Production / 営業送信は承認なしに行わない。

## 0. 結論（率直に）

**今の仕組みは、構想の「AI が既存テンプレートの設定を選ぶ」側にある。** 構想とのずれは大きい。

- Codex は「アートディレクター」と呼ばれているが、実際にしていることは、固定の 1 枚の頁（節の順・見出し・文言が固定）について、列挙された設定値（約 3.7 億通り × 6 色）から 1 組を選ぶこと。HTML / CSS も節の構成も、Codex は一切決めていない（DEV-028 で意図して決めた設計: 「Codex は語彙から選ぶ。文言・HTML・CSS は書かない」）。
- 「Claude 側が実装する」部分は、**実行時には存在しない**。Claude が書いたのは開発時の共通 renderer（`ProfileRenderer` + `profile.module.css`）で、店ごとの実装は 1 行も無い。worker の実行時にいるのは Codex だけ。
- DEV-066〜069 は「選べる値が実際に見た目を変える」ようにする改善で、品質の底上げにはなるが、**方式そのもの（パラメータ選択）は変えない**。2026-10-20 の実走が 18/25（brand_fit 3・generic_template_feel 3）で止まったのは、この方式の天井にかなり近い。

ずれた理由（経緯）: DEV-028 の時点で、公開ページに AI が書いた HTML を出す危険（XSS・事実の創作・崩れ・注記の隠蔽）を避けるため、「安全に検査できる範囲」を優先した。安全側の判断としては正しかったが、構想の中核（店ごとの独自デザイン）を後回しにしたまま、その上に運用（bridge・cycle・flag・gate）を積み上げてきた。

## 1. Codex が今、店ごとに決められること

| 決められる | 範囲 |
|---|---|
| direction | 10 種（DEV-067 で見た目が付く。それまでは名前だけ） |
| 色 | 6 色の hex（自由。contrast の規則つき） |
| 書体 | display 4 種・本文 2 種・大文字化・太さ 4・字間 3（DEV-068 で日本語も 4 書体） |
| hero | 配置 3 × 高さ 3 × 揃え 2（揃えは DEV-067 で効く） |
| 構成 | grid 3・情報の見せ方 3・区切り 4・余白 3 |
| 飾り | 7 種から 4 つまで（monogram・地名ラベル・紙カップ線・枠・点・スタンプ・トンボ） |
| 動き | 4 種（審査の screenshot には出ない） |

組み合わせは約 3.7 億通りだが、**どれも同じ骨組みの上の着せ替え**。

決められないこと:
- 節の有無・順序・数（お知らせ帯 → hero → About → Menu → Visit → 注記、で固定）
- 節ごとの組み方（hero 以外は grid と情報の見せ方の 2 つだけ）
- 見出しの言葉（About / Menu / Visit と固定の日本語）・hero の英語の分類ラベル
- 新しい部品（例: 看板商品の大きな扱い、営業時間の帯、地図風の案内、縦書きの店名、ロゴ風の文字組）
- 店ごとの装飾の造形（飾りは 7 種の固定の形だけ）
- 写真（DEV-029 は人が入れた写真だけ。Instagram 写真は使わない方針）

## 2. Claude 側の renderer で再現できないデザイン要素

構想どおりに Codex が自由に考えた場合に、今の renderer では出せないもの:

1. **構成**: 節の並べ替え・統合・分割、1 画面目の構成（店名以外を主役にする、事実の一部を大きく見せる）、雑誌の見開き風・帯状・カード状などの節ごとのレイアウト
2. **文字組**: 縦書き（日本語の店名・見出し）、店名の字ごとの大きさ・重なり・回転・ロゴ風の組、見出しの書体を節ごとに変える
3. **造形**: 店ごとの罫・枠・地紋・図形（例: 店の雰囲気に合わせた幾何学パターン）、色面の大きな分割、斜めの区切り
4. **質感**: 紙・布・木などの地（今は direction の固定の 1 種だけ）
5. **動き**: 審査に出ないので実質ない（これは問題ではない）
6. **写真**: 無い（方針として Instagram 写真は転載しない。架空の写真は作らない）。→ 写真なしで魅力を出す手段（文字組・色面・図形）がより重要になる
7. **言葉**: キャッチコピー・見出しの言い換えは不可（事実の創作の禁止）。これは構想でも守るべき制約で、変えない

## 3. 頁の構成やレイアウトも店ごとに変えられる設計へ発展できるか

できる。安全性を保ったまま段階的に広げる道が 2 つある。

- **(B) 構成の仕様化**: Codex が「節の一覧と順序・節ごとの組み方・文字組・飾りの指定」を JSON の仕様で書き、renderer がそれを組み立てる。部品の数を増やすほど自由度が上がる。HTML は今までどおり Claude が書いた部品だけ。
- **(C) 店ごとの CSS（と限られた構造）を生成**: 事実だけでできた固定の意味構造（HTML）の上に、店ごとの CSS を生成する。CSS は構文解析して許可した性質・値だけを通す。見た目の自由度は (B) よりはるかに大きい。

「店ごとの HTML を丸ごと生成する」方式（D）は、事実の創作・注記の隠蔽・XSS の検査が難しく、公開頁（`secondroot.jp/demo/...`、本サイトと同じ origin）に出すには危険が大きいので、勧めない。

## 4. 方式の比較

| | A. 今（設定の選択） | B. 構成の仕様化 + 部品 | C. 固定の意味構造 + 店ごとの CSS 生成 | D. 店ごとの HTML/CSS を丸ごと生成 |
|---|---|---|---|---|
| 店ごとの独自性 | 低い（同じ骨組み） | 中（部品の数しだい） | 高い | 最も高い |
| 品質の安定 | 高い | 高い | 中（生成の当たり外れ、検査で抑える） | 低い〜中 |
| 事実の正確さ | 守れる（文言は事実だけ） | 守れる | 守れる（文言は HTML 側で固定、CSS は文字を足せないよう検査） | 難しい（生成文の検査が要る） |
| 安全（XSS・注記の隠蔽・外部読み込み） | 強い | 強い | 検査で守れる（CSS の許可リスト・url() 禁止・content 禁止・注記の位置と見え方の機械検査） | 弱い（script・iframe・偽フォーム） |
| 検査のしやすさ | 高い（今の test） | 高い | 中（Chromium での機械検査を増やす） | 低い |
| 開発費（Claude の作業） | 済み | 中（部品の設計と実装、数週間分の DEV） | 中〜大（CSS 検査器・生成の prompt・評価） | 大 |
| 実行時の費用 | Codex 3〜6 回/店（ChatGPT サインイン、追加の課金なし） | ほぼ同じ | Codex の呼び出しが 1〜3 回増える（出力が長い）。Claude を実行時に使うなら Claude Code のサブスクリプションの使用量（WSL の jail にすでに Claude Code がある）。API キーは使わない方針のまま | 大きい |
| 実行時間 | 約 10〜20 分/店 | ほぼ同じ | +数分 | +10 分以上 |

**推奨: B を土台にしつつ、C を local preview で試し、効果を測ってから公開に進める（B → C の段階的な移行）。** D は採らない。

役割の分担（構想に合わせる）:
- **Codex（アートディレクター）**: 参考画像（ぼかし済み）と測った色から、コンセプト・トーン・構成・文字組・色・造形の**仕様**を書く。仕様は schema で検査できる形にする。
- **Claude（実装）**: 開発時に部品・組み立て・検査器を作る（B）。C の段階では、**実行時に仕様から店ごとの CSS を書く役も Claude にできる**（WSL の jail の Claude Code。生成物は検査器を通ったものだけを使う）。または Codex に書かせて Claude 側の検査器が通す、のどちらでもよい（品質と費用を比べて決める）。
- **Codex（審査員）**: 今と同じ 5 軸・同じ基準・同じゲートで審査する。

## 5. 段階的な開発計画（案）

各段は今までどおり: 設計 → 実装 → test → Fresh Review → CI → develop。実走（controlled run）は人の承認ごと。品質ゲートは変えない。

- **段階 0（今）: DEV-067〜069 を仕上げる**（見えない設定を無くす・日本語書体・色の測定）。設定選択の天井を測る基準にもなる。1 回の controlled run で 18/25 からの変化を見る（人の承認が要る）。
- **段階 1: アートディレクションの仕様（Design Spec v2）**
  - Codex の出力を「profile」から「仕様」に広げる: コンセプト（短い言葉、記録だけで頁には出さない）・節の構成（固定の節の種類から選んで並べる。各節は使う事実を宣言し、事実が無い節は出せない）・節ごとの組み方（部品ごとの 3〜5 種）・文字組の階層（大きさの比率・縦書きの可否）・造形の指定（下の段階 2 の生成器のパラメータ）
  - renderer は仕様を組み立てる。注記・お知らせ帯・事実だけの文言・contrast・overflow の検査はそのまま
  - test: 仕様の schema・事実の無い節を出さない・すべての組み合わせで overflow 無し・注記が見える
- **段階 2: 造形と文字組の生成器**
  - 罫・枠・地紋・図形を、パラメータから SVG / CSS で描く生成器（色は palette の役割だけ、文字を足さない）
  - 店名の文字組（縦書き・字の大きさの変化・ロゴ風の組）を、事実の店名だけで組む
- **段階 3: 店ごとの CSS 生成の試験（local preview だけ）**
  - 固定の意味構造（事実だけの HTML、class は安定した名前）に対して、仕様から店ごとの CSS を生成する
  - CSS の検査器: 構文解析 → 許可した性質・値だけ（`url()`・`@import`・`content` の文字・`position: fixed`・外部の font・`expression` などを拒否）・注記とお知らせ帯の領域に触れない（機械検査: 位置・大きさ・contrast・visibility）・全事実が見える・overflow 無し
  - 評価: 同じ架空の店（または人が承認した店）で A/B と C を比べ、審査の点と人の目で決める
- **段階 4: C を公開の demo に使うか（人の判断）**
  - 使うなら、生成した CSS は検査済みのものだけを DB に保存（大きさの上限・hash）し、demo の頁で読む。公開前の機械検査を server でもう一度
  - 費用（Codex / Claude の使用量・時間）と品質の結果で判断する

## 6. 今すぐの設計変更の提案

1. 「Codex は語彙から選ぶだけ」という DEV-028 の原則を、**「Codex は仕様を書き、Claude 側が組み立てる。公開されるのは検査器を通ったものだけ」**に改める（MVP の重大な変更にあたるので人の承認が要る）
2. `RENDERER_CHANGE_NEEDED`（renderer の機能が要るときの BLOCKED）を、**次の部品の候補を集める仕組み**として使う。今は止めるだけで、何が足りなかったかの記録が残らない（Codex の言葉は残さない規則のため）。足りない機能を固定の符号の一覧で答えさせ、件数を数える
3. 審査の基準は変えない。ただし、方式の天井を知るため、実走の結果（点・軸ごと）を方式ごとに記録する
4. DEV-029 の `generated_concept`（人が作って入れた「イメージ画像」、local preview だけ・ラベル付き）は、今回の方針（画像生成 AI で架空の店舗写真を作らない）と相容れない。**公開に使えない今の制限を保ち、使わない方針を明記するか、機能ごと外す**かを人が決める（提案: 外す）

## 7. 人に決めてほしいこと

- この方向（B → C の段階移行、D は採らない）でよいか
- 段階 1 を始めてよいか（コードの変更だけ。実走は別の承認）
- 実行時に Claude（WSL の jail の Claude Code、サブスクリプション）を店ごとの実装に使う案を、段階 3 の試験で比べてよいか
- `generated_concept` の扱い

## 8. 人の決定（2026-10-20、正式承認）

1. B（Design Spec + Components）→ C（店舗別 CSS 生成）へ段階的に。D は採らない。B は中間段階で、最終目標は「Codex が店舗独自のデザインを考え、Claude がその店舗専用の Web デザインを実装する」。テンプレートの variation を増やすだけで完成としない
2. Stage 1 を承認: Codex が店舗ごとに、節の構成と順序・節ごとの layout・タイポの階層・配色 / 余白 / 装飾・first view の構図・ブランドに応じたデザインを設計する Design Spec。根拠の無い節は出さない。店舗情報・商品・口コミ・実績を創作しない
3. Stage 3 の技術検証を承認: 隔離された WSL 環境で Claude が店舗別 CSS を生成する方式を、ローカルのテストデータで比較検証してよい。実際の WSL worker への投入・Staging 実走・公開 demo への適用は別に承認を求める。生成 CSS の制約: JS・外部コードの実行禁止 / 外部通信・任意 URL 参照禁止 / 店舗情報や注意書きを隠す CSS 禁止 / font・contrast・可読性の検証 / PC・スマホの崩れの検証 / 構文解析と許可リスト / 不合格なら既存の安全な表示へ / jail からの秘密情報アクセス・権限拡大の禁止
4. generated_concept: 使われていない・依存が無いことを確かめて画像生成経路を削除。AI 生成の架空の店舗写真は使わない。Instagram 画像は取得・分析とサイトへの再掲載を区別し、利用許可なしに公開しない
5. DEV-067・068・069 は Fresh Review と CI を通して完了。日本語 font の build サイズは、実際に使う font・weight だけにして WSL の負荷を抑える。その後 Stage 1。各段階で比較: 店舗間の構造・見た目の違い / 実画面での改善 / 品質審査の結果 / 生成時間とモデルの費用 / 安全性と運用の安定
6. 禁止は継続: Staging DB reset・復旧 SQL・cycle 実走・flag 再 ON・Production・timer・実営業送信・権限の拡張・未承認の画像利用
7. 最終的に、業種・ブランドの異なる 3 店舗で明確に違う Web サイトを生成できるかを比較する
